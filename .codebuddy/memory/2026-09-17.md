## 规模承压分析（研报数量增长）

结论：**语义设计可扩展，工程基建未扩展**。

- 可扩展的部分：内容寻址归档（去重、易迁对象存储）、source_id 由字节决定（增量天然幂等）、
  build 不可变 + `active_build_id` 活动指针（检索只扫活动集，历史不拖慢查询、便于未来分区/冷热分离）、
  job 租约 `per (build_id, stage)` + fencing（多 worker 并行安全）。
- 缺口（量级越大越先爆，顺序大致为 重建成本 → 写入吞吐 → 查询 → 存储）：
  无工作队列/调度器（单进程同步解析）、无连接池（`search_pg` 每次 `psycopg.connect` 新建）、
  无分区、无 GIN 批量维护（fastupdate pending list）、长文档 `stage_timeout=600s` 风险、
  `ts_rank` 对候选集全量排序（无 LIMIT 下推）、corpus schema 与主库 `postgres` 共库、
  **I0C-2 冻结的容量门 ≥1GB 偏小**（万份级归档需数十 GB）。
- 量级粗估（一份 20—40 页 → 150—400 chunks / 500—2000 units / 1—5MB）：
  1,000 份 ≈ 25 万 chunk、数据+索引 5—8GB；10,000 份 ≈ 250 万 chunk、50—80GB。
  **存储不是天花板**（单机 PG 可承受），重建与吞吐才是。
- 数字均为量级估算，按项目纪律须在 I2/I3 做实测标定（解析耗时/索引大小/查询 P95），不得凭空承诺。

## 规则 vs 模型的分界（用户反复关心的点）

- 规则的职责边界：只管**可机械验证**的事（保真、坐标、去重、幂等、状态、版本身份）；
  语义判断（评级含义、观点极性、因果、条件）归 LLM；合规/问责（准入终态、金标、删除清单）归人工。
- 防规则膨胀的三道防火墙：① 不确定就标 unknown（`unreadable ≠ absent`、needs_ocr、review_required），
  不要求规则覆盖所有版式；② 规则变更 → rev bump → 受控重建（经济约束抑制随意加规则）；
  ③ 机器特征只给建议，`auto_decision.enabled=false`（新类型进复核队列，不自动加 if-else）。
- 真正会随类型增长的：readers 格式 Adapter（加法，非规则堆叠）、噪声词表/准入特征（应外置为策略
  配置，变更走 policy v2 + 正反例重验证）。
- **R2 不是"取 chunk 再抽一遍"**：R2 读**同一 units + 结构关系**生成候选（`检索块 ≠ R2 原子义务`），
  禁止二次解析源文件产生第二套主正文；模型输出是附加投影（绑定 build_id/parse_rev），不是新权威。
- 门禁顺序：R2-S3 零模型门全过 → 才提交 R2-S4 单轮模型预算（建议 ≤8 调用含 preflight、零重试）；
  **当前 R2-S4 未授权**，须先完成 I2 → I3 基础过门。
- 已向用户给出 R2 抽取端到端**合成示例**（接收→准入→units→clean→chunk→发布→LLM items→权威校验
  →失败路径→版本联动），演示"LLM 只做结构化，事实由底座提供、模型无权改写 raw_text"。
