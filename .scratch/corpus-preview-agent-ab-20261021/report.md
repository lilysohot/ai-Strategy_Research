# 证据预览：小范围主 agent 对照实验

结论：预览在部分问题上能减少原文回查，但这次没有证明稳定提速或降费。维持默认关闭，保留隔离库试验开关。本轮未修改业务代码、.env、索引或题目。

## 实验条件

- 沿用原题 p01（正文解释）、p16（两家公司 NPO 产品对照）、n01（未命中目标公司）。每题 off/pilot 各一次，共 6 次，串行独立进程；p16 反转开关顺序。
- 真正运行 stateful-react-agent / tui，模型 glm-5.3-flash（供应商返回 glm-5-3-flash-260828）。混合检索与原始向量 profile 固定；仅改变 CORPUS_EVIDENCE_PREVIEW。
- 同问题提示、采样参数、工具预算和运行上限：12 轮，研究预算 300 秒，单次输出上限 8192 tokens；原有证据清单自动校验仍运行。
- 仅开放 corpus_search/corpus_fetch，工作流照常自动接入 corpus_submit_manifest。未开放外部搜索或文件操作工具，答案标签不进入模型提示。
- 18 个已发布来源、703 块的同一发布快照，原始向量 profile 为 fbd9941b77ff17a534932b7bbec32358ae5088df9854d62a93b2e38801c3e107。
- 题目是既有已读样本，单次随机采样；agent 自行改写的查询并不相同。因此这是运行行为观察，不是隔离所有变量的统计实验。

## 实测结果

下表均为“关闭 → 开启”。总耗时包括模型生成、工具、校验和异常等待。

| 题目 | 总耗时（秒） | search 次数 | fetch 次数 | 返回原文正文（字符） | 结果 |
|---|---:|---:|---:|---:|---|
| p01 正文解释 | 183.9 → 115.8 | 2 → 2 | 4 → 2 | 4,812 → 2,125 | 两侧均回答主要机理；开启侧一次向量请求约 15 秒后降级，时间比较有干扰 |
| p16 两家公司 | 49.6 → 277.2 | 2 → 2 | 1 → 2 | 2,068 → 5,111 | 关闭侧完成；开启侧已取回两家公司证据，但引文校验失败后模型无响应，llm_error，无有效最终答案 |
| n01 缺少目标公司 | 66.9 → 173.3 | 5 → 7 | 2 → 1 | 1,634 → 216 | 两侧均没有套用其他公司数字；开启侧回查更少，但搜索和生成更多 |

不能用少回查直接推导速度或成本下降。p01 的核心解释在两侧保留：互连数据搬运耗能、缩短走线、降低电压及电压平方关系。p16 预览侧读了正文 0003–0006，并用游标取得后半部分；华工正源 6.4T 去 DSP 与立讯 3.2T Live Demo 均在实际取回正文中，未观察到漏读某家公司的证据，但回答没有完成。

p16 关闭侧虽然初始申请多个块，第一页的 body:0001 已同时给出两家产品，随后就作答，没有读完全部申请范围。原完整取证范围本来就不代表会全部阅读。开启侧首轮结果中也有包含两家信息的 body:0001，却选择了后面的其他块；这说明模型不一定采用最省的 core_fetch_plan，不能将计划大小当作真实节省。

n01 开启侧搜索结果总字符量约 11.23 万，关闭侧约 7.58 万，解释了为何正文读取少了，整体上下文负担仍可能增加。两侧回答都把“未检索到”说成“库中不存在任何资料”，这个表述比检索证据更强；本轮保留问题，不把少回查当作完全正确的拒答证明。

这是多轮请求累加的供应商 usage，不是唯一正文 tokens，也不是实际账单。p16 开启侧失败请求可能没有完整 usage，不拿失败运行的较少 tokens 证明省钱。未按价格换算人民币；缓存计价与异常请求计费未知。

共 20 次搜索、12 次 fetch；19 次成功使用混合检索，1 次 provider_transport_uncertain 降级词法。已报告查询 embedding 用量合计 701 tokens，降级请求用量未知。没有重建文档向量，没有自动重试不确定的 embedding 请求。廉价 preflight 另计。

p16 开启侧模型在第 5 轮出现约 180 秒无流式内容，最终 llm_error。其耗时不能归为检索功能变慢。其余普通搜索／读取调用多为亚秒级；单次工具耗时的加总不能直接从总墙钟时间中相减，因为同轮工具可并行。

## 计数与复核

原始 observations.json 保留未裁剪工具输出；轨迹中的消息会被诊断落盘机制截短，不能直接按它统计模型可见文本。summarize.py 用本项目实际 ReactToolResultPostProcessor 对原始输出做确定性回放，按真实工作流预算计算正文和搜索结果大小，并根据轨迹确认其后有 assistant 响应。该口径表示可送入上下文的内容，不证明模型理解或使用了每个字符。

正文计数只含 corpus_fetch 的 text / items[].text，不含搜索 preview、元数据、所有可扩展定位块。正文重复按完全相同片段去重；不做部分重叠区间的高级去重。6 次运行的两种计数一致。

audit.json 核验两侧问题提示哈希、模型、预算、向量 profile 一致；所有搜索来自同一发布快照；开启侧的 11 次搜索均成功附加预览，关闭侧没有预览。answers.md 保存答案和搜索／读取计划，runs/ 保存全量日志。summarize.py 可离线重算，不发模型请求。

两阶段 import smoke（402/402、451/451）、符号检查（500 文件、0 缺失）、实验脚本语法检查与 preflight 通过。本轮仅增加实验记录并更新规划文档。

## 下一步建议

先保留默认关闭，不扩大入库、不改 RRF。优先改善消费方式：多对象问题优先选择同一片段已覆盖所有对象的证据；相关证据已足够时停止扩展；多次搜索仍未匹配目标公司时明确“当前检索未找到”，避免泛化搜索和绝对缺失断言。另将逐字引文校验与模型接口停滞独立处理。

后续若要证明提速，再对固定题目做重复配对，把 API 降级和失败运行单列，并同时考察成功回答、搜索轮次、模型总输入与正文读取量。本次不计算整体提速百分比，也不据这 3 题切换默认。
