# Corpus 内容推导价值与架构质量评估

评估时间：2026-09-12。对象：当前工作区代码、只读 PostgreSQL 数据、现有人工标注资料、本地源 PDF。此评估包含用户尚未提交的 `claims_v2.py` / `audit.py` 修改，没有修改业务实现或数据库。

## 判断与证据范围

原始资料包含有用的财务预测、历史数据、行业线索与观点。但当前产物适合辅助定位、阅读和提出研究问题，尚不能作为默认可信的自动财务推导数据源。问题横跨解析保真、证据组织、抽取完整性、数值坐标和验收标准。

不能据此声称“每个 block 都差”：没有对 1,096 块逐条人工评分。以下区分全库客观统计、真实样本核对、代码反例和尚未验证的风险。归档页、检索块、计算证据本就不应共用一个质量定义。

检查范围：

- 实时库：87 份文档、1,096 块、1,318 条 v1 claim；v2 claim 和 v2 运行记录均为 0。
- 本地可精确匹配源文件的 PDF：58 份，共 889 页。扫描的是文字层与图像存在性，不代表逐页人工看图。
- 视觉核对：华创证券贵州茅台 2026 年中报点评，第 3 页，完整财务预测表。
- 人工标注资料：full87 基线、180 块候选评估及字段金标状态。
- 6 个合成反例调用实际生产函数，无模型调用、无数据库写入。

可重跑文件：同目录 `probe.py`、`test_quality_contracts.py`；本次指标保存在 `findings.json`。没有把原文复制成公开测试 fixture。

## 金融分析师视角：资料能支撑什么

可用于计算的数据点需要同时回答：谁的什么指标、数值及单位、哪一期间或时点、何种口径、事实还是预测、当时何时可知、来自哪一个可定位来源。这与 XBRL 将事实值绑定到 concept、entity、period、unit 和其他维度的处理一致。参考 [XBRL International 的事实与维度定义](https://www.xbrl.org/guidance/xbrl-glossary/)。这是质量设计参考，不要求本项目立即采用 XBRL 格式。

| 内容类型 | 可以形成的研究价值 | 进入推导前必须保住的内容 |
|---|---|---|
| 财报与财务预测表 | 增长、利润率、现金转化、估值情景、跨机构预测分歧 | 公司、三表分类、行列坐标、金额单位、币种、实际/预测年份、合并/归母口径 |
| 行业供需与经营数据 | 量价拆分、景气方向、产能利用率、产业链敏感性 | 产品和地区、统计样本、计量单位、时间、同比/环比、存量/增量 |
| 宏观点评 | 实际值相对预期的差异、修订、政策情景 | 实际/预期/前值/修订值、发布日期与数据期、季调与年化口径 |
| 技术图表、交易复盘 | 提出假设、识别交易条件和风险、记录当时观点 | 图像、作者、观察时点、标的、指标参数、条件和失效点 |
| 个人期权记录 | 交易事件和个人行为分析 | 买卖方向、开平仓、call/put、执行价、到期日、权利金、数量，不能只留一个价格 |
| 二次整理、翻译、投委会报告 | 导航、观点与推导草稿 | 原始来源链、原文/译文对应关系、作者假设、公式，不能把重复转述当独立验证 |
| 目录、页眉、销售和免责声明 | 归档与文档属性 | 保留归档价值，按区域排除抽取；不是每一页都需要产生 claim |

### 真实例子：原表存在研究价值，产物损失了关键变量

来源：`doc_id=2026-08-16_6f14cc14`，华创证券贵州茅台中报点评，第 3 页。原表单位为百万元，列为 2025A / 2026E / 2027E / 2028E，页脚注明公司公告与华创证券预测。本次验证这些数值确实出现在用户文件，未独立认证文件出版真实性或预测正确性。

| 行 | 原 PDF 四列 | 当前 block |
|---|---|---|
| 研发费用 | 190 / 197 / 206 / 215 | 行名保留，四个数值全部删除 |
| 财务费用 | -815 / -875 / -781 / -680 | 行名保留，四个数值全部删除 |
| P/E | 20 / 20 / 19 / 18 | 行名保留，四个数值全部删除 |
| 应收票据 | 0 / 0 / 0 / 0 | 四个零被删除，零值与缺失混同 |

页内共 131 行匹配整数清洗规则，其中包含页码，因此不能把 131 全部当财务单元格。当前 `parse_pdf()` 重跑仍得到同样的 2,830 字符 block，且没有补抽表格。这是持续可复现的解析损失。

从原表可以确定性重算：

- 2026E 营收增长 = 178,657 / 172,054 − 1 ≈ **3.84%**。
- 2026E 归母净利润增长 = 84,679 / 82,320 − 1 ≈ **2.87%**。
- 2026E 经营现金流变化 = 25,756 / 61,522 − 1 ≈ **−58.14%**。
- 2026E 经营现金流 / 归母净利润 ≈ **30.42%**。

研究问题由此变得具体：为什么预测利润温和增长，预测现金回收却显著下降？是营运资金、存款及金融资产分类、其他调整，还是模型口径导致？这组数据能支撑追问和情景检查，尚不能直接得出企业实际经营恶化的结论，因为 2026E 是该来源的预测。

当前该文档的 claim 指标集合以资产负债表为主，没有保留上述归母净利润与经营现金流组合，因而丢失了这条推导路径。不能把所有缺失都归因于同一个清洗规则：输入截断、模型选择与输出上限也可能影响抽取覆盖。

原文自己也需要合理性核对：按表内 2026E 净利润 87,841 / 营收 178,657 重算为约 **49.17%**，而同页“净利率”列示 **50.2%**。这应进入“公式或口径待核对”，不能静默把任一值当权威，也不能未经核对就断定原文错误。可以复算的内容才允许进行这种检查。

### 非数值内容的价值被当前定义压缩了

例如 `2026-09-02_f273e2ca` 第 1 块同时有英文原文、中文翻译、标题重复和网页按钮文字。它还包含有价值的条件句：作者的市场判断可能因油价变化、协议消息而逆转。若只留下“油价 90”“VIX 16”，就丢掉标的、观察语气、不等式、条件与反证。

`claims.py` 的共享 prompt 明确排除一般背景、偏向数字/评级，v1 triage 也要求数字。v2 虽新增 qualitative/personal_trade 入口，仍继承这个数字/评级共享骨架。候选召回更广不自动意味着研究逻辑能够完整进入最终输出。

“是否含可抽取信息”和“是否足以支持投资推导”应分开标注。情景、反方证据和失效条件不需要硬塞成数值事实；它们需要保留与相关事实的关系。

## 架构师视角：逐模块评估

| 模块 | 当前有用的设计 | 对数据合理性的支撑与缺口 |
|---|---|---|
| `__init__.py` | 保留薄入口 | 包说明仍写“不得依赖 LLM”“纯标准库”，与现有实现不符，易误导维护；非主要坏块根因 |
| `ingest.py` | 解析与落库可分别测试；有源文件 hash、顺序和 locator | **关键缺口**：按页纯文本、删除整数行、可选表格静默降级、无版面坐标/表格单元格模型；文档平均字符数不能诊断局部图片页；DOCX 仅遍历 paragraphs，表格未纳入；MD/DOCX 标题不留在正文，父级标题链消失 |
| `metadata.py` | 有机构、主体、分类、发布日期派生和人工分类覆盖 | 文件名日期优先，正文首个日期可兜底；缺字段级来源与置信依据；v1 分类仍被它使用，与 v2 分类逻辑可能不同；文档类型无法代表页内所有事实的类型 |
| `index.py` | SQLite 旧路径的数字单位 token 绑定、标题加权可复用 | 当前生产工具实际走 PG `service.py`；不可把 FTS5 的测试成绩当 PG 质量证明。检索命中不是证据充分性 |
| `fetch.py` | 定位归一化、FetchedBlock、旧 SQLite 只读取证逻辑 | 生产主要复用返回类型并走 PG。返回的是处理后文本，没有原页区域、表头、脚注和上下文包；依赖 ingest，读写依赖分离也不彻底 |
| `service.py` | 工具统一入口、参数化 SQL、块结果与运行台账原子提交、续跑与备份 | **关键缺口**：存储、检索、抽取编排、去重、迁移、运维聚合在一个模块。调用方仍需知道质量和版本细节；文件 hash 幂等会挡住同文件解析升级；v1 去重不含主体与口径。一个最高分页代表整份报告，未返回计算所需证据组合 |
| `claims.py` | Decimal、部分单位规则、领域插槽、重试、保留原始数值 | **关键缺口**：2,500 字符输入上限；缺精确 evidence_quote 和硬字段校验；以文档类型约束所有 claim；industry 提示词强制 ticker 空；评级被归 forecast；表格前缀与正文指标名不统一 |
| `claims_v2.py` | 原始/派生字段区分、证据类型、scope、期间、known/observed 时间、质量状态、影子表方向合理 | **当前未产数据，且关键反例放行**：虚构 table、数字子串匹配、缺单位/期间；金额改单位未同步换算值；table_ref 尚不是可验证的真实表格对象；旧 prompt 语义冲突未清除 |
| `audit.py` | 候选覆盖、状态、台账成本、字段完整性集中审计 | 数值只在整块做子串存在性检查，抓不住错主体、错年份、错列；候选判定与被测系统共用规则，缺独立金标时不能证明准确性；无数值分母时 rate=1.0 也需防误读 |
| `golden.py` | 有可重复检索题集、按题型看召回 | 命中依据是标题包含与文档前缀，不检查命中页、单元格和推导结果；Recall@5 高只能支持文档定位能力 |
| `verify.py` | 逐字引用、市场取证检查、仓位数值复算、schema 闸 | 语料 quote 以整篇 document resolver 验证，未把 evidence.page 纳入该匹配；不能证明“某指标在某页属于某主体”；算术闸主要检查仓位，不检查财报勾稽与估值模型输入 |
| `strategy_schema.py` | 共用 schema 与 evidence 枚举，降低多个消费者漂移 | 约束策略卡形状、来源字段和仓位参数，无法补偿上游错值；目前没有完整的推导输入 IDs、公式版本和维度检查契约 |
| `research_discipline.py` | search 与 fetch 分工、禁止凭空补数字、反方证据、缺覆盖降级 | 是提示约束，需配合确定性取证与计算执行。原文定位经过破坏性清洗后，提示要求本身无法恢复数据 |

### 关键接口为何还不够深

`CorpusService` 的接口对调用方隐藏了数据库驱动，却没有充分隐藏并承担“证据可用于某次计算”的复杂性。调用方仍需猜测缺失单位、回找表头、判断期间、修复文档级主体和审查 quote。这些工作应由明确的证据准备与验证模块承接，通过小接口返回结果与无法使用的原因。

建议保留内部多个可测试 seam，而不是仅以文件长度拆分：

1. **解析模块**：输入原文件与解析配置，返回带坐标、表格、图片和解析诊断的文档结构。
2. **证据组织模块**：输入命中区域或问题，返回正文/表格与必要上下文、来源锚点和覆盖状态。
3. **claim 抽取模块**：输入证据包，返回候选事实与精确引用；模型不能裁决自己的正确性。
4. **规范化和验证模块**：返回可引用、可比较、可计算的用途状态以及明确原因。
5. **仓储与运行编排模块**：持久化版本、运行台账、不可变输入和派生 lineage。

这些 seam 的测试应从调用方实际使用的接口穿过：输入一份含表格的真实版式样本，断言关键事实和推导证据完整，而不只断言 `_render_table` 能用竖线拼接字符串。

## 已复现的六个质量契约反例

诊断文件 `test_quality_contracts.py` 用合成文本，直接调用当前实现。六项全部产生断言失败，进程退出码 1：

| 反例 | 当前结果 | 后果 |
|---|---|---|
| `Revenue\n100\n120` 清洗 | 只剩 Revenue | 金额永久从解析文本中消失 |
| `evidence_kind=table`，伪造 row 与 quote，源块无对应内容 | ok | table 类型绕过散文的原文存在性检验 |
| 原文是 120，claim value 是 20 | ok | 数字子串被误认为证据 |
| 营收事实没有单位和期间 | ok | 单一 ok 状态无法表示计算适用性 |
| 原始 `2 亿元` | `value_num=2, unit=元` | 规范值与规范单位组合差 10^8；`claim_observation_projection()` 还省略 unit_raw。旧版兼容转换保留 unit_raw，问题尤其针对 v2 默认投影 |
| 两个不同公司的同期间 revenue | 去重只剩 1 条 | `_dedup_claims` 的键不含 ticker；跨块删除亦不含主体。行业路径把主体写进 metric 能减少部分冲突，但不足以保证所有输入安全 |

另有代码层风险：`source_rev` 取源文件字节 hash，`ingest_path` 碰到相同 hash 直接不写 blocks；`ingest_dir` 跳过未变文件。因此仅修解析器再跑普通 ingest，不会自动更新旧 block。正确重建需要把源文件版本与解析产物版本分开管理，并使下游 claim 失效。

当前 `blocks` 缺少原文 span/bbox、表格 ID、章节路径和解析版本。无这些锚点，table_ref 只能是一组模型生成字符串，校验无法可靠证明行列关系。

## 为什么现有评测看起来通过，实际阅读感受却很差

`c2_full180_block_validation_20260912.json` 的确记录候选 precision/recall 和 doc_kind accuracy 为 1.0。但它同时记录：133 个正样本全部是 `label_claims_json=claim` 占位符，字段级有效 JSON 为 0。相关施工文档已经明确这是块级门槛，不能把它解释为字段抽取验收。

`golden.py` 的命中只识别文档，不判断答案是否落在正确页。`audit._trace_values` 只检查数值片段出现，当前只报 2 个未命中，但它也允许 `20` 匹配 `120`，不能解释为其余 1,316 条正确。

表格真实样本测试只需要找到一份能抽到数字的表格；前 5 份未发现表格还会 skip。它不会因为茅台财务表的关键整数被全部删除而失败。

本次环境的 WSL PATH 中无 uv，现有 `.venv` 无 pytest，因此没有取得现有 pytest 套件的执行结果；没有新增依赖。反例用现有 Python 的独立 runner 实际执行，数据库探针与原 PDF 解析也已实际运行。没有运行会调用真实模型的 preflight。

## 建议修复顺序与验收标准

### P0：恢复可信数据输入与用途门禁

1. 数字清洗改为基于版面位置、跨页重复及区域类型，保留整数、零、负数、会计括号。源文件和未经清洗的解析输出可回溯。
2. 金额采用明确契约：`raw_value/raw_unit` 保留原样；`normalized_value/normalized_unit` 成对换算，并记录币种、倍率。零、缺失、不适用分开表示。
3. 证明 table_ref 对应真实表格对象，按行、列、表头和数值 token 校验；数值引用带符号、精度与单位，禁止子串证明。
4. 分开“可引用”和“可计算”：营收等需要期间与金额单位；价格需要观察时点与币种；比率要求指标定义；观点可不含数值，但不能进入数值聚合。
5. 去重键包含主体、指标、期间、口径、事实/预测身份和来源/版本；冲突应记录为冲突，不能按最后出现默认覆盖。

验收：本次六个反例按确定的契约转绿；茅台第 3 页上述四组数值完整保留；能对两年营收、利润和现金流给出逐输入引用。此后再进行受控、版本化重建，不能直接覆盖生产数据。

### P1：把页面组织为可推导证据

保留页面作为归档定位单位，另建抽取用的证据包。财务表按表/行组组织，重复必要的列头与单位；正文保留父级章节、同段条件和相关脚注；跨页续表明确连接；图片页进入待视觉解析状态。输入超长时按结构分页处理，不能以字符串截断等同“完成该块”。

解析产物应绑定 source hash、parser/version/config、OCR/layout 版本；claims 绑定证据包 hash、模型、prompt、normalizer 和 lint 版本。模型完成前缀、块处理完成、文档覆盖完成分别计量。

### P2：用推导题验收研究价值

从已标注的 133 个正块里选择代表公司、行业、宏观、图表和交易记录的样本，补独立字段金标，并冻结未参与规则修改的留出集。

| 验收层 | 应检验的结果 |
|---|---|
| 解析保真 | 数字与符号保留率、表头/单位恢复率、行列归属准确率、扫描页识别、正文条件是否保留 |
| 字段准确性 | 主体、指标、单位倍率、币种、期间、实际/预测、修订状态分别正确 |
| 证据正确性 | 引用精确落在对应页/区域/单元格；错误主体、错列、错值的拒绝率 |
| 研究充分性 | 增长率、利润率、现金转化、预测修订或供需推导的所有输入是否齐全 |
| 推导复现 | 公式、计算代码版本、输入事实 IDs、单位检查和容差可回放 |
| 合理性检查 | 资产=负债+权益、净利润=归母+少数股东、增速复算、原文比率对账；失败回到原文口径核实 |
| 多来源独立性 | 同一来源的译文、转载和不同页面不能被计为多份独立证据 |

在证据组织完善后再选择是否引入布局解析/OCR或更强抽取模型，使用同一冻结样本比较关键事实保留、错误拒绝、成本与耗时。单纯提高 claim 数、候选召回率或检索命中率，不足以验收这次问题。
