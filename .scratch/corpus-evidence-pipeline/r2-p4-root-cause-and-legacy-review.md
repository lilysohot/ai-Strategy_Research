# R2 P4 流程回溯、旧流程边界与重整评估

日期：2026-09-14  
性质：诊断与实施方向评审；对上一轮归因作补充和纠正，不改写历史响应、预算、人工裁决或评分结果。  
依据：用户最新明确项目仍处实验阶段，数据库数据可以重塑，阻碍整体目标的旧流程可以重整或剔除。

## 1. 结论

本次直接失败点是模型把 3 条风险和 1 条问句填进不允许的 semantic_type。但主要流程错误位于
**P3-I → P4 的集成与验收移交**：人工字段投影完成后，没有验证正式运行路径能够独立产生同一输入、
传递完整字段契约并接受同一验收，便另建 scratch 执行器消费了模型预算。

没有证据表明 PostgreSQL 的数据、表结构或旧材料抽取器导致这次枚举失败。实际 P4 从本地人工投影、
微金标和原文件生成请求；重建数据库不会改变这段请求或评分逻辑。

需要调整此前“保护旧流程”的执行方式：保护已有研究能力与可追溯性，允许替换旧实现、字段、表和
入口。2336 文件逐字不变不再适合作为后续改造的普遍成功条件。现有单轮冻结记录继续保留为历史证据，
用户本次说明改变的是今后架构选择的边界，不会追溯改变上一轮预算或当时数据库访问事故的事实。

本轮只完成诊断、反例及文档更新；新增模型调用 0、数据库连接 0，没有执行删表或迁移。

## 2. 可复现证据与失败因果

复现命令：

```bash
uv run python .scratch/corpus-evidence-pipeline/p4_flow_diagnosis.py
```

脚本封锁网络和 psycopg 连接，读取已冻结响应，执行反事实与合成反例；所有修改只发生在内存。
输出见 [诊断证据 JSON](r2-p4-flow-diagnosis-evidence.json)。这些探针确认缺陷仍存在，不是修复后验收。

### 2.1 模型直接错误：已确认，但不是全部原因

首批实际发送 8 个义务，收到 8 行合法 JSON、8 个正确且唯一的义务 ID、8 个 extracted 终态；
4 行因 semantic 枚举失败，严格接受 4 行。连续两次原样回放结果相同。未发送的其余 27 个义务
属于未评估，不能统计为 27 个模型语义错误，更不能据此宣称其所属类目发生退化。

只在内存把 risk→forecast、question→unknown 后，首批协议可接受率由 4/8 变为 8/8；仍有：

| 字段 | 首批与冻结目标不一致数量 |
|---|---:|
| speaker_ref | 7/8 |
| behavior_status | 8/8 |
| unknown constraints | 7/8 |
| value | 2/8（其中首批非空 value 为 3 条） |
| polarity | 3/8 |
| temporal_frame | 1/8 |

枚举映射只是用于排除“修正 4 个标签即可完成”的假设，未应用到真实结果，也不构成新通用规则。
provider 返回 finish_reason=stop，输出 1564 token，低于 4096 上限；本次没有响应截断或超时证据。
原文风险提示及预测数字均在模型上下文中，尚不能归因为文档格式损坏。

### 2.2 字段契约没有完整进入执行输入：已确认

- R1 已写明行为状态“仅行为使用”，P4 只传入含 null/unknown 的枚举，未传入不适用规则。
- 公司报告 7 条目标要求 identity=explicit，但请求只有短句、局部上下文及 ID，没有作者元数据、
  姓名证据或身份判定规则。原文局部可推断作者声音，不等于明确个人身份。
- P3-I speaker registry 从金标 role/identity 推导。上一轮把它称为可以直接注入的“系统已知事实”
  不严谨：它首先是评测目标。只有独立来源元数据或可回取原文支持的身份，才可进入运行输入；否则
  必须保留未知，或把人工协助作为显式产品模式并计入人工成本。
- P3-I 的 3 个 value transform 是按 target_id 登记并检查数字 token 存在，随后直接返回金标 value。
  这足以描述获批目标，尚不等于从任意来源执行可复算的通用转换。P4 未调用这些转换，也未向模型
  说明其完整语义，却用转换后的字符串作精确目标。

例如 EPS 目标包含期间、三个预测数和单位的复合表达。仅给“value 保留来源表达、unit 单列”不能
明确决定哪些片段组合成 value。需要来源 span 和转换实现，不能以目标字符串回填运行结果。

### 2.3 验收与实际执行走了不同路径：关键集成错误

| 路径 | 当前真实接线 |
|---|---|
| service 材料理解入口 | `CorpusService.understand_material` → `build_evidence_run` → `material_semantics.extract_material_understanding` |
| P2 新实验实现 | `_r2_runtime.prepare/execute/validate` + `_r2_plan` + `_r2_audit`，尚未成为上述 service 入口 |
| 本次 P4 | `p4_item_trial.prepare/execute/score` → P3 人工投影/微金标/源文件读取；自建请求、审计与评分 |

动态跟踪本次 prepare/parse 没有执行 `material_semantics.py`、`_r2_runtime.py` 或 `CorpusService`；
对 `_r2_plan` 的直接复用是 digest，不是正式规划入口。

P4 `prepare()` 遍历 evaluation projection 的 35 records，直接取 approved_node 作为原子义务。
移除评测投影后它无法 prepare。unknown 词表也由这些目标约束汇总而来。这可以作为明确标注的
“人工给定原子边界后的字段试验”，但不验证自动发现原子边界、全文覆盖或无需人工的运行能力。
检查 prompt 中不存在 `expected/target_id` 等键，无法证明整条运行链独立于金标。

P4 的 PDF 局部上下文由 `p3_replay_review.scope_text` 使用 pypdf 重读行范围；正式证据解析器使用
`evidence.py` 的 pymupdf 路径。当前未证明两套坐标/文本完全等价；这属于接线与可迁移性缺口，
不是已经证明本批文本被错误解析。

P1 要求逐字段 origin、support_span_ids、transform_rule_id、unknown_reason；P4 的 FilledFields
没有这些字段。P4 也没有生成供 P2 validate 接收的同一结果协议。因此前置测试没有闭合计划所要求的
“生产和测试跨同一接口”。这是上一轮实现与准入检查的遗漏，不能归咎于用户人工填写不充分。

### 2.4 评分器的通过/失败含义发生了偏移：反例已确认

1. **G2 忠实度检查过弱**：score 计算输入 source_text 的 hash 后，只用其非空性作文本条件。
   合成探针替换 source_text、保留原 ID 和完美字段，独立 score 仍判通过。execute 的 verify_plan
   会挡住被篡改计划，所以这不是已观察到真实执行接受伪造原文；它证明 scorer 不能独立支撑 G2
   的忠实度声明。条件、否定和适用范围也不能由 unknown 字段清单代替验证。
2. **G6 把非回归变成隐含全对门**：合成探针仅改错 1/35 个 semantic 标签，G3=passed（97.14%），
   G6=failed。G6 实际按 scope 全字段逐条相等判断，没有比较基线，也没有实现逐类差异度量。
3. **G3 不等于契约规定的标签 precision/recall**：实现只计算全局 semantic accuracy，再将关键轴
   混合统计。即使分数很高，也不足以替代逐标签、逐类、关键错误分别报告。
4. **状态混合**：枚举错被计为 G0 identity 失败，未发送义务也被计入 missing 和语义分母；范围未评估
   与业务错误没有分开。当前总结果仍不应放行，但失败分类必须修正。

27 项 P4 测试与 66 项组合测试主要证明生成的完美字段可过自建 scorer、常见 mutation 可被拒绝，
不能证明真实输入可观测、正式链路已贯通或上述评分定义正确。

## 3. 此前“旧流程”到底包含什么

| 对象 | 具体实现/数据 | 后续处置建议 |
|---|---|---|
| 来源入库、检索和取证 | `ingest.py/index.py/fetch.py/metadata.py`，`CorpusService.ingest/search/fetch`，documents/blocks、入库台账 | 保留检索和原文取证能力；表、解析和 locator 实现可重整，重新生成索引后按业务用例验收 |
| 当前证据与来源内财务核对 | `evidence.py/evidence_pipeline.py`、`claims_v2.py` 中共享模型/校验、`_semantic_validation.py`、`derivation.py`，corpus_evidence_runs | 保留证据关联、用途约束、确定性计算；实现和 schema 可按新契约重构，不强求每个旧字段延续 |
| 历史 claims 抽取与兼容 | claims/claims_v2、claim_block_runs/claim_block_runs_v2；`extract_legacy_claims`、v2 表读写、`--legacy/--v2`、错峰脚本 | 优先退休候选。新默认入口已不依赖这些表的自动 fallback；清理所有消费方后可结束兼容并重建数据 |
| 当前及历次 R2 实验 | `material_semantics.py`（2461 行）、P2 `_r2_runtime/_r2_plan/_r2_audit`、P3/P4 scratch 实现 | 它们都是未完成业务验收的候选，不该全部永久冻结。归并到一条主执行链；旧响应和失败报告留档，旧执行入口可退役 |
| 与 R2 无关的公共能力 | Agent 框架、CLI 审批/沙箱、市场工具、仓位与策略检查、Web | 维持职责和必要用例；按影响范围检查，不让 Web 历史运行目录阻塞语义开发 |

必须注意模块级依赖：`claims.py` 仍提供模型 client/响应类型，`claims_v2.py` 提供共享 ClaimRecord
和校验；`evidence.py` 使用 `ingest.py` 中身份/哈希函数。退休旧表不等于可以直接删除同名 Python 文件。
应先拆出仍在使用的纯模型、解析和身份函数，再删失去调用者的兼容实现。

P0 清单实际按目录广泛扫描：2336 项中 server 有 1735 项，其中 **1706 项位于 server/runs/**。
这些不全是源码，更不是 2336 项“其他类目已验证能力”。当前守卫通过只表示其文件/环境/资产校验
通过；它既不检查数据库行，也不代表逐类模型输出业务非回归。P4 本轮没有重跑完整旧业务快照。

## 4. 实验数据库可重建后的设计边界

采用用户最新前提：实验表、派生结果、检索索引、抽取缓存与旧兼容数据可重塑。历史数据库零变化和
旧 schema 原样兼容不再是永久产品要求。可以从源文件重建 documents/blocks、重新设计证据与材料
产物持久化、移除退役 claims 表和迁移分支。

但本次并未查询当前库目录或行数，不把源码中声明的表当成已核实存在的实际对象。本轮诊断也不需要
操作数据库。落地重建时需先解析确切实验数据库/schema、列对象和消费方、保存必要原始证据与审计、
计算开发重建范围和模型成本，然后执行可重复的重建命令；不把“可以重塑”扩展为删除用户源文档或
将留出样本并入开发。以后是否保留旧 ID 由实际引用需求决定，不能单为保护旧快照增加永久映射负担。

重建对 R2 的帮助在于减少遗留适配和存储约束，不会自动修复枚举、缺少身份来源或评分失真。
`corpus_evidence_runs.payload` 当前本身为 JSONB，本次 wire 的字段限制来自 Python 契约和试验设计，
没有发现 SQL schema 强迫采用这些限制的证据。

## 5. 建议执行方向与完成门

建议先做**主执行链归并 + 验收边界修正**，把 P4-A 从继续扩展 scratch 字段器调整为具体集成任务：

1. **重定保护范围。** 保留原文/人工决定/预算响应等历史证据；允许 R2 模块、必要 parser、service、
   CLI 与实验 schema 的明确范围重构。按能力用例保护四类材料、取证和财务核对，不以全目录 hash
   相等替代验收；框架审批/沙箱等无关机制仍按原要求工作。
2. **统一来源与结果协议。** 正式入口、fake/replay、开发评测共用一个 prepare/execute/validate。
   来源解析、坐标与上下文只走该入口。取证不必先运行数字 Claim 抽取，可将纯 EvidenceDocument
   与语义/计算产物解耦；一个来源可支持多个明确归属的产物。
3. **先证明无 gold 可运行。** 运行模块无法访问微金标和评分投影仍能规划；每个系统填写字段都带
   原文、独立元数据或可执行规则依据。人工边界辅助试验单列，不冒充自动规划验收。
4. **补齐有限字段协议。** 每个模型字段有定义、选项、适用条件和证据要求。字段级义务可以批量
   传输；是否逐轴拆成更多义务需先计算耦合和调用成本，不因本轮失败就认定“拆得越细越好”。
   确定性 span/value 处理必须通用可复算；来源不支持的 speaker 不由金标补齐。
5. **重写有缺陷的验收部分。** 独立验证来源与条件忠实度；标签 precision/recall 与关键错误分开；
   G6 真正比较各类基线；未发送=未评估，非法枚举=协议错误。允许前瞻修正错误标准，保留旧结论，
   不为这批输出改金标凑通过。
6. **退出重复实现并规划数据库重建。** 新链覆盖所需能力后，将旧 R2 入口、旧 claims 写入和无用
   迁移退出主路径；保留失败资产作回放。SQLite/PG 传输是存储 adapter，语义核心不依赖现存数据。
   数据库重建按精确对象与成本计划执行，不抢在语义接口确定前反复重入库。

新模型预算的前置门应包括：正式接口上的真实失败回放与反例、无 gold 运行检查、独立证据支持、
四类开发输出比较、旧取证/计算用例、有限义务容量。当前 1 次已失败预算仍关闭，其剩余 4 次不复用。
完整关系与 CLI 业务验收仍需独立测试；本次重整意见不表示这些能力已完成。
