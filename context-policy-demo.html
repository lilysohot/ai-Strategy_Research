ContextPolicy 图解：白板、托盘与收货清单

state（状态字典）只有一份，像一块公共白板。每个节点门口贴着一张 ContextPolicy（收货清单）， 框架在把白板递给节点函数之前，按清单裁出一个托盘投影。节点看到的永远只是"它声明要看的"。

白板 = 全管线共享的 state ＋ 收货清单 = ContextPolicy.include_fields → 托盘 = 节点函数实际收到的 dict

0三个角色，一分钟对齐

整个机制只需要记住三个东西分别是什么。

🧑‍💼

秘书（框架外壳）

五层包装里的 _wrap_with_context_filter。在把 state 递给节点函数之前，按门口的清单裁剪。节点代码完全感知不到这套机制。

📋

收货清单（ContextPolicy）

声明在图纸（PipelineSpec）里，不在节点代码里。include_fields 是白名单：清单上没有的，节点函数连看都看不见——不是看到 None，是 key 根本不存在。

🗂️

托盘（投影 dict）

节点函数唯一收到的参数。它天生是干净的——只含清单上的字段。工人只看托盘干活，永远不知道白板上还写了什么。

1实弹演练：一条真实管线的四步走

场景：用户在 agent_team（协调者 + reporter）里提问 「分析贵州茅台 2024 年的分红率变化」。下面是管线里白板与托盘的逐步变化。 绿=基础字段 蓝=新写回字段 红=被清单滤掉 悬停字段可看内容示意

🧾 公共白板 5 个字段 · 很瘦

original_question"分析贵州茅台2024年的分红率变化" current_query当前轮的实际查询（多轮时可能与原问题不同） language"zh" task_idrun-20261102-001 metadata画像 / 用途 / 预算等运行元数据

管线刚启动，白板上只有用户问题带进来的基础字段。

📥 main_agent 的托盘 声明 8 收 8

original_question current_query language task_id metadata cross_mode_context continuity_write_enabled continuity_enabled

协调者的清单共 8 项（见 [agent_team/spec.py L29-43]）。此刻白板上的 5 个字段全在清单内，白板 ⊆ 清单，无丢弃。

要点：include_fields 描述的是「启动这个节点需要什么」。协调者是第一个节点，清单里的 continuity_* / cross_mode_context 是跨轮延续性的开关与载体——此刻白板上还没有，属于「清单 > 白板」的情况，框架按 inject/缺省处理。

假设白板因为某种原因混进了一个 legacy_turns 残留字段（示意图）。

📥 main_agent 的托盘 只收到清单内 5 项

original_question current_query language task_id metadata

legacy_turns 被秘书拦在托盘外——节点函数里的 state.get("legacy_turns") 返回的是 KeyError / 缺省，而不是垃圾数据。

关键理解：「被滤掉」不是「置空」，是这个 key 在节点收到的 dict 里根本不存在。 协调者此刻正在跑 38 轮 ReAct 循环（想→查→想→写），但那些过程数据不会经过托盘——它们走的是 messages（节点内部与 LLM 的对话）和 observers（轨迹），与白板是两条通道。

合并走 _merge_state：无 reducer 的字段覆盖，有 reducer 的按规则合并。白板从此变胖。

📤 main_agent 的 output_fields（出口）27 项

final_answer final_content evidence_cards assertions react_steps … 共 27 项

收货清单管「进」（include_fields），output_fields 管「出」—— 一进一出构成节点的完整 I/O 契约，全部声明在图纸上。

不对称是正常的：协调者 include 只有 8 个（启动时白板瘦）、output 有 27 个（白板因它而胖）。 这也是「声明在 spec 里」的直接收益：不用读一行代码，图纸上就写着「白板因协调者新增了这 27 个字段」。

白板 33 项，reporter 清单只勾了 10 项。23 项被拦在托盘外。

📥 agent_team_reporter 的托盘 声明 10 收 10

original_question current_query language task_id metadata final_answer final_content evidence_cards assertions live_followups

5 个基础字段 + 5 个协调者的成品。reporter 的职责是把成品包装成对外报告—— 它不需要看协调者的思考过程（react_steps）。

这正是设计的意图：协调者的「草稿过程」（38 轮循环轨迹、任务完成度、用量统计）对报告者是纯噪声—— 喂给模型只会烧 token、稀释注意力。托盘里只放「写报告真正需要的东西」。

2收货清单的三个旋钮

声明在 frontier_agent/models/pipeline_spec.py L19-37，是一个 pydantic 模型——带字段校验，写错直接报错。

include_fields
白名单（99% 的场景）。托盘里只放这几样。最直观：清单上写什么，节点看什么。

例：reporter 的 10 项清单。
filter_fn
自定义函数（优先级最高）。白名单表达不了的复杂逻辑——比如「只给我 error 状态的任务」。 写一个函数，赢了 include_fields（源码注释原文：Takes precedence over include_fields）。
inject_fields
额外注入。字段不在白板上，但这个节点需要（运行时上下文），框架单独塞进托盘。

另一侧还有 output_fields：节点干完活往白板写什么。
# NodeDefinition 同时声明「进」和「出」——完整 I/O 契约在图纸的一个块里看全
NodeDefinition(
    node_id="agent_team_reporter",
    node_function="workflows.agent_team.nodes.reporter.agent_team_reporter",
    context_policy=ContextPolicy(
        include_fields=["original_question", "final_answer", "evidence_cards", ...],
    ),
    output_fields=["final_answer", "report_contract", ...],
)

3为什么清单贴在图纸上，而不是让节点自己挑？

技术上完全可以让节点函数自己 state.get(...)——那为什么非要提前声明？三个理由，一个比一个硬。

① 数据流要画在图纸上

有了声明，不读一行节点代码就能看出「reporter 消费协调者写的 final_answer」。靠 state.get()，这个依赖就沉进函数体——图纸退化成「一堆函数 + 一个万能字典」，谁依赖谁全靠考古。

② 治理必须发生在进门前

压缩、截断、预算、与工具集对齐——都要求框架在递托盘之前知道节点会看到什么。等节点运行起来自己挑，框架已经失去介入点。声明是治理的抓手。

③ 一进一出 = 可校验契约

include（入口）+ output（出口）凑成完整 I/O。提示词引用的字段不在清单里 → 编译/校验期报错，而不是运行时模型对着缺失字段瞎猜（add_task 事故的同款防复发机制）。

一句话总结

白板（state）管「有什么」，ContextPolicy 管「给谁看」—— 存在性和可见性分离。每个节点按收货清单取一个干净的托盘投影干活，按 output_fields 交回白板； 治理（裁剪/截断/对齐/校验）全部发生在框架层的进门前。 一句话：节点收到的不是白板，是白板按清单裁出来的托盘。
