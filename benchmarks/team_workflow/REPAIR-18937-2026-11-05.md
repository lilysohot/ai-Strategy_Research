# Team workflow repair — Web run 18937

Source run: `18937dbdabb1401296a685aeaa747c0b`.

## Reproduced failures

1. `web_fetch` accepted a JSON-string URL list as two URLs, while the handoff layer recorded
   the original string as one combined source.
2. Recheck context used source order under a fixed byte budget. In the recorded run, 17 of 24
   web bodies were omitted, including all industry and global-market bodies. A fetched paragraph
   containing the 2026 overseas AI-drama USD 650 million estimate was therefore unavailable to
   the verifier.
3. A blocked partial answer could disclose a failed verification and still retain an equivalent
   unqualified absolute claim elsewhere in the final prose.

## Implemented repair

- Web handoff now applies the same JSON-list coercion as the fetch tool to URLs and extraction
  focuses, preserving per-page source attribution.
- Verification passes the bound subject and previous defects to web evidence projection. Evidence
  is ranked against those bytes; when a relevant body exceeds the remaining budget, the handoff
  carries an exact source slice with offsets and an explicit `text_excerpt` marker.
- Failed factual publication checks now protect blocked partial delivery. An unqualified restatement
  with the same absolute scope and topic is rejected; explicit limitations remain deliverable.
- Delivery evaluates missing passed excerpts and retained failed claims during the non-mutating
  preflight, so these defects are returned before task-board or manifest mutation.

## Benchmark extension

- P23: JSON-string and native-list URL batches have identical per-page attribution.
- P24: late direct evidence relevant to the bound claim survives a constrained handoff budget.
- P25: an absolute claim rejected by verification cannot re-enter partial delivery through a
  paraphrase, while a qualified limitation is accepted.

## Remaining boundary

The new publication residue gate is deliberately narrow and deterministic. It detects absolute
claims tied to a failed factual publication check; it does not claim general semantic equivalence
checking. Protocol success verifies the repaired seams, not the quality of every future model
answer. A fresh Web run on a new topic remains the next semantic validation step.
