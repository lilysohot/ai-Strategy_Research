## 为什么停在构建，哪些属于执行错误

| 环节 | 本批证据/实现行为 | 补救规则 |
|---|---|---|
| 去重 | 只减上一批 62 个哈希，151 个旧来源和 2 个已覆盖原件再次进入流程 | OCR/准入前完成全量发布与父子来源核对 |
| 准入 | `admit.json` 为 `ok=false`，含不支持 PNG；后来 `admit-readable.json` 才成功 | 输出有效且 `ok=true` 才能称准入成功；失败后查实际状态，不假定原子回滚 |
| 预检 | `reader-precheck.json` 的 167 个 AttributeError 来自调用方读取不存在的 `ReaderResult.text`；另 61 个为 OCR RuntimeError | 用 CLI plan；调用方统计错误不算材料读取失败。167 份可构建由后续 build 成功另行证实 |
| 批量检查 | `check-results.json` 有 167 条 `build 不存在: `，传入参数为空 | 先验证非空 build 与单份输出身份，记录退出码，不吞错继续 |
| 缺口处置 | 后续仅有效检查过一份，发现 `image_only_page` 就结束任务 | 不外推为 167 份都不可发布；有保留正文且满足凭证条件时按既有授权继续 text-publication |
| 发布与激活 | 本批未留存 publish/scope/pack/Web 验收证据，配置仍指向旧包 | 逐份发布结果进入 published-manifest；完成新包与运行态验证后才报告 Web 生效 |

这些问题主要是执行偏离已有规程。旧文档虽已要求去重、检查退出码和最后激活，
但仍缺少明确的逐份分流、进度账、异常续办和交付条件；尤其 scope 示例直接使用
全批 manifest，遇到部分阻断时无法继续。此次修订补上这些环节，不增加绕过发布门的方式。

另外，`plugins/corpus/cli.py` 的 `_precheck_entry` 未捕获 OCR `RuntimeError`，
整批 plan 可直接中断；原生 reader 的 `ReaderResult` 没有 `.text` 属性。
本次只记明能力边界，以单来源 CLI 调用隔离异常，没有修改运行代码。

## 本批补救顺序

1. 保存恢复前快照：配置与运行态索引、活动来源/build/generation、备份结果及当前
   Web 健康/活动任务状态。不能把现在的快照追记为上次执行前的备份。
2. 以原始 232 个候选为审计母表，记录上述分类。把 151 个旧来源和 2 个已覆盖原件
   从待发布清单排除；不重建、不替换它们当前活动版本。历史构建与失败输出保留。
3. 从原 `build-readable.json.outcomes` 中按下表 source_id 取完整 build_id，
   创建单来源恢复记录。先跑一份 `status → check`，确认参数和 JSON 身份正确，再
   逐份处理其他来源。旧的 167 次空参数输出不能作为检查完成凭证。
4. 检查直接通过则 publish；若仅有凭证允许的已定位 PDF 图像/表格缺口且保留正文，
   按既有用户授权导出、填三项授权字段、登记 text-publication，然后
   `check → publish → status`。无正文、未知缺口、DOCX 未识别元素等保留阻断，
   不修改 gap_keys 或伪签完整性审核。新的恢复尝试使用新输出文件，不覆盖旧记录。
5. 将确认活动发布成功的来源写入 `published-manifest.json`，从当前实际允许包扩展
   scope；生成缺失上下文说明与向量，检查失败/不确定项，再打包、验证旧内容和新来源。
6. 在无活动任务的窗口切换 Web；验证实际运行配置、认证 search/fetch、新来源覆盖
   与旧句柄。失败则回退索引配置并保留正式库已发布成果，继续查因。
7. 61 份 OCR 失败、4 份 PNG 及步骤 4 的新阻断逐份留待办。它们不妨碍步骤 5/6
   发布已通过的材料；修复成功后作为后续增量走相同流程，不能将“部分上线”写成“全部完成”。
