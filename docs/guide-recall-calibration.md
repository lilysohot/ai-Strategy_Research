## 0. 如果只记三句话

1. **「召回」比「精确」更优先**：对 Agent 来说，**找不到 = 后面全错**；多找几条无关的结果，Agent 还有机会自己筛掉。
2. **换数据库 = 换了一套打分规则**：同样的数据、同样的查询，排序算法一变，结果顺序就全变了。**不能想当然认为"迁过去应该一样"**。
3. **检索是按「块」打分，但答案是按「文档」判的**：这个错配会引发一系列反直觉的 bug（本文 §5.4 的坑最典型）。

## 1. 先建立直觉：什么是「召回」

### 1.1 一个比喻：你和一个助理

想象你有一个档案柜，里面是 17 份研报。你让助理去找资料。

你说的是一句**自然语言**（人话）：

> "James Bulltard 买入 MDB 每周到期看涨价差的成本是多少美元？"

助理有两种极端做法：

| 做法 | 规则 | 结果 |
|---|---|---|
| **过于严格** | 必须找到**同一页**上同时出现"James""Bulltard""MDB""每周""到期""看涨""价差""成本""美元"**全部**这些词 | 一页都找不到 → **交白卷** |
| **过于宽松** | 只要出现**任意一个**词就算命中 | 交上来几十份，大半是无关的（提到"美元"的报告都来了） |

真实情况是：助理**先严格试**，找不到再放宽；然后对结果**打分排序**，把最可能的那几份放前面，交给你前 5 份。

### 1.2 Recall@5 到底是什么

- **Recall（召回率）**＝「你要的东西，**有没有**出现在助理交上来的清单里」。
- **@5**＝助理只交前 5 条。
- **Recall@5 = 100%**＝20 道题里，每道题的正确文档都进了前 5。

> ⚠️ 注意它**不要求排第一**。
> 只要正确文档进了前 5，就算「召回成功」。
> 这是刻意的：Agent 的真实用法是「搜一次、看前几条、再取原文」，
> 只要进了候选集就有机会被抓到。卡死在"必须第一"会低估系统可用性。

### 1.3 为什么我们更在意「召回」而不是「精确」

我们的场景是**投研 Agent**：

```
用户提问 → Agent 检索语料 → 取原文 → 引用数字 → 产出策略卡
              ↑
        这一步挂了，后面全错
```

- **漏召（找错/找不到）**：Agent 会基于错误信息编数字 → **硬闸①直接判死，整卡作废**。
- **多召（多几条无关）**：Agent 读一下发现不相关，自己筛掉 → **只是多花一点 token**。

⇒ 所以设计上宁可"多带几条噪音"，也不要"漏掉正确的那条"。
后面 §5.1 的「AND → OR 兜底」就是这条原则的直接体现。

## 2. 幕后原理（小白也能懂版）

### 2.1 分词：把一句话切成「词元」

计算机不理解句子，它先把文字切成**词元（token / lexeme）**。

- 英文按空格切：`James Bulltard` → `James` + `Bulltard`
- 中文**没有空格**，需要**分词器**：`全球流动性最新估算` → `全球` `流动性` `最新` `估算`

我们的数据库用 **zhparser**（基于 SCWS）做中文分词，配置名叫 `zhcfg`。

**数字的处理很关键**（这是 P0 阶段花大力气解决的点）：

```sql
SELECT to_tsvector('zhcfg', '194.9万亿美元');
-- 结果： '194.9':1 '万亿':2 '美元':3      ← 小数 194.9 保持完整，没被切成 194 和 9
```

如果分词器把 `194.9` 切成 `194` 和 `9`，那搜"194.9 万亿"就会匹配到一堆别的数字——**数字检索就废了**。

### 2.2 倒排索引：从「词」反查「文档」

数据库会建一张**倒排表**（想象成书后面的索引页）：

| 词元 | 出现在哪些块 |
|---|---|
| `茅台` | 块A、块C、块F … |
| `评级` | 块A、块B、块D … |
| `MDB` | 块K（**只有一处**） |

有了它，查询就不用逐篇扫描，直接查表即可。

### 2.3 查询：AND 还是 OR？

把你的问句也切成词元，然后决定**怎么组合**：

| 组合方式 | 含义 | 特点 |
|---|---|---|
| **AND（与）** | 命中的文档**必须包含全部**词元 | 精准，但**容易一无所获** |
| **OR（或）** | 命中**任意一个**词元即可 | 宽松，但**噪音多** |

PostgreSQL 里：

- `plainto_tsquery('zhcfg', '你的问句')` → 生成 **AND** 组合
- 我们手写的 OR 版本：`'词1' | '词2' | '词3'` → **OR** 组合

### 2.4 打分排序：谁排第一？

命中只是一半工作，还要**排序**。PG 提供两个打分函数，它们的思路**完全不同**：

| 函数 | 打分思路 | 直觉理解 |
|---|---|---|
| `ts_rank` | **词频 + 权重**：词出现越多、越"重要"（如在标题里），分越高 | "这份文档反复提到我要的词" |
| `ts_rank_cd` | **覆盖密度（cover density）**：词元**挨得越近**，分越高 | "我要的这几个词在这份文档里挤在一起" |

⚠️ **两者都不是 BM25**（MySQL/Elasticsearch/Lucene 常用的经典算法），
只是 `ts_rank` 的**思路更接近** BM25。这就是本次事故的核心背景之一。

**标题加权**：标题里的词比正文里的词更重要。SQLite 那套用 `bm25(fts, 0, 0, 5.0, 1.0)`——
意思是**标题权重 5.0、正文权重 1.0**。PG 里我们用 `ts_rank(标题) * 5 + ts_rank(正文)` 来模拟。

## 3. 事故：换个数据库，Recall 从 100% 掉到 0%

### 3.1 发生了什么

语料从 SQLite 迁到 PostgreSQL 后，跑黄金集测试：

```
Recall@5 = 0%   ← 20 道题，一道都没召回
```

**数据没丢**（17 份 / 298 块都在），**中文分词也在工作**，但搜索就是找不到。

### 3.2 怎么定位的

关键动作：**不要猜，把中间结果打出来看**。

```python
for q in GOLDEN_SET:
    hits = svc.search(q.question, limit=10)
    print(q.qid, q.question)
    for h in hits[:6]:
        print(f"  {h.score:.4f}  {h.doc_id[:22]}  {h.title[:34]}")
```

打出来就发现：**`hits` 是空的**（不是排序靠后，是根本没命中）。

由此锁定方向：**不是排序问题，是查询根本没匹配上** → 直奔 §5.1。

> 💡 **诊断心法**：先分清是「**没召回**」（结果为空或正确文档不在列表里）
> 还是「**排错序**」（正确文档在列表里，但名次靠后）。
> 这两种病的药完全不同。

## 4. 五步修复总览

| 步 | 措施 | 解决的是什么问题 | Recall@5 |
|---|---|---|---|
| 0 | ——（纯 AND） | —— | **0%** |
| 1 | **AND → OR 兜底** | 长问句纯 AND 必然零命中 | 70% |
| 2 | **标题显式 5× 加权** | 正文里的常见词把无关文档顶上来 | 80% |
| 3 | **改用 `ts_rank`**（词频）而非 `ts_rank_cd`（覆盖密度） | 稀有词（MDB/EXE）拉不开同系列文档 | 85% |
| 4 | **按 `doc_id` 去重** | 一份多块的长文档霸占整个前排 | 95% |
| 5 | **时效查询 Recency 偏置** | 「最新一期」没有关键词信号 | **100%** |

## 5. 五步详解

### 5.1 第一步：AND → OR 兜底（0% → 70%）

**现象**：所有查询返回空。

**人话解释**：
回到 §1.1 的比喻——助理用了"过于严格"那条规则。
我们的黄金题都是**自然语言长问句**：

> "James Bulltard 买入 MDB 每周到期看涨价差的成本是多少美元"

切成词元后有 9 个：`James` `Bulltard` `买入` `MDB` `每周` `到期` `看涨` `价差` `成本` `美元`。
要求**同一块（同一页）同时包含全部 9 个词**——几乎不可能。

**技术上**：`plainto_tsquery` 生成的是 AND：

```
'james' & 'bulltard' & '买入' & 'mdb' & '每周' & '到期' & '看涨' & '价差' & '成本' & '美元'
```

**怎么修的**：AND 查不到时，**自动退回 OR**（把 `&` 换成 `|`）：

```python
# 先按 AND 查
rows = cur.execute(SELECT.format(tsquery="plainto_tsquery('zhcfg', %(q)s)"), ...)

if not rows:                      # AND 空结果才兜底
    and_text = cur.execute("SELECT plainto_tsquery('zhcfg', %(q)s)::text AS tsv", ...)
    or_ts = and_text.replace(" & ", " | ")     # 'a' & 'b'  →  'a' | 'b'
    rows = cur.execute(SELECT.format(tsquery="to_tsquery('zhcfg', %(or_ts)s)"), ...)
```

**为什么叫"兜底"而不是"直接用 OR"**：
AND 精准、噪音少，**能用就用**；只有 AND 确实找不到时才放宽。
这样既保住了正常查询的质量，又不会"交白卷"。

**效果**：0% → **70%**（20 题里 14 题召回）。

---

### 5.2 第二步：标题显式加权（70% → 80%）

**现象**：能召回了，但正确文档**排在后面**，被无关文档挤出去。

**真实案例**（题 N4，找 `James-Bulltard_83126 复盘`）：

```
  18.0   油价突破与战争溢价_小红书文案     ← 无关，却排第一
  16.8   国信证券_贵州茅台…               ← 无关
  13.6   James-Bulltard_9226              ← 同系列，但不是要的那期
  13.2   James-Bulltard_9126
  13.2   华创证券_贵州茅台…
  12.0   James-Bulltard_83126 复盘        ← ✅ 正确答案，却排第 6，掉出前 5
```

**人话解释**：
"小红书文案"那份文档为什么排第一？因为查询里有 `美元` 这个词，
而那份文档的正文里 `美元` 出现得很多 → 得分高。

但 `美元` 是个**烂大街的词**，它不该有那么大的话语权；
真正的特征词是 `James` `Bulltard` `MDB`，而这些**恰恰出现在标题里**。

⇒ **让标题里的匹配比正文里的匹配更值钱。**

**技术上**：原来用 `setweight(title,'A') || setweight(body,'B')` 合并后打分，
但 PG 的默认权重（A=1.0，B=0.4）**只有 2.5 倍差距**，压不住正文里高频词的累积。
改为**显式相乘**：

```sql
-- 修复前：合并后打分，标题只占 2.5 倍
ts_rank_cd(setweight(d.title_tsv,'A') || setweight(b.tsv,'B'), q) AS score

-- 修复后：标题与正文分开打分，标题 ×5
(ts_rank(d.title_tsv, q) * 5 + ts_rank(b.tsv, q)) AS score
```

这与 SQLite 那套 `bm25(fts, 0, 0, 5.0, 1.0)`（标题 5.0 / 正文 1.0）**对齐**。

**效果**：70% → **80%**。

---

### 5.3 第三步：`ts_rank` 换掉 `ts_rank_cd`（80% → 85%）

**现象**：同系列的多份文档（James Bulltard 有 4 期：83126 / 9126 / 9226 / 9326）
**互相分不开**——正确那一期被兄弟文档压住。

**真实案例**：

- 题 N4 要 `83126`（这期讲 **MDB**）
- 题 N5 要 `9226`（这期讲 **EXE**）

`MDB`、`EXE` 是**极其稀有**的词——全库可能只在那一期出现。
按常理，搜 `MDB` 就该精准命中 83126。但结果不是。

**人话解释**：

- `ts_rank_cd` 衡量的是「**我要的词在这份文档里挨得多近**」。
- 它**不看**这个词有多稀有。`MDB` 和 `美元` 在它眼里**地位差不多**。
- 于是兄弟文档靠"美元、每周、成本"这些**常见词**凑密度，分数反而更高。

> 类比：考试时，`ts_rank_cd` 只数你答对了几道题；
> 而 `ts_rank` 会给"最后那道难题"更高分值——**难题才是区分度所在**。

**技术上**：

| | `ts_rank_cd`（覆盖密度） | `ts_rank`（词频 + 权重） |
|---|---|---|
| 关注点 | 词元**位置**是否接近 | 词出现**次数**与**权重** |
| 稀有词 | ❌ 不加权 | ✅ 天然被词频/权重放大 |
| 更接近 | —— | BM25 的思路 |

改为 `ts_rank` 后，`MDB` / `EXE` 这类稀有词终于能拉开差距。

**效果**：80% → **85%**。

---

### 5.4 第四步：按文档去重（85% → 95%）—— 最反直觉的一个坑

**现象**：某些查询的前 10 条结果，**全是同一份文档**。

**真实案例**（题 N5，找 `James-Bulltard_9226`）：

```
  0.1043   市场研判：油价突破与战争溢价下的新信号   ← 第 1 名
  0.1043   市场研判：油价突破与战争溢价下的新信号   ← 第 2 名（同一份！）
  0.1043   市场研判：油价突破与战争溢价下的新信号   ← 第 3 名
  ...                                              ← 前 10 名全是它
```

**根本原因（重要）**：

> **检索是在「块」级别打分，但答案是按「文档」判的。**

我们入库时会把每份文档切成很多**块**（PDF 按页、DOCX/MD 按段落）。
一份 20 页的 PDF → 20 个块。

- 数据库返回的是「**块**」：一份文档有 20 个块，它可能占 20 个名额。
- 但我们要的是「**文档**」：一份文档只该占 1 个名额。

⇒ 一份块多的长文档，只要**松散命中**了 OR 查询，就能用它的 N 个块**霸占整个前排**，
把真正相关的其他文档**彻底挤出候选集**。

**另一种受害姿势**（题 C1，需要同时召回「华创」和「国信」两份）：

```
1-5 名：全是《华创证券_贵州茅台》的 5 个块
8-10名：《国信证券_贵州茅台》            ← 被挤到第 8，掉出前 5
```

这题要求**两份都进前 5**，结果华创一家独占了 5 个名额 → 判失败。

**怎么修的**：取回候选后，**按 `doc_id` 分组，每份文档只留分最高的那一块**，再取前 N 份文档：

```python
candidate_limit = max(50, limit * 10)   # 先多取一些候选（去重后数量会变少）

# 同一文档多个块都命中时，只保留分最高的那一块
best_per_doc = {}
for r in rows:
    prev = best_per_doc.get(r["doc_id"])
    if prev is None or (r["score"] or 0.0) > (prev["score"] or 0.0):
        best_per_doc[r["doc_id"]] = r

ranked = sorted(best_per_doc.values(),
                key=lambda r: r["score"] or 0.0,
                reverse=True)[:limit]
```

> 💡 **为什么 SQL 的 `LIMIT` 要放大到 10 倍？**
> 因为去重是在 Python 里做的。如果 SQL 只取 5 条，而这 5 条恰好都属于同一份文档，
> 去重后就只剩 1 份——其他文档连被考虑的机会都没有。
> **先多捞、再去重、最后截断**，顺序不能反。

**效果**：85% → **95%**。
（顺带改善了工具输出：Agent 不再看到同一份文档被刷 5 遍。）

### 5.5 第五步：时效查询的 Recency 偏置（95% → 100%）

**现象**：只剩 1 道题（T1）失败：

> 题 T1：「James Bulltard **最新一期**的复盘是哪一期？」
> 正确答案：`James-Bulltard_9326`（2026-09-03，四期里**最新**的一期）

**人话解释**：
这道题**没有任何能区分答案的关键词**。
四期文档的标题都长一样：`James-Bulltard_XXXX 复盘`。
"最新"是个**时间概念**，而全文检索**只认识词，不认识时间**。

⇒ 纯靠词频排序，四期得分几乎一样，谁排前面全看运气。

**技术上**：给「**看起来在问时效**」的查询加一点**日期偏置**——
只在这类查询上生效，避免污染其他题目。

```python
_RECENCY_WORDS = ("最新", "近期", "最近", "本期", "新一期", "最近一篇", "上一期")

if any(w in q for w in _RECENCY_WORDS) and rows:
    pubs = [r["published"] for r in rows if r.get("published")]
    lo, hi = min(pubs), max(pubs)
    span = (hi - lo).days or 1
    for r in rows:
        if r["published"] is not None:
            # 越新的文档加分越多；最大加 0.1（与 ts_rank 分值同量级，只做"打破平局"）
            r["score"] += 0.1 * ((r["published"] - lo).days / span)
```

**两个设计细节**：

1. **只认关键词才触发**：查询里有「最新/近期/最近」才加偏置。
   否则所有查询都会被推向新文档——那些问历史报告的数字题就全错了。
2. **权重刻意小（0.1）**：它的作用是**打破平局**，不是**主导排序**。
   0.1 与 `ts_rank` 的分值（约 0.05~0.2）同量级，够翻转同分文档，不足以推翻相关性。

**效果**：95% → **100%**（20/20）。

## 7. 可复用的心法（6 条）

1. **「没召回」和「排错序」是两种病，药不同。**
   先把中间结果打出来看，再动手。空结果 → 查查询构造；结果里有但靠后 → 查排序。

2. **换存储 = 换打分规则，必须重新校准。**
   BM25、`ts_rank`、`ts_rank_cd` 是**三种不同算法**，不是换个名字。
   迁移方案里如果写着"排序应该差不多"，那基本就是要出问题。

3. **标题匹配要显式加权。**
   默认权重几乎总是"压不住"正文里的高频常见词。
   别指望 `setweight` 的默认值能等价于你原来那套的 5×。

4. **警惕「按块打分、按文档判答案」。**
   只要你的检索单元比答案单元更细（块 < 文档），
   就一定要**去重**，否则长文档会吃掉全部名额。这是本次最反直觉的坑。

5. **先多捞、再后处理、最后截断。**
   任何"取回后再加工"的逻辑（去重、重排、偏置），
   SQL 侧的 `LIMIT` 都要**放大**，否则加工前就已经把候选切没了。

6. **给特殊查询加偏置时，务必限定触发条件、且权重压到"只够打破平局"。**
   无差别加偏置会污染其他查询；权重过大会让偏置压过真实相关性。

## 9. 术语表

| 术语 | 人话解释 |
|---|---|
| **Recall（召回率）** | 正确答案有没有出现在结果列表里 |
| **Recall@5** | 只看前 5 条结果时的召回率 |
| **词元 / token / lexeme** | 分词器切出来的最小单位（`茅台`、`194.9`） |
| **分词器** | 把连续文字切成词元的程序（我们用 zhparser / SCWS） |
| **tsvector** | 一份文本被切成词元后的"数据库表示形式" |
| **tsquery** | 一个查询被切成词元后的表示形式（含 AND / OR 关系） |
| **倒排索引** | 「由词反查文档」的索引结构，全文检索的地基 |
| **`plainto_tsquery`** | 把自然语言问句转成查询（**默认 AND**） |
| **`ts_rank`** | 打分函数：**词频 + 权重**（更接近 BM25） |
| **`ts_rank_cd`** | 打分函数：**覆盖密度**（词挨得越近分越高，**不看稀有度**） |
| **BM25** | 经典的检索打分算法（Elasticsearch / Lucene 用），PG 原生**没有** |
| **`setweight`** | 给字段打权重标签（A/B/C/D，默认权重 1.0/0.4/0.2/0.1） |
| **块（block）** | 文档被切分后的片段（PDF 按页、DOCX/MD 按段落）——**检索的最小单位** |
| **定位符（locator）** | 块的"门牌号"（PDF 是页码，DOCX/MD 是标题/段落），取证用 |
| **黄金集** | 人工标注的 20 道测试题，用来衡量检索好坏的标尺 |
| **硬闸①** | 「数字可溯源」校验：引文必须能在原文中逐字找到 |
| **去重（dedup）** | 同一文档的多个命中块只保留一个，避免霸占名额 |
| **Recency 偏置** | 按发布时间给新文档加分，用于「最新一期」类查询 |

## 10. 一句话总结

> **召回不是"搜到了就行"，而是"在正确的候选集里、按正确的顺序搜到"。**
> 本次 0% → 100% 的修复，本质上是在补齐四件事：
> **① 查不到会兜底；② 标题比正文值钱；③ 稀有词比常见词值钱；④ 一份文档只占一个名额；**
> 再外加一个「时效题额外看日期」的特例。
