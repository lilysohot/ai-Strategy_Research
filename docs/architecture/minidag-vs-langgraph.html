01 / WHERE ORCHESTRATION LIVES

外层推进阶段，还是图层管理分支？

CURRENT IMPLEMENTATION

MiniDAG：一个当前节点，一次选择

运行器维护 current_node，等待节点执行完，合并返回的状态增量，再选出唯一的下一节点。节点内部可以很复杂，甚至包含整个 Agent 团队。[1]

LANGGRAPH GRAPH API

LangGraph：一组活跃节点，一轮推进

编译后的图由 Pregel 运行时驱动。每个 super-step（超级步）选定活跃节点并执行，再统一更新状态通道；同轮的节点可以并行。[7]

MiniDAG 阶段 / 内部协调LangGraph 图节点等待与恢复边界
别被 DAG 这个名字误导。

当前 MiniDAG.validate() 检查入口、引用、可达性等，但没有检查环。运行器可以沿回边继续执行，并以 _MAX_STEPS = 100 限制步数。因此这里更准确的描述是“轻量、单路径的状态图执行器”，不能简单说成“MiniDAG 无环，LangGraph 有环”。[1]

项目里另一个真实图：Stateful ReAct

输入→react_agent→END

看起来只有一站，却可以在这一站内部多次“调用模型 → 执行工具 → 观察结果”。外层图的节点数，不等于模型轮数，也不等于任务复杂度。LangGraph 同样可以把完整 Agent 循环装进一个节点；右图只是展示其图层拆分能力。[3]

03 / CAPABILITY BOUNDARIES

相同的节点与边，不同的运行语义

比较维度项目 MiniDAGLangGraph Graph API
编排声明PipelineSpec 描述节点、角色、上下文策略和迁移；Builder 包装节点并编译。[2]StateGraph 声明状态、节点和边，编译为 Pregel 应用；也有共享运行时的 Functional API。[7][8]
并行与汇合运行器只有一个 current_node。多个无条件出边在 Builder 中只取第一条。团队并行由节点内 AgentBus 承担。[1][2]图层支持多分支、并行节点与汇合；Send 可为动态数量的任务传递不同输入。[7][8]
条件与循环路由函数返回一个键，选一个目标。支持沿回边执行；100 个节点步数上限是当前实现的固定兜底。[1]支持条件分支、循环与 Command 路由；执行有可配置的 super-step 递归上限。[8]
状态合并节点返回 delta；带 Annotated reducer 的字段归并，其他字段覆盖。reducer 抛出 TypeError / ValueError 时会警告并回退为覆盖。[1]状态字段同样可指定 reducer。并行分支写同一个默认单值字段需要处理冲突，不能把它理解成任意“最后写入者胜出”。[8][11]
上下文与压缩Builder 可按 ContextPolicy 过滤输入并截断字段；Agent 对话压缩另在 loop / 工作流中处理。[2]可设计节点输入输出 schema；对话裁剪和摘要仍需在应用中设计。图状态持久化本身不会自动解决模型上下文过长。[8][12]
检查点与恢复有 save / load_latest / load_history 接口，节点完成后可保存 state 与 next_node。当前运行入口显式传 None，没有启用该能力。[1][4]配置 checkpointer 后按 super-step 保存检查点，并记录任务级 pending writes。跨进程恢复需持久化后端；内存 saver 不够。[9][13]
人工参与apodex 的工具审批、steering、会话存档属于终端与 Agent loop 层，MiniDAG 内没有等价的 interrupt() 原语。[5]interrupt() 配合 checkpointer 暂停，Command(resume=...) 继续。恢复会重新进入所在节点，因此中断前的副作用需要幂等。[10]
可观测性MiniDAG 按节点完成输出 updates；模型 token、工具事件、团队活动由 observers / apodex trace 呈现。[1][5]提供多种流式投影及状态检查能力；拆进图里的步骤也更适合按图追踪。图形可见程度仍取决于节点粒度。[14]
展开：两种调度循环的最小心智模型

MiniDAG：顺序推进

# 语义示意，省略中间件和错误处理
node = entry_point
while node is not None:
    delta = await nodes[node](state)
    state = merge_with_reducers(state, delta)
    next_node = route(node, state)
    if checkpointer:
        await save(state, next_node)
    yield {node: delta}
    node = next_node

LangGraph：超级步推进

# 语义示意，不是 LangGraph 的源码
while active_nodes:
    # Plan：按上一轮通道更新确定活跃节点
    # Execute：运行本轮节点，可并行
    writes = execute(active_nodes, channels)
    # Update：归并本轮写入，下一轮才可见
    channels = apply_updates(channels, writes)
    checkpoint_if_configured()
    active_nodes = plan_next_step(channels)

节点可以继续封装自己的循环；图层没有展开的细节，不会因为使用 LangGraph 就自动获得细粒度恢复。

04 / WHAT CHANGES IN LONG TASKS

“长”有三种，优势也分三种

推理过程长

几十轮工具调用、检索、纠错。项目把这些交给成熟的 ReAct loop、压缩和 guardrails，MiniDAG 只管阶段交接。这种分工紧凑，也容易定制。

分支数量多

很多独立分支，且希望逐分支观察、重试、汇合。LangGraph 可将它们直接放进图，减少自行维护调度状态的工作；当前项目由 AgentBus 管理团队任务。

跨时间持续久

进程重启、等待隔天审批、从历史状态重放。LangGraph 的持久化检查点与中断原语更贴近这些需求；MiniDAG 当前入口仍需补齐持久化接线和恢复语义。

更细的节点，才有更细的恢复边界。

如果把两个小时的研究放在一个节点里，外层 MiniDAG 在该节点完成前不会保存它的节点后检查点。把同一整段代码直接塞进一个 LangGraph 节点，也不会自动让每次 LLM 调用都变成可恢复步骤。需要拆分节点，或正确使用其任务与持久化机制。[1][9]

项目当前选择的收益：让图层保持小，把 Agent 行为留在自己的框架中。

已有工作流的外层只有一个主节点，或主节点加可选 reporter。此时 MiniDAG 的实现范围与实际拓扑相匹配，模型调用、工具授权、团队通信和上下文管理都能继续独立演化。这是基于代码结构的工程判断，不是运行速度或成功率的实测结论。

需要承担的成本：复杂恢复和图级并行，要自己补。

如果需求变成“100 个分支各自保存进度、跨进程重试、人工审批后继续、历史状态分叉”，单一路由指针与可选保存钩子就不足以提供完整语义。届时引入 LangGraph，或系统扩展自研运行器，才有明确的收益。

采用 LangGraph 的成本：学习并遵守它的状态与恢复模型。

需要设计状态 schema、reducer、分支汇合、检查点后端，以及外部操作的幂等性。编排框架提供机制，工具权限、模型判断质量、证据核验和应用业务约束仍由应用负责。

四个容易误读的源码细节
  • “兼容接口”不是完整替代。MiniDAG 提供部分相似的方法名，但 checkpointer 使用自定义 save/load_latest 协议，不能直接假定 LangGraph saver 即插即用。
  • 会话恢复与图恢复分层。apodex 的 session.json 由终端层保存；项目当前 EventStore 即使文件名为 sqlite.py，实现仍是 no-op，不能当作持久化数据库。[5][6]
  • terminal_nodes 不会覆盖显式出边。Builder 只给没有出边的 terminal node 补结束边，所以 main_agent 虽列为 terminal，仍能按条件进入 reporter。[2][3]
  • 恢复钩子还需语义验收。当前 MiniDAG 若读到带 next_node 的检查点，会优先恢复它；即使调用方给了新 input_data 也如此。扩展持久化时，应明确“继续旧任务”和“开始新任务”的区别。[1]
