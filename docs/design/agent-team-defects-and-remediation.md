## 0. 执行摘要

本次最重要的缺陷是：**系统已经收到核验未完成的信号，但该信号没有约束最终报告的完成
状态和验证声明。** `final_verifier` 的报告明确标记 `incomplete / wall_deadline`，协调者仍将
核验任务标为 `resolved`，最终声称“已获充分交叉验证”；`summary.json` 同时给出
`answer_status=complete`、`team_completeness=complete`、`gaps=[]`。

问题应拆为三条独立因果链，不能全部归因于“单次 Run 有墙钟上限”：

1. **可信度约束缺失**：任务完成、证据覆盖、核验结论和交付状态没有形成可追溯的约束链。
   增加时间、换模型或允许续跑，都不能自动解决过度声明。
2. **规划与预算不匹配**：重复全文处理、核验启动晚、核验范围大，以及一次耗时重试，
   共同压缩了终审交付机会。需要保护核验预算、缩小任务和尽早形成中间核验结果。
3. **恢复能力有限**：已结束 job 有结果快照，但保存结果不等于恢复执行。跨进程续跑、
   安全接管和副作用幂等属于后续能力，不作为前两类修复的前置条件。

S1—S3 已有实现与聚焦回归，不能称总体方案“完全未实现”；S4/S5 基础验收及 S6 外部监管
仍有待办，也不能据此声称交付可靠性已超过行业水平。本次 Run 证明的是当前验收存在缺口。

修复原则：**失败时收缩声明，保留有用结果，准确披露未完成范围。** 不用全面拒答替代
诚实交付，也不以附加一句免责声明来容忍正文中的相反声明。

## 3. 修复方向与适用边界

### 3.1 R1：分离执行、核验和交付状态（D1/D16/D17/D18）

以下是建议契约，不是已经存在的接口或已确定的数据库字段。

| 维度 | 示例 | 判定依据 |
|---|---|---|
| 执行 | 运行中、结束、超时、失败、取消 | 实际 job 生命周期 |
| 工作项 | 摘要已完成、复核尚未完成 | 任务目标及关联结果；协调者可维护工作进度，但不能据此授予核验通过 |
| 核验 | 未核验、部分核验、范围内通过、发现错误/冲突、因能力或时间不足未完成 | 对应检查项、方法、证据引用、核验结果及版本 |
| 交付 | 完整交付、部分交付、系统状态报告 | 用户要求覆盖度、必要核验、产物及上下文提交状态 |

建议关系为：`工作项/结论 → 必要检查 → job → 证据版本/草稿版本 → 检查结果`。
“是否必要”按用户要求和任务策略确定，协调者不能在失败后静默撤销必要检查来获得完整状态。
用户调整范围或有依据的计划变更需要记录原因及影响；可选探索失败不必使整个 Run 永久降级。

具体约束：

1. 任务板 resolved、工具返回成功、job 结束或调用 submit_report，都不是事实核验通过的
   充分条件。协调者不能只凭 notes 把核验状态提升为通过。
2. 超时但已经提交的局部核验继续有效；没有产出对应检查结论的事项保持未核验/未完成。
   原始工具观测作为待解释证据保留，不能冒充完成的核验报告。
3. 后续补核验可以解决对应缺口，必须引用新 job、证据与版本，并保留旧失败记录。
   不能永久锁死在失败状态，也不能删除失败事实。
4. 最终完整度汇总整轮必要事项及其解决关系，不能只读取最后一批 wind-down 或任务板。
5. 检查结果绑定实际受检内容。草稿、计算输入或文件变化后，受影响的核验需要失效或重做；
   不相关修改不要求全部重验。文件生成、下载成功和内容正确分别判断。
6. 正式核验状态说明由受控字段生成。正文与状态冲突时进行有界修订；修订仍失败时，输出
   安全的状态说明及可明确归属的局部结果，不保留相反的成功声明。

示例：摘要已完成、数字检查 8/10 项通过、2 项因超时未核验、图片不可读。允许交付有限摘要，
同时列明覆盖范围；不得称“全文全部核验通过”，也不应抹掉已经完成的八项检查。

结构化核验记录证明的是执行与证据关系，不能保证模型判断本身正确。可计算事项优先使用
确定性检查；语义判断仍需要质量评测与人工抽样。

### 3.2 R2：按核验目标选择方法（D2）

| 核验目标 | 合适方法 | 不应扩大成的结论 |
|---|---|---|
| 摘要忠于原文 | 回到原始页码、段落和上下文检查 | 原报告中的现实事实已被证实 |
| 数字、单位与跨行排版 | 原 PDF 页面渲染、文字坐标、单位及上下文核对 | 仅多解析器一致即可保证无误 |
| 计算正确 | 固定输入、可重复计算、独立断言 | 脚本成功退出即公式与输入正确 |
| 外部事实成立 | 能支持具体结论的原始公告或其他适当来源 | 链接存在或搜索命中即完成核验 |
| 判断稳健性 | 寻找反例、矛盾、替代解释；可选择异模型审阅 | 换模型本身即构成事实证明 |

同模型复核和多解析器比对均有价值，但必须按范围表述，如“已做文本一致性检查”。
不强制所有任务换模型或外部联网；多个网站转载同一来源也不等于多个独立证据。

### 3.3 R3：记录引用取得方式及具体支持范围（D3）

至少区分三个维度：取得方式（正文、片段、搜索摘要、未取得）、来源性质及来源关系、
该证据对具体结论的支持情况。`fetched-full-text` 只表示取得了内容，不能直接等同 verified。

保存来源定位、实际取得片段及时间；按需保存内容版本/hash。PDF 优先引用页码/区域。
外部网页抓取失败时，不抹掉先前有效取得的证据，但必须保留失败和已有证据的范围。
搜索摘要可以作为有限线索，不能展示为已经读过正文或完成官方核实。
用户正文使用“原文称”“搜索摘要显示，正文未核实”等自然表述，无需堆叠内部枚举值。

### 3.4 R4：输入覆盖度与能力缺口（D4）

把图片案例推广为页面、段落、表格、图片、附件、截断及缺失区域的覆盖记录。
视觉/OCR 不可用时保留“图片未读取，可能遗漏图表信息”；像素统计只能辅助定位，不能
将未读区域自动标为无关。已确认不存在图片的文档不追加无依据的漏读警告。
能力失败后进行有限、可行的替代尝试，不反复调用已知不可用的安装或识别路径。

### 3.5 R5：为必要核验保护预算；R10 合并于本项（D5/D6/D11）

从总预算中先考虑最终交付和必要核验，再规划研究、发布及工具收尾；不同任务采用不同
分配，避免将每个任务都变成固定的“研究完再全文终审”。关键证据出现后即可并行核验，
最终审阅只处理定稿覆盖度、改动和未解决冲突。

允许核验拥有独立受限额度，或由程序在现有阶段内明确预留和调整；不能靠把 verifier
伪装为 publisher 获取时间或写权限。所有调整仍受 Run 硬墙、调用/工具超时和费用预算约束。
模型队列、重试和回收耗时也计入预算，不能只预留名义秒数。耗时参数需用真实样本验证，
不保证任何核验必定成功；预算不足则缩小覆盖范围并披露。

### 3.6 R6：按剩余资源限制核验范围（D7）

结合任务类型、检查项数量、输入规模、工具能力和实际模型延迟估算耗时；估计值不是硬性
真理。不足时拒绝无法兑现的全面核验承诺，改为关键数字/高风险事项检查，保留未覆盖清单。
临近截止时，重试决策应比较“继续采样”与“提交已完成核验”的价值，保护成员汇报机会。

### 3.7 R7：回收延迟调查，替代事件驱动重构（D8）

保留现有 FIRST_COMPLETED 路径。记录成员 loop 结束、结果适配、快照写入、结果入队、
等待唤醒和协调者获得结果的时刻，明确耗时属于模型、工具、保存还是回收。
只有证实异常延迟后再修对应环节；195 秒等待本身不构成调度缺陷，也不能通过频繁轮询
制造进展。需要展示最后有效活动与结果状态时，沿现有心跳/事件通道补齐。

### 3.8 R8：复用基础处理，保留有目的的独立核验（D9）

提取成员提供包含来源哈希、页码、提取方法、覆盖缺口及不可变 handoff ref 的基础材料。
下游先检查已有材料，再针对歧义或高风险位置回到原始 PDF，必要时重新提取或渲染。
不强制所有核验只读同一份提取文本，否则会共同继承上游错误。跨 Agent 文件继续走已有
只读 handoff，不共享整个私有 workspace；复用范围遵循当前研究和用户访问权限。

### 3.9 R9：分段续跑作为后续恢复能力（D10）

在现有结果快照基础上，按真实长任务需求补执行检查点、依赖队列、会话载体、权限恢复、
执行代次和迟到写入隔离。恢复先读取已保存结果；涉及副作用的工具需确认已执行状态或
幂等身份，不能为重建上下文盲目重放。

保留单段进程硬超时、整项任务累计费用/token/时间上限和用户停止机制。并发任务累计时间
与用户实际等待时间分别计量；休眠、排队和审批的计费/预算规则需明示。续跑不得变成
无限延长任务，也不作为本次可信度修复的前置条件。实施归入 S6 后续监管/恢复范围。

### 3.10 R11/R12：按用户目标规划团队与输出（D12/D13）

路由至少考虑摘要、事实核查、计算、研究建议等目标，以及风险、输入格式和能力。
7 页文档也可能有复杂图表，不能只按页数决定预算。先调整现有 Run 内策略，再决定是否
需要长时队列；长任务的时间/费用范围应符合用户授权。

对于“这份研报说了什么”，可采用一名内容分析员加一名重点核验员，按需扩展。输出先给
主线、关键依据和局限，再给必要数字及原文定位。对于用户要求全文逐项整理的任务，完整
覆盖优先。不得统一套用固定长度，也不强制加入用户未要求的投资判断。

### 3.11 R13：正确性评测从第一批开始（D14）

| 指标 | 可执行口径 |
|---|---|
| 无依据通过声明率 | 声称检查通过的事项中，没有对应有效核验记录的占比；注入失败场景要求为零 |
| 关键结论支持率 | 预先标注的关键结论中，被实际取得证据充分支持的占比 |
| 已知缺口披露率 | 影响交付的已知缺口中，在报告和结构化结果里准确保留的占比 |
| 数字/单位/日期错误率 | 对固定样本的预标注字段逐项比较，明确总字段数和错误类型 |
| 引用准确性与覆盖率 | 引用是否实际取得、是否支持相邻结论；需要引用的关键结论是否有依据 |
| 任务完成度与有用性 | 回答是否覆盖用户问题；同时统计不必要拒答和过度降级，防止靠拒答获得低错误率 |

固定样本需包括可正常完成的正例和注入失败的反例。机械一致性用确定性断言；语义支持与
摘要质量用有依据的评审规则并做人工抽样，不能只由同一模型自评分。财务材料只是一个
样本，还应覆盖表格对账、代码/计算、网页研究和图片缺失任务。

### 3.12 R14：补齐工具业务结果与覆盖度契约（D15）

区分工具传输/执行是否成功与任务内容是否取得；支持成功、部分成功、不可用、失败，以及
明确的策略拒绝。批量读取逐项保留状态，不因一个分项成功便宣称全批成功。
优先在工具产生结果处提供结构化信息，避免持续扩展字符串关键词猜测。

正文提取为空、vision 不可用、策略阻止等情况必须传到成员报告、完整度、实时事件和回放。
兼容旧轨迹时仅修正读取投影，保留原始审计内容；共享工具改动须验证单 Agent。

## 5. 最低验收矩阵

| 场景 | 必须观察到的结果 |
|---|---|
| 本次 Run：终审超时后协调者写 resolved | 必要核验仍未完成；不能输出“充分验证”；最终缺口不为空 |
| 不完整报告已经提前收回，收尾计数全零 | 全 Run 的未解决必要缺口仍保留，不被最后一批统计覆盖 |
| 部分检查通过后核验员超时 | 已通过范围保留，未检查项明确；既不全盘否定，也不升级为全部通过 |
| 替代 job 补验成功 | 对应缺口可关闭，保留旧失败及替代关系 |
| 可选探索失败，必要工作已完成 | 不无条件降低整轮状态；不得把失败后静默撤销必要检查当成可选探索 |
| 修改已核验草稿或数据 | 受影响核验不再覆盖新版本，无关部分可保留 |
| 搜索摘要可得、正文抓取失败 | 摘要仅作有限证据，不声称取得正文或完成官方核实 |
| 图片/表格/附件未读或部分读取 | 覆盖缺口贯通工具、报告、页面与后续上下文；不以推断消除 |
| 正文与程序核验状态矛盾 | 有界修订或降级，不能只加前缀后保留相反声明 |
| 正常核验与正常交付 | 保留准确结果与有效通过状态，不能把所有任务统一降级或拒答 |
| 成员结束但回收迟滞 | 能定位适配、落盘、入队、通知耗时；不把模型执行时间重复算作调度浪费 |
| 发布/上下文保存失败 | 不确认完整提交，不让下一轮静默继承过期状态；按 S4 范围处理 |
| 单 Agent 与跨模式回归 | 共享工具错误契约一致；原有上下文细节可读，新增核验限制不在模式切换中丢失 |

脚本模型用于确定性故障与状态转换；真实模型用于规划、证据理解和自然语言声明质量。
两者分别记录，不以其中一项替代另一项。第一阶段不宣称覆盖跨进程接管和全部崩溃窗口。

## 6. 本次运行时间线与因果边界

相对时间以主 Agent 轨迹 start 为起点，约数存在工具执行、日志及最终汇总计时差异。
780.8 秒是本次实际运行时长，不是新的配置上限。

| 相对时间 | 事件 | 可以支持的判断 |
|---|---|---|
| 第 0 秒 | 主 Agent 启动 | 建立本轮阶段时钟 |
| 第 43 秒 | 两个提取成员并发派发 | 初始研究确实并发 |
| 第 372、436 秒 | 协调者分别回收两份报告 | 已有材料可用于逐步核验；不能据回收时刻推断成员精确结束时间 |
| 第 521 秒 | 终审任务派发 | 距 720 秒研究截止仅约 198 秒 |
| 第 551—690 秒 | 终审第 9 轮模型调用及重试 | 首次出现约 46.3 秒无可见进展的 watchdog 中止；重采样约 88 秒后返回工具调用，整段不宜全部称为无产出空转 |
| 第 702 秒 | 终审 loop 以 wall_deadline 结束 | 未产出最终核验结论，保留工具观测；loop 结束不等于 job 已完成保存并可回收 |
| 第 719 秒 | 主 Agent 的 195 秒等待返回超时 | 与终审执行重叠；仅凭此无法证明等待机制浪费了 195 秒 |
| 第 723 秒 | 非阻塞调用取得终审不完整报告 | 本次 0 秒调用有有效结果，并非空转 |
| 第 742 秒 | t3 被改成 resolved | 主 Agent 将不完整证据解释为核验通过 |
| 约第 780 秒 | 最终回答与汇总 | 自然语言声明“充分交叉验证”，结构化结果 complete、gaps 为空 |

已确认的核心链路是“启动晚、重复处理、重试占用 → 核验未完成 → 协调者错误升级 → 最终
边界未阻止”。前半段需要效率与预算修复，后半段需要可信度约束；二者独立验收。
不能由一次运行证明 198 秒必然无法完成该任务，也不能将当前结果保存能力描述为完全不存在。
