## 1. 目标与已有约束

Super-link 采用服务端主导的运行方式：客户端发起研究、审批、暂停、停止、恢复等操作，
服务端管理执行并通过 SSE 推送状态和可展示的运行内容。客户端可以随时离开或重新连接，
不成为协作执行链路的必要参与者。

本轮建议借鉴资源状态同步、订单通知、交易所行情和持久工作流的设计方法，结合现有
PostgreSQL、Redis 与 Run 事件能力建设独立的空间事件适配层。无需因此引入 Kubernetes、
Temporal 或另一套大型编排框架。

以下边界继续成立：

- Team 与 Single 共享研究目标和对象，各自维护业务状态、会话和记忆；空间视图只汇总
  状态，不建立双方共同使用的研究状态机。
- 编排层管理通信和顺序执行，旁路检查目标、证据与可执行条件；SSE 不承担这两项职责。
- 正式交付仍遵守真实运行收尾及交付检查，不能以文本输出结束或 SSE 结束代替可靠交接。
- 普通 Single、Team 和现有监控模式保留原有能力与行为；Super-link 单独适配。
- 关闭页面不取消已接受的研究与交付任务。监控是否允许离线运行仍遵循原有规则，不能
  由 SSE 的连接独立性推导出离线监控已经实现。
- 实时展示仅使用模型接口提供的可展示内容；不假定所有模型均提供思考流。

本次只登记设计，不表示 Super-link 空间级 SSE 已实现、完成验收或部署。

## 2. 跨领域参考与项目映射

### 2.1 Kubernetes 资源同步

Kubernetes 支持先读取资源快照及其版本，再订阅对应版本之后的变化。历史版本过期时，
客户端重新读取快照并建立订阅。[官方 API 概念](https://kubernetes.io/docs/reference/using-api/api-concepts/#efficient-detection-of-changes)

建议将这一方法映射到 Super-link：

1. 打开空间时获取 Team、Single、交付、旁路、审批与队列的当前视图。
2. 快照携带与其内容一致的事件游标，从该位置继续接收后续事件。
3. 断线后按游标补读并去重；超过保留窗口时明确要求重新同步。
4. 前端区分“连接中断”“正在同步”和实际业务状态，不能把断线显示为执行失败。

典型场景：用户离开数小时后重新进入，直接看到当前研究和交付进度，无需从第一条
模型输出开始播放。快照与游标必须具有一致性保证，不能分开读取后简单拼装，否则仍会
漏掉读取快照与建立订阅之间的变化。

### 2.2 订单与支付系统的可靠通知

Transactional Outbox 模式把业务状态和待发布事件放入同一数据库事务，再由独立流程
发布通知。它解决数据库写入成功但消息发送失败等双写问题；通知仍可能重复，消费方需
幂等处理。[AWS 模式说明](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

建议对审批结果、正式交付、运行终态等关键事实采用这一原则。Redis 用于及时通知，
持久化记录用于补读和核对；Redis 暂时不可用不能使已提交的事实永久不可见。

| 阶段 | 含义 | 客户端应表达的内容 |
|---|---|---|
| 命令已接受 | 服务端记录了操作意图 | 请求已提交或等待执行 |
| 操作已生效 | 执行端满足实际完成条件 | 已暂停、已停止等真实状态 |
| 页面已收到 | 某个客户端获知变化 | 更新当前显示，不反向决定业务是否完成 |

典型场景：停止请求已被接受，但 HTTP 响应丢失。客户端使用同一幂等键重试，取得原请求
结果，随后接收实际停止事件。不能重复发起停止流程，也不能把收到请求直接显示为已停止。

展示通知与工作派发应分开设计：工作队列的领取、确认语义不等于向多个 SSE 客户端广播。
是否复用现有 outbox 的代码或表结构，需要后续核对；本节只确定可靠通知原则。

### 2.3 交易所行情的快照与增量衔接

Coinbase 的完整行情频道采用先订阅并缓存增量、再读取快照、按序号过滤快照已包含的
消息、最后继续应用增量的流程。这提供了另一种避免快照与订阅之间出现空隙的方法。
[官方同步流程](https://docs.cdp.coinbase.com/exchange/websocket-feed/channels#full-channel)

借鉴的是状态同步方法，不要求 Super-link 改用行情系统的 WebSocket 协议。后续应在
“一致快照后按游标补读”和“先订阅缓存再对齐快照”之间选择可验证的实现方式。

Super-link 的事件还应根据用途区分可靠性要求：

| 类别 | 示例 | 建议策略 |
|---|---|---|
| 业务事实 | 审批结果、交付检查结果、运行终态、实际停止 | 持久化、去重、可补读；不能因展示拥塞永久丢失 |
| 实时展示 | 可见思考片段、文本增量、工具进度 | 有界缓冲、合并推送；缺片后由文本快照或归档恢复 |

文本增量存在缺口时，不能静默跳过后继续拼接。应补齐缺片或替换为完整文本，避免页面
展示残缺结论。最终文本和产物以已保存内容为准，不要求每个 token 都独立写入业务事件表。

典型场景：多个 Team 成员同时输出，浏览器处理不及。展示层合并片段并限制缓冲，
审批和停止事件仍可及时处理；慢客户端不阻塞模型运行，也不能造成无限内存堆积。

### 2.4 Temporal 的长任务生命周期

Temporal 使用持久化事件历史记录工作流过程，并区分请求动作的 Command 与记录事实的
Event，支持执行状态恢复。[官方事件历史说明](https://docs.temporal.io/encyclopedia/event-history)

对 Super-link 的借鉴是职责分离：执行器推进任务，持久化记录说明已发生的事实，SSE
让客户端观察这些事实。浏览器重连只恢复显示，不重新调用模型、执行工具或派发交付。

典型场景：研究运行等待人工审批时页面关闭，审批记录仍然存在，用户回来后继续处理。
审批超时与取消仍由服务端规则决定，不与 SSE 连接寿命绑定。

增加事件表不等于获得 Temporal 的完整恢复能力。服务端重启后的执行恢复仍依赖现有
运行记录、真实收尾校验和幂等机制；显示事件回放不能直接充当工作流重执行。

## 3. 建议的模块边界

```text
客户端 ── HTTP 命令 ──→ 现有控制与编排服务
                               │
                        状态与关键事件落库
                               │
                        发布通知至 Redis
                               │
客户端 ←──── SSE ───── 空间事件适配层 ←── 持久事件补读
                               ↑
                    Team / Single 原有运行事件
```

空间事件适配层向前端提供稳定的展示契约，关联空间、参与方、会话、Run、成员及事件版本。
Team 或 Single 内部升级时，由对应适配器消化事件差异，不让客户端依赖内部计划、私有
checkpoint 或具体工作流步骤。标识字段、游标与兼容策略尚待接口设计冻结。

关键业务事件和实时输出可以共用一条 SSE 连接，但保留各自的恢复规则。单个 Run 结束
只结束该运行的展示段，不自动结束整个空间订阅；审批、交付及下一次 Run 仍可能发生。

适配层不读取对方私有历史来构造研究上下文，也不通过思考文本推断下一步执行。用户
查看空间事件的权限与 Agent 读取另一会话记忆的权限相互独立。

A2A 可继续作为任务、状态及产物通信的参考，其支持长任务的 SSE 更新。
[A2A 流式与异步操作](https://a2a-protocol.org/latest/topics/streaming-and-async/)
采用这些概念不代表已实现 A2A 兼容，也不自动提供本项目需要的空间游标、历史补读和
状态一致性保证。

## 4. 待明确的实现契约

| 议题 | 后续需要明确的内容 |
|---|---|
| 事件身份与顺序 | 空间游标、Run 输出位置、事件 ID、去重键与版本兼容；展示到达顺序不能替代业务 FIFO |
| 快照与补读 | 一致性边界、保留期限、过期响应、历史与实时切换、文本缺片恢复 |
| 可靠发布 | 状态与事件的原子写入范围、重试、重复投递、Redis 故障后的补偿读取 |
| 多实例推送 | API 实例之间的事件路由、独立 Redis 命名空间及广播方式，避免误用工作队列消费组 |
| 背压与容量 | 客户端队列上限、合并频率、慢连接处理、重连退避与连接数量限制 |
| 生命周期 | 空间与 Run 的终态区分，暂停、停止、等待审批和连接健康的独立表达 |
| 权限与内容 | 建连和重连鉴权、长连接权限失效处理、回放与实时一致脱敏、跨空间隔离 |
| 前端隔离 | 独立 Super-link 状态管理，多 Run 与 Team 成员输出归属，避免占用普通模式的当前 Run 状态 |

此表保留开工前的讨论范围。T01 已确定事件身份、快照补读、生命周期、可靠发布和首版
默认参数，具体契约集中见[技术框架 §11](super-link-technical-design.md#11-sse-接入边界2026-11-20)，
后续实施按该契约验收；本稿不维护第二套接口定义。

### 4.1 事件来源覆盖

关键事件不能只在 HTTP 路由内产生。需要逐一登记人工控制、审批请求及超时、Worker
退出、收尾提交、旁路检查及重试、交付补正、队列受理及取消、后台停止确认和启动恢复等
状态变化的权威写入位置。事件应在实际状态提交处生成，不能依赖页面刷新来发现遗漏。

事件目录需说明来源模块、产生条件、事务边界、空间与 Run 归属、恢复方式和对应测试。
既有审批或运行记录若不能与空间事件同事务写入，应定义可恢复的转换与核对机制，不能
以跨进程内存通知冒充原子提交。来源核对只读取必要状态，不读取或重放私有模型上下文。

### 4.2 并发提交顺序与游标

自增事件 ID 不自动保证提交顺序。事务 A 先取得 100，事务 B 的 101 先提交并被客户端
读取；若游标推进到 101，A 后提交的 100 就可能被永久跳过。必须定义空间内安全的发布
顺序及可推进位置，覆盖并发、回滚和服务重启；不能直接取当前最大的 ID 作为安全水位。

T01 选择业务事务末尾锁独立事件头、分配空间序号并一同提交，具体锁顺序和保存点规则
见技术框架 §11.3；不采用单纯的全局自增 ID 或事后另写事件。
空间展示顺序仍不替代接收会话的业务 FIFO，实时文本的位置也不能冒充业务事件游标。

### 4.3 不干扰执行的故障边界

浏览器断开、SSE 发送失败、慢连接及 Redis 通知失败应隔离在展示和通知层，可从持久
记录恢复。权威状态、交付或必要事件记录保存失败则需按事务与既有恢复规则处理，不能
忽略异常后对外宣称成功。最小事件记录的存储成本和锁竞争需纳入负载验证。

### 4.4 历史阅读与多标签页

用户阅读较早交付、审批或运行记录时，后台仍可更新最新状态，但不能强制翻页、滚动或
覆盖正在编辑的输入；用新记录提示让用户自行返回最新位置。切换空间后必须释放旧订阅，
迟到响应不能写入新空间。多个标签页继续使用原控制版本和幂等键处理并发操作，SSE
接收到新版本不等于用户已确认基于新版本执行原操作。

### 4.5 观测与部署链路

至少记录事件发布延迟、待发布积压、补读和重新同步次数、活跃连接及慢连接断开数量，
通过空间、Run 和事件标识关联排障；日志避免写入令牌和未经脱敏的内容。

验收要经过实际代理链路，覆盖心跳、空闲连接、缓冲、重连和服务关闭时的资源释放。
运行输出目前存在进程本地订阅来源，不能用关键事件的 Redis 通知证明跨 API 实例的
文本流也已接通。首版若限定单 API 实例，需明确配置约束和拒绝或降级行为；多实例能力
必须另有运行输出路由证据。已有控制迁移与新增 SSE 迁移的升级顺序、备份和代码回退
兼容性在启用前一并验证，不以删除新记录作为回退手段。

## 5. 优先验证场景

下表是后续实现的验证目标，不是已通过的测试记录。

| 场景 | 操作或故障 | 预期结果 |
|---|---|---|
| 离线期间完成交接 | 已接受研究后关闭页面，服务端完成 Team 收尾、旁路及 Single 交接，再打开页面 | 当前状态准确；关键事件可补读；不重复派发；监控仍按原有在线规则处理 |
| 停止响应丢失 | 服务端接受停止，但客户端未收到 HTTP 响应，以同一幂等键重试 | 复用原操作记录；请求接受与实际停止分别显示；不能伪造退出或提前交付 |
| 输出拥塞与通信故障 | 多成员输出时模拟慢客户端、SSE 断线或 Redis 暂时不可用 | Agent 正常执行；缓冲有界；关键状态可恢复；文本缺口能修复 |
| 运行切换与重复事件 | 一个 Run 结束并启动下一次，补读与实时事件出现重叠 | 空间订阅继续有效；事件去重且归属正确；旧终态不覆盖新运行 |
| 恢复与隔离 | 事件游标过期、API 实例切换或访问权限失效 | 能重新同步或明确终止访问；不跨空间泄露；不因回放重新执行任务 |
| 原有模式兼容 | 同时运行普通 Single、Team 与 Super-link | 原有工具、上下文、运行控制和 SSE 行为保持兼容 |
