## 1. 目标与范围

新增 Super-link 页面入口，在独立协作范围内连接 Team 与 Single 两个可延续的会话：
Team 研究并形成策略，Single 承接、核验、建立监控和持续跟进；双方在完成各自一轮运行后
交换成果和请求，围绕共同目标和共同研究对象自主推进，各自维护独立的业务状态。

文档统一使用 Super-link；讨论中的 surper_link、Super—link 指同一产品设想。
内部标识、路由与数据库命名属于实现设计，尚未冻结。

本模式与现有“同一研究逐轮切换 single/team”分别定义。已有运行模式、会话历史、工具能力
和默认执行方式保持兼容；新模式的协作行为不得成为原有模式单独使用的前置条件。
最大限度复用既有执行能力，同时隔离新模式的目标、交接、队列和执行所有权。

## 2. 已确认的基本约定

1. Team 与 Single 是两个独立会话，各自保存上下文、运行记录、证据和产物。会话可以延续；
   一次运行结束不代表会话永久关闭。不得用“运行”“会话”互相替代。
2. 只有本轮运行结束且结果保存后，才能向对方正式交接；内部思考、成员草稿和运行中消息
   不直接触发对方运行。运行结束与任务完成分别表达，部分成果不得冒充完整交付。
3. Team 主 Agent 保留思考、规划和委派成员的能力；Single 自主分析跟进变化。双方自主提出
   下一步请求，不要求预先穷举所有研究分支，也不新增总控 Agent 作为必要条件。
4. Super-link 按协作约定执行交接、排队和运行启动。旁路只检查交付，不承担编排。
5. 接收会话按入队顺序执行。当前运行结束并保存结果后，再处理下一项；默认不跳过、
   不合并、不覆盖排队交接，不将新交接插入当前运行。
6. 默认最大限度自主授权，在既定目标和资源范围内自动研究、计算、通信、核验和维护监控。
   删除等破坏性操作为明确例外；具体例外清单后续确定。不能仅因调用命令行就要求人工批准。
7. 用户调整目标、暂停等明确控制必须有效。可靠性检查与操作记录不等于逐次人工审批。

### 2.1 共同研究对象与独立业务状态（2026-11-08 确认）

Team 与 Single 必须拥有共同的研究对象，例如同一家公司、行业或一组候选标的。研究对象
与承载过程的研究会话分别定义，见 [领域词汇](../../CONTEXT.md)。共同对象和总体目标不要求
双方维护一份统一业务状态，也不要求双方对该对象始终持有相同判断。

| 归属 | 自己维护的业务状态 | 对外交流的内容 |
|---|---|---|
| Team | 研究问题与进展、证据和反证、分析判断、分歧、待研究项及研究交付版本 | 完整且有深度的研究成果、结论变化、待验证问题及补充信息请求 |
| Single | 对象跟进、监控配置与覆盖、观测变化、采用的研究版本、处理结果及待答复请求 | 实际观测、接管和处理回执、补充研究或复研请求 |
| Super-link | 共同目标与对象关联、会话关联、交接检查/投递/接收/处理记录 | 可追溯的通信与执行记录；不维护双方共同改写的研究判断或监控业务状态 |

Team 的“完整”针对本轮研究问题：包含可定位证据、分析结论、支持与相反依据、适用范围、
时点、失效条件和未知项。无法回答的内容明确说明缺口，不为满足完整性强行生成确定结论。
Team 仍可产出市场阶段、策略适用性与交易条件判断，职责不缩减为原始材料收集。

Single 对接管和后续处理负责。Team 发布新结论，不直接修改 Single 的监控或已采用判断；
Single 接收、核验和处理后返回实际回执。Single 的处理结果也不回写 Team 已发布的原始交付。
双方可保存对方交付的固定版本及本方采用情况，并保留来源、时点和版本，不自动同步覆盖。

例如，同一公司 A 在 Team 侧可以处于“盈利逻辑重新评估中”，在 Single 侧同时处于
“继续观察并等待补充研究”。两者可以并存。若 Single 的新观测与 Team 的判断有分歧，
应保留各自依据并通过复研请求交流；旁路检查是否有依据和是否符合目标，不强制结论一致。

通信需要关联共同对象、具体问题、事实时点、所引用的研究/跟进版本、新增变化及处理请求。
研究结论变化、关键新事实、补充研究请求和处理回执均应可定位到相应对象。

本项业务原则已形成基础共识。对象标识与别名、公司和证券映射、对象集合增减、不同时间
尺度的关联及多份研究交付的采用细节，后续在业务开发中按实际问题补充；本版不预先冻结。
交付证据的读取范围见 §2.2；各自长期记忆原则见 §2.4，交接及记忆的实现机制仍待细化。

### 2.2 正式交付与证据读取范围（2026-11-08 确认）

双方会话独立，基础能力不包含任意查询对方完整会话历史。接收方需要读取和复核的是对方
正式交付的成果及其依据；不以开放对方内部对话为完成研究交接的前提。

| 内容 | 接收方式 |
|---|---|
| 资料库研报及公开市场资料 | 按交付提供的来源定位，通过接收方自身可用工具读取和复核 |
| 对方生成的报告、计算结果和数据底稿 | 随交付提供，或通过接收方可读取的固定版本引用取得，保留出处与时点 |
| 对方内部对话、规划过程、成员讨论和未交付草稿 | 保留在对方会话，不默认开放，也不要求接收方自行翻查以补齐交付 |

信息不足时，接收方提出具体补充请求；发送方在自己的会话中查阅历史或重新研究，完成
新一轮后补充交付。双方对称适用，不因一方是 Team 而改变该范围。

接收方可以保留并复用过去已收到的交付，读取这些固定版本材料不等于进入对方内部会话。
对方交付也不自动成为接收方已执行的工具结果；依赖当前行情的操作仍需核验最新事实。

旁路核查交付是否包含下一步所需证据，以及指定接收方是否能够读取、复核。仅有发送方
本地路径或旁路自身可访问的引用，不足以证明接收方可用。具体文件传递、引用解析和复取
方式留到技术实现细化，不要求新增完整跨会话历史查询接口。

本项确认第三个问题的读取范围和交付责任。第二个问题的自主交付业务原则见 §2.3；可靠
交接点、旁路启动及保存完成确认属于待设计机制，不能推导出已确认的两阶段检查或就绪状态方案。

### 2.3 编排方向登记（2026-11-08）

以普通编排代码实现专用 Super-link 协作执行器，集中管理两个独立会话的通信与执行路径。
Agent 提出业务请求，旁路检查交付，执行器管理请求关联、队列、运行启动及结果反馈；
既有 Team/Single 内部能力与独立业务状态保留，不需要新设总控 Agent。

本次仅登记方向，具体技术细节继续讨论，见 [技术框架 §1.1](super-link-technical-design.md#11-专用协作执行器方向登记2026-11-08)。
不把某种消息中间件或图框架设为前置，不冻结持久化、接口、状态模型和恢复机制。
第二项的业务原则已明确：是否交付、交付意图与内容由双方 Agent 根据目标自主判断，
典型场景不构成穷举的触发条件；运行结束并保存是正式交付的前提，不要求每轮都交付。
接收方自主判断如何处理，旁路负责校验，执行器负责排队与运行。精确交接机制仍待设计。
第四项长期记忆的已确认业务原则见 §2.4，不由本节的编排技术方向推导。

### 2.4 各自研究与跟进记忆（2026-11-08 确认）

Team 与 Single 各自形成并维护自己的记忆，对方的结果通过正式交付进入本方记忆。
人工发起和自动触发都是本方会话的工作来源，都可以形成有效记忆；是否纳入长期积累，
由内容的价值和依据决定，不仅由触发来源决定。双方不共享可变的记忆或统一研究判断。

#### 每轮工作的积累

原始执行记录作为追溯依据；每轮还应留下继续工作所需的判断与证据、适用时点、实际完成
事项与执行结果、未解决问题及后续理由，以及原有判断的变化和原因。具体有价值的内容
由本方 Agent 判断，不以只保存最终回复替代必要的工作积累。

Team 重点积累研究假设、证据、反证和结论演变；Single 重点积累监控依据、观测变化、
实际处理动作和待跟进事项。保存记录、后续可检索和自动带入下一轮上下文是不同能力，
不要求全部原始历史常驻模型上下文。

#### 收到交付与采纳判断

正式收到的交付应保留来源、版本和时点，并记录本方如何理解、是否采用、实际处理及
待验证事项。收到不等于认可或执行；双方可以保留不同判断。对方结论不能在多轮摘要后
变成本方已验证的事实，收到的材料也不自动成为本方已执行的工具回执。

#### 后续工作的续接

下一轮延续本方已有积累，由当前任务决定使用哪些判断、待办和历史依据。Agent 自主选择
相关历史，不因同一对象存在旧待办就自动恢复全部旧任务。记忆提供依据，后续执行仍通过
协作请求及编排流程推进，不能仅凭记忆中存在任务就自行绕过运行调度。

#### 新旧结论与分歧

结论可以改变，但变化过程应可追溯。记录新信息推翻旧判断、旧判断仅在过去时点成立、
双方存在待验证分歧等不同情况，保留变化依据和时点；不简单覆盖旧结论，也不使所有历史
结论长期保持同等效力。变化影响对方工作时，由本方 Agent 自主决定是否发起新的正式交付。
这不意味着新研究自动替换对方监控，具体策略采用和生效机制仍待讨论。

#### 用户重新介入

用户再次发言时，本方能够找到并使用自动工作期间的重要判断、执行结果和未完成事项，
不退回到上次人工发言时的认知。原始自动执行过程不必全部注入人工对话上下文。例如，
Single 应能解释为何仍监控某公司、期间有哪些变化、当前理由及实际采用的研究版本。

本节确认业务要求，不冻结存储结构、记忆写入接口、摘要与检索策略、上下文窗口、保留
期限及故障恢复机制。不通过修改普通 watch 的连续性语义来隐式实现 Super-link。

### 2.5 任务执行顺序（2026-11-08 确认）

每个会话统一排队、每次只执行一个运行；轮到任务时由本方 Agent 判断当前如何处理；
跨会话等待不长期占用本方执行位置。顺序约束保证请求获得处理机会，不要求机械执行
已经失效的动作，也不替 Agent 决定业务下一步。

#### 会话内串行、会话间并行

Team 与 Single 分别串行处理各自的会话级任务，两者可以同时运行。Team 内部主 Agent
规划与子 Agent 并行能力保持不变，不将会话级串行误解为禁止 Team 内部并行。
Team 研究期间，Single 可以继续处理监控事件；新交付进入接收方队列，不插入当前运行，
也不直接改变当前运行正在使用的判断依据。

#### 统一执行请求的排序范围

需要启动同一会话运行的用户普通任务、对方协作请求、监控触发任务及本方后续任务，
均经过同一套排队和会话占用检查，不能通过不同来源的入口绕过串行约束。
仅保存资料、记录回执或后台采集不必启动 Agent，也不因此获得改变当前判断的权限。

用户明确停止或暂停属于运行控制，不能排在待停止的任务后面等待执行。停止后的剩余
队列、在途交付及恢复行为仍待讨论；控制操作不等于普通任务获得插队优先级。

#### 按序处理时重新判断适用性

排队时提出的行动意图不保证执行时仍有效。轮到任务后，Agent 根据当前事实和合法可用
依据自主决定继续、结束、请求补充或提出后续任务，并保存实际处理结果与原因。
例如价格突破事件排队期间已回落，Single 应按序复核并记录当前判断，而非照搬触发时动作。
这种有记录的处理不等于编排层静默丢弃或跳过任务。

排在后面的交付不能被悄悄视作本方已经采纳的依据；未处理材料的提前可见范围及紧急
纠正机制需单独设计，不在本版引入自动抢占、重排或提前采纳。

#### 等待答复与释放执行位置

请求对方补充研究后，本方保存等待的问题、对应请求及已有进展，结束并保存本轮运行，
释放执行位置；问题仍未完成，不得将其记作业务成功。本方随后可以按序处理不依赖
该答复的其他任务。对方答复作为新交付按流程进入本方队列，并关联原问题。
不以长期占住运行、同步等待对方的方式维持协作；等待依赖的具体表示及恢复机制待设计。

#### 自主业务判断与执行秩序

Agent 可以判断当前无需行动、需要拆分或补充研究，并留下处理结果或新请求；编排层
执行已经确定的顺序，不因模型临时认为某项更重要就静默跳过、合并或覆盖已有队列项。
优先级调整、队首技术故障、等待超时及停止恢复仍需另行讨论，不从自主判断推导出任意改队权。

本节确认逻辑排序范围和业务处理原则，不冻结物理队列、入队时点、序号分配、并发仲裁、
租约、依赖恢复或调度框架，也不宣称当前实现已经支持全来源统一排序。

### 2.6 旁路的独立监管职责（2026-11-08 确认）

旁路是独立监管参与方，围绕任务目标、必要证据和交付可执行性进行检查，不参与形成
被检查的研究结论，不承担编排或推动业务必须得出某种结果的责任。独立性体现为依据、
检查上下文、记录和核查交流的独立归属，不预先要求实现为第三个长期会话。

旁路直接获得用户确定的目标、当前任务、双方职责及适用约束，不能仅依赖交付方对
任务要求的转述。目标变化应有来源和版本；被检查内容不能自行改写目标或降低要求。
旁路保留此前问题、补充说明、修订交付和复核结果，默认不读取双方完整内部会话。

| 交流关系 | 内容与边界 |
|---|---|
| Team 与 Single | 研究成果、观测、业务请求和实际处理结果 |
| 旁路向交付方 | 问题、依据、影响下一步的原因及需要说明或补足的内容 |
| 交付方向旁路 | 解释、补充证据、修订交付或有依据的异议 |
| 旁路向编排层 | 检查结论、对应交付版本、允许继续或阻断的原因 |

核查交流保留发送者、对应问题及交付版本，不混成双方的研究结论，也不冒充用户指令。
旁路可以核验证据、指出缺口，但不替交付方补做研究并审核自己形成的结论。补充运行
及队列安排仍由编排层执行；本节不增加绕过完成后交付原则的运行中通信路径。

检查结论需要可追溯、可复核；交付方可以提出有依据的异议，旁路重新核查并保留前后
结论及变化原因，不因其监管身份假定判断永远正确。合法分歧、反证、无交易机会和
有依据的继续观察不自动构成阻断。具体复核流程及次数仍待设计。

旁路是否进一步核查交付后的实际执行，属于监管范围扩展，尚未确定；不因“监管”
称谓默认增加全程监督、业务决策或执行控制权限。

### 2.7 工具能力延续与逐步接入（2026-11-08 确认）

除监控专属能力外，Single 的工具能力原则上在 Team 中延续，相应能力逐步接入。
两者主要按业务职责分工，不以长期限制 Team 的数据和研究工具作为分工手段。
Team 可使用资料检索、行情、财务、宏观数据及计算等能力独立研究和核验，无需将 Single
作为必要的数据中转。Single 保留研究与复核能力，并承担监控建立、维护和处理。

历史行情查询、指标计算等研究能力不因与监控相关就整体归入监控专属工具；具体工具
清单和接入顺序后续明确。当前缺少的 Team 工具属于逐步补齐的实现事项，不是长期架构
限制；计划接入不等于当前已可用。接入需保护既有模式的默认行为和基础能力。

旁路结合任务分工及实际能力判断交付，不要求每次都使用同一套工具。但能力缺失不能
成为伪造证据或豁免必要证据的理由：缺口应如实说明，按其是否影响下一步判断处置。

### 2.8 观察对象与等待交易信号的对象（2026-11-08 确认）

业务需要区分仍在研究、观察和补充依据的对象，与已经具有一定研究及策略依据、当前
重点等待交易条件或信号的对象。该区分说明当前跟进意图，不表示发现候选或建立监控
就已具备交易条件，也不表示信号出现就已授权或执行真实交易。

本版不固定两类对象的全部判定条件、阈值、枚举或转移路径，不要求所有对象按同一阶段
依次推进。执行中可以依据新事实和业务需要调整跟进意图、退回观察或采用更合适的表达；
由 Agent 在既定目标内判断，保留当前理由、依据及重要变化，不为填满流程强行升级对象。

双方仍保留独立业务状态：Team 的研究判断不自动改变 Single 的跟进安排。通信应表达
当前意图和需要对方做什么；旁路据此检查相应证据与执行条件，不对普通观察任务套用
等待交易信号任务的完整交付要求。未来业务扩展可补充此处，当前不建立僵化状态机。

| Single | 承接研究、最新事实核验、监控建立与维护、信号复核、反馈变化和提出复研请求 | 用无依据阈值伪装监控完成、把触发事实直接当作成交 |
| 旁路 | 独立检查目标一致性、必要证据及下一步可执行性；保存检查与复核记录，开展有依据的核查交流 | 选择下一位执行者、替交付方补做研究、启动运行、改写双方原始交付 |
| Super-link | 维护共同目标、研究对象与会话关联，执行允许的交接及顺序派发，记录处理结果 | 维护双方统一业务状态、替代 Team 内部规划、把模型请求直接升级为更大权限 |

双方会话的物理映射及业务资料绑定见技术框架建议，不因此改变既有研究的归属定义。

## 4. 交付与旁路检查

一次交付需要让接收方理解：对应哪个共同研究对象和目标、本轮完成了什么、依据是什么、还有哪些问题，
以及是否请求接收方行动。应区分研究结果与下一步请求；信息回执不必自动生成新运行。

旁路以既定任务目标、当前分工和接收方下一步需要为依据：

| 结果 | 条件 | 处理 |
|---|---|---|
| 通过 | 内容符合目标，必要证据和执行信息齐备 | 允许交接 |
| 附带说明继续 | 有不确定性或非关键缺口，接收方仍可继续执行 | 原交付与问题说明一同传递 |
| 阻断 | 明显偏离任务；缺少支撑关键判断的证据；必要内容不足导致下一步无法执行 | 不投递为可执行任务，向发送方返回具体缺口 |
| 检查未完成 | 检查失败或缺少判断条件 | 保存交付与失败原因，不伪造通过；恢复方式待后续设计 |

每个问题应关联具体目标/要求、相关交付内容及原因；不能只给模糊分数。
例如，核验最新行情已分配给 Single 时，Team 未提供最新行情不必阻断；标的身份无法确认、
关键来源不可定位而导致无法接手时，则应阻断。证据要求随本次任务而定，不要求所有候选
假设在交接前都被证明。反证、策略否定、未发现合格候选均可构成有效交付。

旁路检查不等于收益验证、策略正确性证明或交易执行授权。它不复做完整研究，不要求双方
接受其偏好的研究方向。退回后的补充请求由 Agent 与 Super-link 协作规则处理，旁路不调度。

## 5. 场景一：最新研报 → 候选对象 → Single 建立监控

1. 用户给出目标：“从资料库检索最新研报，找出潜在交易对象，列出清单交给 Single 监控”。
2. Team 明确检索范围、发布日期口径、截止时点及覆盖缺口，检索并读取材料。“最新”不能
   用入库时间代替发布日期，部分检索结果不能声称全库穷尽；最近 30 天仅是此前推演假设，
   不是本需求固定默认值。未知发布日期应如实表达。
3. Team 交付候选对象、研究逻辑、来源/时点/原文定位、反证、适用与失效条件、建议跟进问题。
   作者观点与系统分析分开。找不到合格对象时允许空清单，不凑数。
4. Team 本轮结束并保存，提交交付；旁路检查后进入 Single 接收队列。
5. Single 核验标的身份、最新数据、现有监控和数据能力，将可支持的跟进要求落为监控目标。
   成功必须有实际保存回执；报告正文不能代替保存。
6. Single 本轮结束后交付接管结果：已建立、部分覆盖、待验证或暂不跟进，并说明原因。
   价格监控不能冒充产品价格、订单或政策兑现等基本面监控；不能编造阈值来完成数量目标。

上述接管状态、逐项检查与继续方式属于推荐表达，具体字段枚举尚未冻结。
候选可用于持续观察，也可用于等待已有依据支持的交易信号；跟进意图按 §2.8 表达，
不因加入清单或建立监控就视作已经进入交易阶段。

## 6. 场景二：完整监控 → 市场环境研究 → Single 持续核验

1. 在推演中，Single 已建立完整监控。它在本轮结束时向 Team 提交补充研究请求，附候选和
   策略版本、观测时点、已触发/未满足条件、待解决问题，以及目标市场和分析时间尺度。
2. 旁路检查请求是否仍服务于共同目标、信息是否足以推进；Super-link 将通过的请求按序派发。
3. Team 主 Agent 自主规划与委派，从宏观、整体市场、行业及候选对象出发，判断策略适用性、
   当前阶段、信号是否清晰和行动条件。未知或证据冲突可以是有效结果。
4. Team 返回当前判断、支持与相反证据、已满足/未满足条件、待核验事实、适用时间和失效条件。
   环境支持、对象值得关注、交易条件满足分别表达，不能互相替代。
5. 旁路检查后，Single 按序接收，核验等待期间是否发生变化，再落实监控或跟进处理并保存回执。
6. 新事实影响原策略时，Single 可以自主提出有依据的复研请求，形成下一轮；普通确认消息
   不应引发无实质进展的来回运行。

后台监控与 Team 研究可以并行，但不因此承诺关闭浏览器后继续采集；在线要求、频率及
监控覆盖的产品调整尚待确定。当前监控能力不能因推演中的“完整监控”假设被视为已经补齐。

## 7. 页面与可观察结果

已确认新增独立入口。以下为基础展示建议，具体页面布局尚未确定：

- 共同目标、两个会话及各自运行状态；用户可分别查看过程与成果。
- 每次交付、检查回执、队列顺序和接收处理结果可关联查看。
- 区分“已提交、检查通过、已排队、已接收、已处理”，不把收到等同采用或执行成功。
- 显示实际监控覆盖、失败原因和待解决问题，不把数据源故障描述为无机会。
- 既有 single/team 入口继续可用，不要求用户迁移旧研究才能使用原功能。

## 9. 明确暂缓的决策

用户要求以下内容在整体框架形成后再讨论。本版保留问题，不替用户冻结答案：

- 第二个问题的业务自主原则见 §2.3；实现仍需讨论可靠交接时点、运行结束与保存完成的关系、旁路介入时机，以及
  材料尚未就绪和内容缺失的判定责任。原有“运行结束并保存后交接”原则保留，但程序就绪标记、
  两阶段检查及等待/恢复机制均未确认，不能作为已经定案的实施要求。
- 新策略采用、生效、替代，以及旧策略事件的处理规则。
- 旁路是否扩展至执行后核查、是否采用独立长期会话及具体复核机制；监管独立原则已确认。
- 非监控工具的具体接入清单和顺序、监控专属能力边界；对象跟进意图的具体表达随业务细化，不预设固定枚举或转换规则。
- 修正次数、往返预算、停止条件、失败重试和人工介入阈值。
- 删除等破坏性操作的完整例外清单；监控取消与数据删除不能未经讨论直接等同。
- 真实交易是否纳入、具体账户/额度/工具及授权范围；当前基础链路不包含券商下单。

写入、检索与摘要、上下文继承及故障恢复机制仍需技术设计。
