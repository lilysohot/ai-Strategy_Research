## 1. 结论与交付标准

本轮主要问题是执行入口分散、参数接线不完整、错误恢复缺失，以及把检索增强失败当成
整批发布失败。不能将说明校验拒绝、网络异常和普通 DOCX 书签归为“研报质量差”。
部分 OCR 文本确有错字、日期与时间粘连；这要求明确记录识别质量，不代表原件损坏。

改造目标：部署时一次配置数据库、OCR、备份、Web 激活方式、授权与重试预算；之后用户
放入文件、运行一条发布命令即可。中断后用同一批次续办，无需临时 Python、SQL、复制
build 哈希、手工生成多个清单或反复询问已授权的文字不完整发布。

完成必须分开表示：全量完成、部分已在 Web 生效、等待基础设施恢复、需要资料处置。
有材料被隔离时不得报“全部成功”；异常材料不得阻断其他已就绪材料的 Web 激活。

## 2. 本轮可复现根因

### 2.1 说明校验把格式变化、同义表述当成新增事实

以数据库里保存的 8 条 rejected 说明，调用实际 `contextual.validate_note` 只读重放，
8 条均重现原错误。对应文件为 `plugins/corpus/retrieval/contextual.py`。

| 实际原文 | 生成说明 | 当前拒绝原因 |
|---|---|---|
| `2026.11.1310:16期五` | `2026.11.13` | 通用数字正则把原文的日和小时粘连部分当成其他数字，找不到独立的 `13` |
| `2026.11.1207:06` | `2026.11.12` | 同类日期误拒 |
| `2026-28年收入分别为…` | `2026-2028年业绩预测` | 无法处理原文缩写年份，另有词面差异 |
| `东北证券…预计…归母净利润…` | `归母净利润预测` | `预测` 两字不在原文，虽有 `预计` 也拒绝 |

这证明部分拒绝是误拒，不证明整条说明的全部事实都准确。不能通过放宽数字子串匹配或
无条件同义词放行来解决；数字、机构、预测归属仍应绑定具体原文范围。
OCR 粘连日期的解释还可能有歧义，不能自动把推测日期写成已核实发布日期。

### 2.2 命令参数被接受，但没有生效

只读调用真实 `cli.main`，替换执行函数为记录参数的 mock，不写数据库、不调用模型：

- 请求 `context-generate --chunks-per-request 1`，实际收到 `12`（来自环境配置）。
  `cli.py` 仅在 context-plan 中使用该参数；generate 直接创建 `NoteConfig.from_env()`。
  所以上轮声称“已经逐块重试”不成立。
- 请求 `native-pack --retry-uncertain`，实际 build_pack 未收到该参数。
  argparse 接受这个全局选项，但只在普通向量 build 分支传递。
- mock 返回 `missing=1, error_code=null` 时 CLI 退出码仍为 `0`。
  这只代表命令执行结束，不能代表准备完成。

### 2.3 向量异常成为不能续办的状态

实际数据库保存 2 条 `uncertain/provider_transport_uncertain`。
`embedding.py` 将 HTTP 传输异常合并为此码，未保存细分异常类别；现有证据无法进一步
证明具体是连接、读取超时还是其他传输故障，不能断言供应商已计费或未计费。

`contextual_pg._embed_missing` 只为不存在的缓存记录执行 INSERT/请求；已有 uncertain
记录触发冲突后直接跳过。普通 `VectorIndex.build` 虽支持 retry_uncertain，却明确拒绝
contextual-note-v1。因而重复 native-pack 不会修复这两条记录。

说明生成也没有完整恢复语义：ready 之外的记录都会再次进入 pending，与其“不自动重试
不确定结果”的注释不符；调用前缺少持久请求登记，崩溃无法清楚区分未请求与结果未知。

### 2.4 DOCX 普通书签被当成未知正文缺口

实际解包 `11月10日Anthropic 27年ARR.docx`：`word/document.xml` 的 body[221]
是 `w:bookmarkEnd`，body[222] 是 `w:sectPr`。该书签结束节点没有子节点。
本次 `unknown_body_element@body[221]` 是读取器未识别非正文结构标记。
不能泛化为“忽略所有未知元素”：承载文字、对象或图片的未知节点仍应保留阻断。

### 2.5 CSV 备份没有覆盖本次写入的数据

`.scratch/corpus-incoming-20261117/recovery-prepublish-backup-001/manifest.json`
只列 documents、blocks、claims、claim_block_runs，四项计数全部为 0。
`service._backup_csv` 的固定表集合没有新链的 corpus.* 与 corpus_retrieval.*。
同期只读核查实际新链有 312 个来源、499 个构建、279 条发布记录。
所以“CSV 备份命令成功”不能证明新链可恢复；上轮的恢复快照完成声明应撤回。

### 2.6 编排和观测不足，放大了上述问题

- `scripts/ingest-corpus.sh` 调用旧 `service ingest`，描述的是 data/corpus；不覆盖
  当前 incoming → preparation → contextual pack → Web 激活，不能冒称完整入口。
- 上轮用上一批 inventory 当历史全集，重建了已有来源；又手写哈希、混用 shell，
  将参数错误误判为材料故障。文档已提醒，但没有程序阻止。
- 没有统一批次状态、来源清单收敛、发布锁及 Web 验收控制；准备就绪的来源仍未激活。
- 长任务输出被重定向而缺少进度事件，操作者把“暂时没输出”判断为挂起。
  进程总时长不能证明某个请求超时；上轮终止任务的判断依据不足。
- `generate` 的返回字典把本轮 token 数和 `status` 的存量 token 数使用同名字段合并，
  后者覆盖前者；记录更新也覆盖旧尝试 usage，不能据此统计本轮实际消耗。
- 历史记录另有 61 份 OCR 失败、4 份不支持格式。此前只汇报 14 份候选的结果，
  不足以代表整个输入目录完成；这些记录需重新与当前活动来源、OCR 衍生版核对。

## 3. 统一入口：日常只运行固定命令

以下是拟实现的接口，**目前不可作为已实现命令执行**。扩展现有 corpus CLI，复用
现有服务，不再另建一套解析器、检索算法或证据句柄。

```bash
cd /home/administrator/FrontierAgent
uv run --no-sync --env-file .env python -m plugins.corpus.cli release \
  --incoming data/corpus-incoming/20261026 --deployment web

# 中断、网络恢复或需要续办时：
uv run --no-sync --env-file .env python -m plugins.corpus.cli release --resume <batch_id>

# 只查看结果：
uv run --no-sync --env-file .env python -m plugins.corpus.cli release-status --batch <batch_id>
```

部署配置一次确定：目标库、归档目录、OCR 与模型服务、完整备份方式、Web 服务管理器、
检索验收身份、已有授权的可用文字政策、重试次数和费用上限。缺少授权的例外单独待办；
不得伪造人工核验，也不得每个来源重新询问同一已授权政策。
重复对同一目录运行命令先核对活动状态，不能产生重复发布或重算已就绪向量。

## 4. 执行状态与恢复

### 4.1 自动执行顺序

1. **部署预检**：解析配置，核对目标库和运行中 Web 包；检查凭据、OCR 的真实小样本、
   模型服务、备份与 Web 管理入口。全局鉴权/目标错误立即停止，避免对全目录反复失败。
2. **冻结输入**：检查文件写入稳定性、签名和哈希；对比全量活动来源、当前 Web 包与
   已验证衍生关系。生成批次与逐文件台账，保存别名、来源 ID、活动构建和下一步。
3. **完整备份**：使用经验证覆盖新链、检索衍生表及关联对象存储的方案；检查 dump
   目录/schema/表覆盖和恢复能力。CSV 旧表导出不能充当替代。备份缺失在首次写入前失败。
4. **逐来源准备和发布**：准入、读取/OCR、构建、检查、按已有政策登记文字缺口、发布。
   有效结果直接传给下一阶段，不从 stdout 文本猜字段、不手填 build_id。
5. **检索准备**：对新增活动构建生成说明、补向量；失败按类型恢复，成功记录复用。
6. **冻结发布集合**：旧允许包 + 本批所有已就绪来源；其他来源生成明确待办。
   旧来源活动版本发生并发变化时重新协调，不能静默替换或丢失旧来源。
7. **生成并检查包**：逐文件哈希、来源范围、活动构建、旧句柄/正文/向量不变；先准备
   临时目录，检查完成后原子写入可用 manifest。复跑可识别本批已有包。
8. **激活与验收**：持部署锁，阻止新的运行进入切换窗口并等待已有任务结束；使用配置
   的服务管理方式激活。检查运行态包、认证 search/fetch 与新增来源覆盖，再记 Web 成功。
   验收失败自动恢复旧配置并验证旧检索；失败批次保留可续办记录。

首次生成的来源失败清单不永久冻结发布集合。每次 resume 重新收敛本批各来源状态，
把已恢复来源并入下一版；没有新增就绪项时不重建相同包、不重启 Web。
等待运行结束是 `waiting_activation`，不冒称完成；命令可以持续等待或报告明确待续办。

### 4.2 故障策略

| 故障 | 默认动作 | 何时需要人工 |
|---|---|---|
| 日期/数字/措辞导致说明拒绝 | 带具体拒绝原因定向修复一次；仍失败则使用有原文范围的抽取式上下文 | 没有可核验的抽取候选时隔离该来源 |
| 说明增强不可用 | 抽取标题、章节或本块完整原句，120 字内，保留出处；不捏造日期与机构 | 不能保持可追溯性时，不强造说明 |
| 网络超时、429、可恢复 5xx | 按持久预算有限退避；确认无活跃请求后重试相同输入 | 预算耗尽或部署鉴权错误 |
| uncertain 向量 | 记录结果未知及可能重复计费，按部署已授权的有限重试策略处理 | 不具备重试授权/预算时报告可操作待办 |
| OCR 忙/超时 | 按服务容量排队，按页检查点恢复，有限重试 | 无可用正文或持续识别失败 |
| 普通 DOCX 书签等标记 | 显式白名单识别并保留结构信息，不产生正文缺口 | 未知且可能承载正文的元素 |
| 图片/图表残缺但文字可用 | 按已授权文字版政策登记全部准确缺口并发布 | 不在已有授权范围内的例外 |
| 格式不支持或文件确实损坏 | 该文件记待办，继续其他来源 | 需要替换文件或新增读取能力 |
| 一份材料失败 | 隔离该来源，其他就绪来源照常进入 Web | 无需反复询问是否继续其余材料 |

抽取式说明是**拟新增的明确策略**，不是手改 rejected 为 ready。保留 generated 与
extractive 类型、出处、拒绝原因和质量状态；原文、fetch 哈希、chunk ID 不改。
检索可能失去部分上下文增强效果，需用通用查询回归验证，不能声称与生成说明等效。
验证/提示词变化必须版本化；旧包与旧就绪说明冻结复用，新策略只用于新增/待修复输入。
不能通过整体改版本导致历史全库重算。实施时包构造需按条目携带的验证版本重验。

### 4.3 持久化与成本边界

- 每个阶段结果使用明确类型；不能通用地把 `ok=true` 或退出码 0 当作阶段完成。
- 每个模型请求在发出前登记 input_hash、profile、attempt、预算与状态；请求结束记
  ready/rejected/retry_wait/uncertain。lease 到期后核对持有者，仍运行的请求不得重发。
- 有限重试次数按输入累计并跨 resume 保存，不因重新运行命令而清零。部署层可提前授权
  uncertain 最多一次重发；不能承诺供应商恰好计费一次。
- 每次尝试的错误、耗时、usage 独立保存；总额、本轮额和未知费用分别汇总。日志不存密钥。
- 按来源及发布目标加锁；配置/发布指针使用比较后更新，防止两个批次互相覆盖。
- 进度事件输出阶段、完成数量、当前来源、心跳和请求截止时间。用真实请求期限判断
  超时，禁止用外层终端回传时间或累计运行时长判断“挂死”。
- 统一结果：`complete`、`partial`、`waiting`、`blocked`；拟定退出码分别为 0、10、11、12，
  参数错误为 2。逐文件区分 published_db、context_ready、vector_ready、web_verified。
  完整回执列出所有输入去向和精确恢复动作，不以命令数或构建数代替发布数。

## 5. 实施顺序与验收

1. **先修命令真实语义**：参数必须被执行层使用或明确拒绝；为上下文向量增加有锁、
   有预算和逐次记录的恢复路径；状态与退出码一致。针对 CLI 调用链写失败回归再修复。
2. **修本次确定误拒**：日期解析仅用于校验副本、避免推断；缩写年份与同义措辞要有
   具体范围支持，优先通过简短抽取式说明避免新增事实。识别 DOCX bookmarkEnd。
3. **一次性补齐发布编排**：把现有 API 串入统一 release 状态机，将临时目录中检索与
   Web 验收脚本的能力迁入正式维护入口；旧 ingest 脚本明确标为旧链。
4. **用本批故障验收**：不重建已发布历史资料；重新核对 61 条 OCR、4 条格式待办是否
   已被其他活动来源覆盖；对 12 条已发布来源从缺少的阶段恢复，单独复核两条解析待办。
5. **最后才更新操作主文档为可执行新命令**，标明旧分步命令为排障接口。

必要验收包括：

- 真实拒绝样本的离线重放和伪造数字/机构的负例；原文和句柄完全不变。
- CLI `--chunks-per-request 1` 实际传 1；不适用的参数明确拒绝，不再静默接受。
- uncertain 经受控重试变 ready，重复运行不重复请求；崩溃后不抢占活跃 lease。
- 断点后恢复、不重复发布；一份 OCR/解析失败不阻止其他来源 Web 生效。
- 任一说明/向量故障都有明确待办，预算耗尽不无限循环。
- 新链备份覆盖验证及隔离库恢复演练；空旧表 CSV 必须被预检识别为不适用。
- 部分发布必须至少一次真实运行态验收；有新增已就绪材料时不允许只交付 DB 发布。
- 每份新来源在包内存在且原文可读；认证检索核对目标来源，抽查新旧 ref 的 fetch 与
  页码/OCR 覆盖标记。自然语言未命中要区分检索质量与缺失入包，不能只测通用旧查询。
- 激活失败自动回退，原包继续可用；活跃任务期间不得强杀任务。

本设计不能保证损坏文件或供应商持续不可用时所有资料自动成功。保证的是：正常材料
一次命令走到 Web，暂时故障按预算自动恢复，无法恢复的材料有明确状态，合格材料不
再因这些例外反复被整批阻断。
