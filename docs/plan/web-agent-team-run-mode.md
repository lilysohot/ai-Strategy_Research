## 1. 已确认的上下文标准

用户明确接受现有单 Agent 的上下文处理方式：模型窗口限制、正常压缩/摘要和按需读取历史细节；可以接受切换模式导致 KV cache 失效。

**切换不能主动删掉信息，重要约束必须直接继承，历史细节仍可读取。** 这是原有上下文能力的延续要求，不是无限历史逐字常驻模型的要求。

具体验收含义：

1. 原始对话、已持久化工具结果、证据和产物不能因切换被删除或覆盖。窗口裁剪只影响本次输入，不应等同于删除存档。
2. 最新有效用户要求、否定/修正、未解决问题、业务绑定和当前业务快照，必须在新模式输入中直接可见，不能只存一个等待模型主动读取的文件链接。
3. 原有压缩记忆和近期上下文可沿用；不得以“切换”为理由只保留最终答案、重新从空上下文开始，或再强制做一次有损交接摘要。
4. 历史细节按授权引用可读，能定位原始来源；仅数据库/磁盘中有记录、目标 Agent 没有读取路径，不算满足。
5. 接受正常 token 上限及压缩限制；上下文来源缺失、关键约束装不下或历史不可用时明确失败/说明缺口，不以静默丢失冒充完整续接。
6. 不把 KV 命中、跨角色共享缓存或固定主 Agent 作为交付条件；纯 single 的原有路径仍不因团队功能额外增加调用或迁移要求。

此处“不丢”是工程层的数据保留、组装和读取保证，不承诺模型在收到信息后永不误解。既有历史本来就未保存、已截断或已删除的细节不能凭空恢复，须区分既存缺口与切换引入的损失。

## 2. 推荐方向及难度

**推荐重新采用按 Run 选择实际工作流：single 使用 stateful-react-agent，team 使用 agent_team；补齐工作流之间的上下文适配。**

相比 v2.1，不再强制“先独立团队研究、最后单 Agent 整合”，也不再把“每轮最多一次团队阶段”作为架构限制。团队轮次由 coordinator 直接统筹、补数和回答，可在预算内安排成员迭代。账户/计划的唯一业务职责仍保留。

难度判断：中高，主要在上下文语义、历史读取、提交恢复和团队 Web 通道，不在 KV。接受缓存失效后可使用目标工作流自己的 system、工具集合和模型会话身份，省去维持跨模式相同前缀的约束；仍不能绕过消息格式与权限校验。

本次不直接复活 v1.4 的全部设计：不要求所有 pure single 维护中性记忆，也不引入切换专用的逐轮摘要。物理存储和接口在 M0 冻结，旧版本工期估计与验收编号失效。

## 3. 代码依据与不可忽略的现状

- workflows/stateful_react_agent/spec.py 与 nodes/main_agent.py 已接收 replay_payload，工作流验证后通过 initial_messages 回放；server 只运输不透明载荷。
- frontier_agent/components/observers/conversation_snapshot.py 已实现近期窗口、token 上限与累计摘要；select_replay 校验 pipeline/node、system、工具及消息格式。跨模式不能直接拿原生载荷强行回放。
- 现有摘要失败有 fallback/裁剪路径，不能把当前机制描述成无损记忆。切换需保留已有摘要与来源，不额外放大其损失。
- workflows/agent_team/spec.py 尚未接入同等跨轮回放；coordinator 原生续接也需要实现，不是仅首次从 single 导入。
- plugins/tools/assign_task.py、collect_reports.py 与 AgentBus 已支持队内任务追加/报告收集，有现成预算与次数限制。团队模式不必变成固定的一次批处理。
- server/orchestrator.py 目前读取会话失败可能无上下文启动，快照写回为 best-effort；历史是否可读也须逐类核实。沿用 single 的策略不等于上述异常已达到新验收条件。
- server/relay.py 固定 react_agent 轨迹，workflows/_shared/sdk_shim.py 的成员 trace observer 为空；Web 事件/审批/停止/用量仍需接线。

## 4. 上下文的职责划分

| 资料 | 职责 | 切换规则 |
|---|---|---|
| 原生会话载荷 | 各工作流自己的合法近期消息与压缩记忆 | 保持原样存档，不能让另一工作流直接覆盖或冒充自己的历史 |
| 最新人工上下文来源 | 确定哪次已提交 Run 是下一轮权威来源 | 同研究单一逻辑顺序，记录来源 Run、模式与版本；不能切回时复活旧 single 快照 |
| 重要约束及用户修正 | 新模式必须直接看到的输入 | 保留原文、来源与替代关系；模型提取可辅助，不能无来源编造或默认丢弃不确定项 |
| 历史记录与产物 | 详情与证据的可读取来源 | 绑定归属、版本、定位和状态，压缩摘要不覆盖其原始记录 |
| 业务数据 | 账户/计划及本轮有效输入 | 由服务端授权冻结快照提供；旧对话和团队结论不能覆盖当前业务数据 |

重要约束记录是有来源的输入要求，不是第二套不断改写的研究长摘要。纯 single 不强制每轮生成新交接内容；首次切换按原生载荷与可用原始来源初始化。混合会话后续必须跟上新用户修正，具体维护方式在 M0 验证，不能仅凭一次模型抽取宣布保证完整。

## 5. 工作流间的适配规则

### 5.1 同模式与跨模式

- single → single：优先沿用现有原生回放、窗口、压缩及缓存策略；未启用混合模式的研究不进入额外交接逻辑。
- single → team：从最新合法 single 上下文读取已有摘要、近期内容、有效要求及引用，构造 team coordinator 可接受的新输入。
- team → single：从最新 team coordinator 上下文与研究结果续接，不能只加载团队启动之前的旧 single 快照。成员详细记录通过引用取回。
- team → team：续接 coordinator 的有效原生历史；成员按本轮任务启动，不承诺复活旧进程。上一轮的证据、分歧和未完成事项仍可读取。

切换时不删除旧快照。目标工作流使用自己的 system 和工具定义，来源中的 system、内部控制信息和工具权限不能原样升级为目标指令。

### 5.2 适配内容与预算

工作流侧 Context Adapter 读取、校验和导出内容，server 继续只管外层版本、归属、传输和提交。不得从展示用 turns 重建 prompt，不恢复 history.txt 或 conversation_history。

跨模式转换优先确定性处理：保留已有压缩记忆、用户原话、近期结论、必要工具结果与来源；来源工具交互作为带角色和出处的历史资料呈现，不能伪造为目标 Agent 已执行的工具调用。完整工具调用/结果配对和目标 provider 消息合法性要验证，不直接关闭 select_replay 的保护。

不额外调用模型把所有历史总结成一小段“交接说明”。只有在模型预算要求时才使用与现有 single 相当的窗口/压缩策略，并记录裁剪原因；消息格式转换本身也占 token，需实测，不能声称字节不变。

重要约束优先进入本轮输入。若硬约束本身无法容纳或相互冲突，需明确澄清/失败；不得静默压掉约束。成员只接收主 Agent 分配的任务及必要约束，不要求所有成员携带完整主会话。

### 5.3 历史详情读取

M0 先核实原始用户输入、工具结果、团队报告和附件/产物各自保存在哪里，哪些已截断，目标工作流实际能读取什么。优先复用既有只读文件工具与授权 manifest 暂存路径；确有动态历史检索需要时再补受限读取通路，不把宿主目录或数据库凭据交给 Agent。

引用需指向当前有权限访问的来源版本；原文件改变、被删除、撤销访问或旧数据缺失时显式标记不可用。用户主动删除仍按既有产品规则处理，不因“上下文保留”私自延长保留期限。

## 6. 主 Agent 与账户/计划

single 时主 Agent 是 stateful-react-agent；team 时主 Agent 是 coordinator。职责随本轮主角色执行，业务归属始终在同一研究。

主 Agent 独占完整账户/计划读取、业务补数请求、回执处理和个性化计算；成员只研究分配的问题、报告缺口。通过角色工具白名单、执行 scope、环境和挂载限制实现，不能仅靠 prompt 约束。

业务请求幂等与服务端快照仍是数据真源；切换不新建重复待办，不把旧计划约束当成本轮实际资金数据。成员的通用工具不能绕过业务权限。

## 7. 提交、中断与一致性

混合会话必须知道最新已提交的上下文来源。沿用现有 single-only 存储语义，另以最小元数据记录混合会话来源；具体是否扩展既有表由 M0 确认，不预设双 head/coverage 合并系统。

- 同研究从启动到收尾保持互斥；提交检查 Run 所有权、执行代次和来源版本，迟到结果不能覆盖后轮。
- 正常完成后提交当前主 Agent 的上下文、证据引用及最新用户修正，成功后才作为下一轮来源。
- stop/崩溃时保留已有记录；区分已进入有效上下文和尚未处理的用户输入，后者下轮一次性承接，不虚构已回答。
- 未提交成功、来源读取失败或适配失败要可见；不以无历史新运行冒充连续会话。既有 single 异常路径的加固范围单独明确，不把未实现的保证宣称为原有能力。
- watch 可读取最近人工上下文，不推进人工上下文来源；删除研究、重试和迟到成员报告按同一执行所有权处理。

## 8. 团队通道与维护原则

主流程每 Run 执行所选工作流，不再要求 v2.1 的准备/team/single 三阶段。团队内部成员管理仍由现有 agent_team 负责，避免另外实现一套 Web 团队内核。

事件、轨迹、工具和审批使用 run/agent/attempt/source 身份；多成员审批不能互相覆盖。coordinator 结束、全队清理和产品 Run 完成正确衔接，刷新恢复不重复计费；用量覆盖全部成员及压缩调用。停止覆盖全部成员与工具进程，确认收尾后才能切换运行。

维护变化集中于工作流 Context Adapter、历史读取、原生快照来源提交以及 Web 多来源事件适配。以公共契约测试双方实现，避免在 server 写两套消息转换或复制 select_replay；框架内核不导入 server/benchmarks。不为暂时保缓存添加隐藏的主 Agent 准备/收尾调用。

## 9. 缓存和性能边界

跨模式 KV cache 失效被接受：允许改变提示词、工具集合与会话身份，并记录冷启动用量与时延。同模式仍尽可能沿用既有前缀策略。

不以缓存是否命中判断上下文是否完整；冷缓存也必须通过续接验收。历史读取和必要压缩仍产生成本，需分别计量；接受缓存损失不意味着取消每 Run 预算与超时。

## 10. 实施顺序

1. **M0：契约与最小往返验证。** 核实原生载荷/归档/历史读取能力，冻结主上下文导入导出规则；必须先落实 §13 的原文归档、输入采用与约束、幂等转换、历史读取、提交恢复和入口配置六类契约。用模型替身检查消息合法性、来源、约束及冷切换，再进行有预算的真实模型核验。
2. **M1：上下文闭环。** 实现 coordinator 原生续接、双向适配、重要约束承接、历史引用读取及失败恢复；纯 single 请求基线不退化。
3. **M2：团队 Web 接线。** mode/profile、角色业务权限、事件/审批/停止/用量、串行提交与历史兼容。
4. **M3：真实任务验证。** 模式往返、长对话、用户修正、账户更新、证据追问及中断恢复；完成下表后才启用功能。

M0 的关键止损条件：若只做到摘要传递而原始细节不可读，或靠恢复旧模式快照丢掉中间回合，则不得进入正式实现。若适配无法达到现有 single 的上下文标准，应说明具体缺口重新选择路线，而不是要求用户接受未声明的信息损失。

| C11 | 引用变化/删除/越权和不可信历史文本 | 来源状态真实、访问受控；历史内容不升级为目标系统指令 |
| C12 | 对照现有 single 的真实任务 | 同等窗口预算下关键约束及证据任务不因切换额外退化；报告成本与时延而不要求缓存命中 |

| C14 | 旧会话首次切换、连续修正、未采用 steer | 输入来源及采用状态可对账；不遗漏有效否定，不把排队但未采用的输入当已处理 |
| C15 | 连续十次模式往返、不新增事实、重复导入 | 同来源记录不重复，旧交接不递归包裹；语义和来源不随包装轮次漂移 |
| C16 | 成员发现关键反证但未进入最终答案、最终答案经过修复 | 反证/分歧有可发现索引；已发布答案及其状态与下一轮上下文一致，不只保存修复前消息 |

| C18 | 输出已显示而上下文未提交、孤立工具调用、重复恢复 | 不能提前允许后轮续接；不重跑有副作用工具；只采用可证明已保存的上下文与输入 |
| C19 | JSON/multipart/业务重算/watch、排队后改变默认模型 | mode 和角色 profile 不丢失；请求幂等、配置来源确定；watch 只读且不意外启用团队 |
| C20 | 通过 shell/共享文件/继承 scope 读取账户，尝试业务工具 | 子 Agent不能借旁路获得完整业务资料或修改补数槽；coordinator 具备正确业务工具及政策 |
| C21 | 旧浏览器/worker、关闭开关、旧历史、版本回退 | 不静默退回 single 或空历史；已生成混合历史仍可读；不兼容版本明确阻止执行 |
| C22 | 总预算耗尽、成员并发洪峰、慢 SSE 客户端 | 全队预算含重试/压缩/收尾，限流与缓冲受控；stop/approve 不被事件洪峰阻塞 |

## 12. 本次裁决与状态

2026-10-22 用户确认：接受当前单 Agent 的正常上下文处理方式及切换缓存失效，要求切换不主动删信息、重要约束直接继承、历史细节可读取。据此撤回固定主 Agent 与一次研究阶段作为必要前提，重新以实际工作流切换加上下文适配作为推荐方向。

本次只更新需求和设计；没有实现模式切换、执行真实模型实验或验证全部历史可读。需求边界明确不等于实现已经保证。

## 13. 全链路遗漏审查（v3.1）

结论：路线仍成立，但 v3.0 是方向契约，尚不是可直接完整实施的规格。以下事项中有些已提及目标却没有接线/失败语义，属于设计未闭合；不能因文档出现过关键词就判定完成。全部为待实施条件，不表示发现的是已上线团队功能缺陷。

### 13.1 原文归档不等于当前会话存储（阻断 M0）

代码事实：server/store.py::upsert_session_conversation 更新同一研究的一行 payload；server/orchestrator.py::_ingest_conversation 成功后删除 run/conversation.json。它们提供最新续接载荷，不提供每 Run 不可变快照档案。frontier_agent/components/observers/trajectory.py 的 JSON 默认截取工具结果正文前 16384 字符，JSONL 保留 observer 实际接收到的 result；JSONL 也不意味着能恢复工具更上游从未返回的内容。

补齐要求：混合模式启用前，归档最新可用原生载荷及其来源；后续每个参与混合研究的人工 Run 保存一次可验证的来源记录，成功后再推进最新来源。记录源类型、run/agent/attempt、版本/哈希、大小和完整度。轨迹展示 JSON 不能作为完整工具结果的唯一来源；JSONL 被配置关闭、尾行损坏或源工具已裁剪时明确给出完整度，不宣称无损。

不要求为每一轮复制全部累计历史；可用不可变原文记录、manifest 与引用去重。继续沿用研究删除/保留规则。pure single 不增加模型调用，不为了归档改写原始请求。旧会话只迁移可证实存在的记录，找不到的细节标记为 legacy_gap，不能从最终答案反向编造。

### 13.2 约束和输入采用状态没有生产契约（阻断 M0）

v3.0 的“重要约束直接继承”缺少生产者、更新时点及首次切换规则。若只从最新摘要抽取，早期用户否定可能已经不在摘要里；若只依赖模型输出列表，不能证明未遗漏。

补齐要求：混合会话保存有来源的用户输入记录，包括正式问题、已提交补充、结构化业务回执及采用状态；约束至少具备来源记录 ID、原文区间、作用范围、提出时点、有效/被替代/冲突/待确认状态及替代来源。更新与上下文提交关联，同模式继续也须更新，不能只在切换时运行。

直接用户要求与引用文档里的指令区分来源。自由文本提取可以使用模型建议，但删除/替代须可追溯；无法确定时保留新旧表述和冲突，不默默以新摘要覆盖旧要求。首次切换只从原生快照与可验证原始来源初始化，不能将 turns 全量重新渲染进 prompt；旧资料不足时说明缺口。约束过多超过预算需明确处理，不假装有一个永远放得下的摘要。

区分用户输入已保存、已注入、上下文已提交三件事。现有 steer 的 control_applied 可作为采用证据，但不能只看 UI 的“已排队”；停止前未注入的修正下一轮承接，已注入但快照未提交的输入按来源去重恢复。仅更新约束元数据不应强迫 pure single 每轮额外调用模型。

### 13.3 多次切换的去重与角色语义未定义（阻断 M0）

若每次把“上次会话内容”整体包成历史资料，S→T→S 会重复包裹旧交接，历史体积增长且角色含义逐渐模糊。

补齐要求：适配记录具备稳定 source ID；同一研究事实/消息不因新一次导入生成新的来源身份。保存转换器版本及已覆盖来源，导出时识别既有导入记录，不递归包装；正常新回答仍是新记录，不能按文本相同就删除真实重复用户发言。该覆盖信息用于去重与审计，不引入两个互相竞争的会话 head。

目标消息遵守 provider 规则；历史 user/assistant/tool 的身份保留为来源标签，不把历史 tool 调用伪造成目标运行已执行的调用。处理并行调用配对、工具错误、空/部分响应、结构化内容和 reasoning 格式；不兼容的 provider 私有控制字段留在原生档案，不能换 provider 后照搬。模型可用文本、证据和原附件引用需保留；非文本内容若目标无读取能力，显式提示而非丢字段。私有思考格式转换不是保证用户上下文连续的替代物。

M0 要做多次往返与重复导入的性质验证：给定不变来源，语义记录和 source ID 集合不因包装增加；目标上下文超限时只按明确窗口规则裁剪并留下来源。

### 13.4 团队结果完整性与已发布答案的一致性（阻断 M1）

coordinator 的近期消息并不必然包含成员全部报告。workflows/agent_team/nodes/main_agent.py 在 loop 返回后还会合并成员证据、修复引用 URL、执行发布限定并生成 final_text；若简单照搬 single 的 loop-end snapshot，可能保存了用户从未看到的修复前回答。可选 reporter 还会进一步改变发布内容。

补齐要求：首版明确关闭 reporter，不对外开放 agent_team_report；若后续启用须另验收发布同步。区分 loop 原生快照和本轮已发布答案/answer_status/来源，两者关联但不伪造工具历史；下一轮必须知道用户实际收到的回答、限定及未完成状态。

成员报告建立可发现索引，包含任务、输入版本、报告状态、证据/产物与未解决冲突。结果中已经标明的反证、冲突和关键缺口直接交主 Agent，不能仅因未入最终答案就不可发现；无法自动识别的重要性不作绝对保证。迟到报告按任务版本登记为未采用材料，不自动改写已发布结论。不能将“所有子 Agent全文常驻主 prompt”作为解法。

### 13.5 历史读取工具当前并未跨 Run 打通（阻断 M0）

代码事实：plugins/tools/recover_result.py 只读取调用者 ExecutionScope 的 trajectory_jsonl，并以当前运行的 turn/call_id 查找；不能因为它叫 recover_result 就认为能读取旧 Run 或另一成员轨迹。现有 team 的 tui profile 主工具主要是调度和 grep/glob，也不是 Web 历史阅读 profile。

补齐要求：定义 history manifest 的最小可发现字段及读取语义，引用必须包含 run、agent/source、attempt、记录 ID/版本，不能仅用 turn/call_id。主 Agent要具备实际读取入口及分页，不仅收到索引；验证跨模式读取一个被摘要省略的原始数值和其上下文。大文件按授权暂存/分页处理，不能为了一个问题扫描全部研究档案。

manifest、实际挂载/读取授权与工具白名单一起验证；成员只读必要任务切片，不能把包含完整账户信息的主 Agent 历史目录作为共享输入。引用失效、revert 后内容变更和历史删除的状态回传到主 Agent。

### 13.6 保存失败和发布终态之间存在恢复缺口（阻断 M1）

现有 ConversationSnapshotObserver 主要在 on_loop_end 写入；消息校验失败会不产生快照，不能假设取消时总有合法载荷。现有 _pump_frames 在 run_finished 回填回答/状态，而上下文入库在 _spawn 的 finally；“已有最终答案”早于“来源已提交”。store 的同 Run 幂等也不等于拒绝旧 Run 覆盖新 Run。

补齐要求：至少区分执行结束、来源提交、可安全续接。混合研究在归档、最新来源和输入采用确认持久化后才放行下一轮；跨实例/outbox 的活跃判断覆盖收尾期，普通请求不能只靠进程内队列。原始文件/对象与数据库无法同事务时用可恢复的提交清单：先持久化并校验源，再原子推进来源指针和采用确认；重入不重复，孤立源可稍后清理。

中断可能留下未配对工具调用：保留原始记录供审计，目标上下文采用明确的未完成状态或最后合法检查点，禁止伪造成功工具结果。恢复读取已存在结果，不能为重建消息重新执行有副作用工具或再次创建补数请求。连续性失败可作为独立可见状态，不能把无历史启动当作成功恢复。

### 13.7 模式选择尚未覆盖全部入口（阻断 M1）

代码事实：server/routes/runs.py 的 RunRequest/JSON/multipart 当前没有 mode；创建和业务重算使用 cfg.pipeline_id，orchestrator 启动也使用全局 pipeline。server/worker.py 的覆盖项主要是单 Agent 的 agent_tools，team 则读取 main_agent_tools/sub_agent_tools。这些层必须一起调整，单改数据库 pipeline_id 无效。

补齐要求：mode 采用 single/team 枚举，非法值拒绝；旧请求缺省 single；不得静默忽略 team 字段。前端提交、JSON/multipart、业务保存并分析、补数后续 Run、重算与自动派发都持久化并传递相同选择。内部重试保留原 Run 模式与配置；用户重算是新 Run，默认沿用来源模式，可显式改选，按新 Run 规则解析业务快照。补数触发的后续 Run 沿用其发起来源模式，不能取浏览器当前选择。

watch 首版固定 single、只读最新人工来源；人工最新来源为 team 时也必须经过只读适配，不能因此退回空上下文，亦不能启动额外团队。用户明确的新请求可改 mode；运行中的 mode 不可变。

新客户端统一提交幂等，指纹含研究、mode、问题、附件哈希及业务输入；同键异请求拒绝，旧客户端行为保持兼容但不宣称具备新幂等保证。接纳时固定 pipeline/profile/角色模型配置引用及非秘密版本，启动时不能重新选不同默认模型；凭据撤销应失败可见。worker 使用对应角色工具白名单与业务政策，不沿用 single 的 agent_tools 期待 team 自动识别。

### 13.8 成员权限存在 scope 与文件旁路（阻断 M1）

plugins/tools/investment_input_request.py 使用 ContextVar 包含可变 requested 槽，异步子任务可继承同一个对象；team 也存在 shared_workspace_dir。仅从成员工具列表去掉业务工具，不能证明它无法经 shell/read_file/共享历史读到账户资料。

补齐要求：主 Agent 与成员的业务 scope、任务输入、可读文件和运行环境分别核查；授权观察器对角色失败关闭。完整业务快照、主历史和原始控制记录不进入成员共享目录；最小任务约束由主 Agent 明确下发。主 Agent 自己并行调用或重复调用补数仍须幂等；现有单槽不能悄悄覆盖不同用途的未决请求，是否扩成按用途集合由业务流程用例决定。

此处限制的是成员业务权限，不限制 coordinator 正常统筹、工具审批或在队内追加任务。

### 13.9 发布兼容、开关与回退未定义（上线前必须）

增加 mode 会同时改变前端事件、worker 帧及上下文载荷契约。旧浏览器/worker可能忽略字段，因此需要声明受支持能力及载荷版本，接纳前验证；不兼容的 team 请求明确拒绝，禁止悄悄执行 single。

团队开关关闭后拒绝新 team，但已生成团队历史和跨模式读取适配仍需保留，确保用户可用 single 继续。旧版本若只理解 single 原生载荷不能直接回退处理混合会话；须先验证兼容桥接或阻止不兼容读取，并准备受控备份恢复，不能以“缓存可丢”掩盖存储不兼容。

旧会话无历史 manifest 时按可证实来源迁移并声明完整度，不能把缺少档案标成“没有历史”。上线需验证 provider 消息格式、实际沙箱及受控目录读取，不只测试一个模型替身。

### 13.10 全队预算及数据压力需要硬约束（上线前必须）

预算以产品 Run 为单位，包含 coordinator、全部成员、重试、压缩/总结及收尾；按调用身份记录用量，缺失时标记 incomplete。设置并发成员上限、总截止时间和收尾预留，不能简单把 single 上限乘以人数；不同研究还需用户/全局容量限制。

SSE/轨迹队列、历史读取页长、归档大小和成员报告体积有上限；输出洪峰不能阻塞 stop/approve，慢浏览器不能拖住队伍。超限显式呈现部分/失败状态，日志和诊断不复制完整私有上下文到浏览器。指标记录来源选择、适配版本、输入采用、压缩理由、历史读取失败、归档/提交失败及清理耗时，不能仅记录 token。

### 13.11 优先级与范围收口

M0 必须冻结六类契约：**原文归档、输入采用与约束、幂等转换、历史读取、提交恢复、入口配置**。随后按 M1/M2 实现角色业务隔离及 Web 通道，兼容与预算作为发布硬门。新增 C13—C22 对应本次查漏，现共 22 类验收；原 C01—C12 不取消。

可以后置：任意工作流市场、跨轮存活团队、成员直接与用户聊天、可编辑拓扑、独立 reporter、专门的 KV 优化与通用跨研究历史 broker。不能后置：团队同模式续接、早期证据读取、重要约束更新、停止后的未处理输入、账户权限、全队停止、全队用量与旧历史兼容。

本轮判断不改变用户已确认的上下文标准，也不重新推荐固定主 Agent。仍需先做最小往返与故障验证，再据真实工作量估算实施成本；本次审查不代表遗漏已在代码中修复，也不保证穷尽所有实现风险。
