| 项 | 内容 |
|---|---|

| 关联 | [修复报告](web-runtime-trace-repair-report.md)、[已执行审核记录](web-storage-chain-audit.md)、[任务状态](../../.scratch/web-runtime-trace-hardening/spec.md) |

本文取代此前“先新建 PostgreSQL、持久卷、端口和整套前后端才能验证”的通用前提。
**先确认并复用现有环境；按具体测试影响范围隔离。** 创建新目录或容器属于测试安排，
不代表正式存储迁移已经执行，也不要求把本机部署改成 Docker 部署。

## 1. 回查发现与纠正

| 原方案遗漏 / 不准确之处 | 纠正 |
|---|---|
| 只查看 Docker，没有核实本机 Web 服务 | 8000 API 与 5173 页面已被只读识别；进一步核验进程、工作目录、启动方式和实际配置 |
| 将包存在、磁盘空间足够称为执行就绪 | 区分基础设施可用、配置已核实、真实冒烟通过、恢复通过四个状态 |
| 所有测试默认新建整套环境 | 只读与正常流程优先现有服务；第二个 API 才配独立测试库；实例级故障才拆 PG 实例 |
| 新端口被当成充分隔离 | 新端口不隔离数据库/文件；第二 API 连接原业务库存在启动恢复误标活跃 Run 的风险 |
| PG 16 文档、PG 15/18 镜像和正在使用的库混为一谈 | 实际连接的服务版本、库、schema、扩展与迁移版本为准；本轮不顺带升级 PostgreSQL |
| 现有代码等同于现有进程加载的代码 | 记录进程身份、启动时点、解释器、工作目录和代码指纹；不能仅凭 OpenAPI 标题认定版本相同 |
| 未完整考虑 pytest / 配置缓存 / 子进程 | 独立 PG 集成入口绕开 SQLite 自动夹具；进程启动前设定配置，核对 parent/worker 相同落点 |
| 只设置测试模型 URL，忽略默认连接与回退 | 检查用户模型配置覆盖、worker 读取 .env 及 fallback；本地模型阶段限制出口，不能落回真实供应商 |
| 新前端可能仍代理旧 API | 核实 VITE_API_PROXY/反代和真实浏览器请求地址；保留现有前端配置 |
| 未定义测试账号、Run 与文件的登记/清理 | 每次执行有唯一批次、账号/会话/Run/文件清单；只清理登记对象，证据先保存 |
| 迁移目标写成固定用户名路径，并把所有缺陷列成迁移前提 | 由实际服务身份决定稳定目标；按迁移相关缺口设门槛，模型快照等可并行推进 |
| 失败断言都被表述成已确认生产缺陷 | 分别记录契约差距、隔离复现、现环境复现和部署影响；目标契约须先确认适用性 |

以下是上一轮准备检查的观测快照，实际执行当天需刷新；本轮没有重新启动或改变这些服务。

只读核验时建立“浏览器 → API 进程 → 实际业务库/schema → Run 根 → worker → 文件”的对应表。
记录代码/镜像摘要、schema 版本、服务版本和路径；凭据、JWT、完整环境变量、用户正文不进入台账。

数据库可用只读连接核验 current_database、current_user、server_version、
扩展及 Alembic revision，无需先启动一套新数据库。先确认连接身份与目标，
不要仅凭容器名称选择库。按最小范围查询系统元数据，不扫描用户消息/轨迹正文。

## 3. 按测试内容选择环境

| 阶段 | 使用方式 | 数据与端口 | 允许的验证 |
|---|---|---|---|
| E0 现状核验 | 复用现有 API、前端、数据库服务 | 保留现有端口/目录 | 配置、进程、schema/版本、路径/权限/挂载、只读接口 |
| E1 正常流程 | 默认复用现有 Web 与其数据库 | 两个专用测试账号，各自创建测试会话/Run；文件由该服务正常分配 | 提交、上传、正常工具执行、轨迹/下载、会话刷新、测试 Run 的停止/回滚、正常重连 |
| E2 可控失败/回归 | 需要启动改动版或第二 API 时，复用同一 PG 实例的**独立测试数据库和受限角色** | 独立数据根；额外 API 端口；仅需要浏览器覆盖时另开前端 | 约束/并发、服务自身重启、断线时序、测试目录迁移；不得影响共享 PG 其他库 |
| E3 实例/存储故障 | 仅这些场景新建独立 PG 实例、卷或受控文件系统 | 独立端口及挂载，与目标版本/部署方式匹配 | PG 重启/断连、磁盘满、卷丢失、容器重建、数据库恢复、升级与回退故障 |
| E4 正式切换 | 在真实使用的原部署中实施经验证的 F01 方案 | 原数据库实例可继续使用，按清单迁移文件与更新引用 | 备份、排空或明确停止、校验、切换、恢复写入、回退验证；不自动清空旧目录 |

E1 的“测试账号隔离”只是数据识别，不是资源或安全隔离。先完成 E0，确认活跃任务和资源余量，
并发从 1 开始。仅使用合成输入，不借真实业务会话复现 F08，不在共享目录构造 F17 越界链接，
不修改共享默认模型、运行根或全局环境。若当前权限/模型配置不能为测试账号单独设置，则相关用例移到 E2。

页面刷新或断开某个测试浏览器连接可以在 E1；杀 API、修改挂载、重启共享 PG 不属于 E1。
备份恢复到同一 PG 实例的独立库适合逻辑恢复；验证实例崩溃与物理卷恢复必须放到 E3。

## 4. 启动与配置需要满足的条件

### 第二个 API 不能共用原业务库

[app.py](../../server/app.py) 启动会执行恢复；
[orchestrator.py](../../server/orchestrator.py) 按数据库查全部 queued/running Run，
仅排除当前进程内的 handles。第二个进程看不到原进程 handles，可能将其活跃 Run 标记失败/停止。

因此 E2 必须在启动之前确认独立 DB/角色和独立数据根，不能“先启动再改配置”，
也不能只换端口、只加测试账号或只设不同 session_id。没有验证完整 schema 隔离前，默认选独立数据库，
不把同库不同 schema 当作等价方案。E2 的测试角色不拥有业务库的读写权限。

同时核实原部署的 uvicorn worker 数、副本数及滚动重启方式；同端口多 worker 也有同一风险，
不能只防范“新端口”。跨进程恢复协议未修复前，验证部署保持单 API 进程；不擅自改变现有服务拓扑。

### 父进程与 worker 的配置必须一致

- [config.py](../../server/config.py) 的 get_config 有缓存且加载仓库 .env；
  [worker.py](../../server/worker.py) 另行加载 .env。修改测试进程内的 cfg 对象不能保证子进程继承。
- 启动前设置 SERVER_DATABASE_URL、SERVER_RUNS_ROOT、SERVER_UPLOADS_ROOT、
  服务密钥、模型/工具配置及运行时限；按真实代码路径核对优先级和必要参数，不打印秘密值。
- E2 的合成凭据与模型配置独立创建；若为恢复演练，另按受控流程提供解密备份所需密钥。
  修改 master_key 不能当成恢复已加密数据的方法。
- 本地模型阶段验证实际有效模型端点与请求计数，确认用户默认连接未覆盖预期；
  限制该测试 worker 的出口到允许服务。必要时提供只含合成配置的测试源码副本/启动配置，
  不能靠删除现有 .env 解决隔离，也不能把运行数据复制进源码副本。
- 新服务仅监听需要的本地地址，先检查端口空闲。VITE_API_PROXY 在前端启动时明确指向测试 API；
  验收通过浏览器真实网络请求确认，而不是只看启动日志。跨 Windows/WSL/容器时明确 localhost 所属环境。

环境准备还须覆盖以下边界：

- 在原 WSL/Linux 执行环境核对解释器、uv/Node 的实际路径及锁文件；依赖不足才按仓库约定用 uv 补齐，
  不为测试擅自更新共享虚拟环境或锁文件。先做不调用模型的导入检查，再做真实 worker 冒烟。
- 独立测试库先确认身份、再执行所需 Alembic 迁移并核对 revision；与原库版本不符时记录差异，
  不在应用启动后才发现连错库。核验角色授权与连接目标，不以“新建角色”代替权限验证。
- 浏览器采用独立测试配置文件/上下文，核验认证、CORS 和 SSE；cookie 不按端口隔离，
  只换端口可能仍携带原会话。测试密钥、账号与令牌不能混用，令牌不进入日志或命令行。
- 核验实际工具准入和执行身份。独立 Run 根不等于 native shell/file 工具拥有 OS 隔离；
  E1 只运行明确无外部写入的工具场景，攻击/越界与宿主文件变更用例移至受限的 E2/E3。
- 故障域需实际限制资源：磁盘满在有配额的临时文件系统内注入，不能填满共享宿主磁盘；
  新容器仍共享宿主资源，须设置用量上限，不能把容器名称不同当作完全隔离。

### 测试不能悄悄降级到另一条链路

[tests/conftest.py](../../tests/conftest.py) 自动切换 SQLite，
[run_audit.py](../../.scratch/web-runtime-trace-hardening/audit/run_audit.py) 禁止网络和子进程。
它们保留用于原隔离检查，不通过关闭其保护来连接现有业务库。

E2/E3 使用单独、显式选定的集成入口：实际 DB dialect 必须是 postgresql，库名/角色/Run 根
与本次登记一致，配置不符立即停止。PG 驱动缺失、mock 请求数为零、worker 未生成、落点错误均算未通过，
不能自动回退 SQLite、本地文本替身、真实默认模型或另一个目录。
从真实 API 发起 Run，核对实际子进程、轨迹文件与数据库行，不手工插入终态冒充完成。

## 5. 数据登记、版本一致性与退出

每批登记测试账号、会话、Run ID、文件清单/校验值、所用端口/进程/测试库与执行命令。
敏感令牌只用于本次执行，不写入报告。两个测试账号均由本次创建，F08 跨用户检查只针对它们。
合成资金/成本只用于这些测试身份，明确标记为测试数据；不能写入真实用户的已确认业务事实，
也不能据此宣称真实用户资金或买入价已核实。真实业务仍须由用户明确回答并确认事实来源。

记录当前部署与待修复代码的区别：已有服务可能运行旧代码或自动 reload；测试过程中不能
一边修改它的工作区一边把结果算作固定基线。现有服务身份/源码无法可靠核实时，标为未知；
验证修改版改在 E2，保留两套版本的证据，不以强制重启旧服务取得确定性。

模拟模型先覆盖可控时序及工具协议，再用实际供应商验证返回格式差异。
后者记录模型、连接来源、用量边界与实际调用数；仅凭本地 mock 通过不能宣称供应商兼容。
改换数据库版本、部署方式或安全策略时，要作为差异记录，不能混入存储迁移的验证结果。

异常退出先终止本批拥有的测试 Run/子进程与连接，保留必要脱敏证据；只按登记清单清理本批资源。
不按模糊名称杀进程，不删除整个 server/runs，不删除被其他环境使用的卷。
现有软删除不足以完整清理时，登记残留并由受控清理处理，不能临时直删关系表绕过约束。

## 6. 目录整改与环境复用的关系

F01 的目标仍是源码树之外的长期运行数据目录；复用现有 API/数据库不等于继续保留不合理文件位置。

- 先核实当前服务运行模式和实际身份。交互式 WSL 可采用 XDG 用户数据目录；
  系统服务应显式配置稳定服务数据目录，不能固定写成 administrator 的 home，
  也不能因服务账号不同而静默改变数据落点。
- Docker 目标路径与命名卷按 F01 修复；当前使用本机服务时，先验证本机迁移，
  不为完成该项强制容器化。Docker 打包检查保留为对应交付的验收。
- 迁移前必须具备实际旧路径/引用清单、可恢复备份、可信目标、停写边界、历史读取和回退方案。
  diff/base、manifest、outputs_baseline、messages.spool 等纳入清单；不得只迁 JSONL。
- F15/F17/F18 中影响迁移的恢复、路径和索引问题须处理或给出已验证的兼容方案。
  不把 F20 模型快照、全部前端改进或所有 21 项修复一律设成目录迁移前置。
- 无 schema 改动时不额外做数据库升级；需要引用/结构更新时单独执行已验收的迁移步骤。
  不在现有业务库上试跑 create_all/Alembic 来确认它是不是测试库。
- 回退覆盖切换后新生成的 Run 和文件，不能只改回环境变量。旧数据清理另有验收，不随切换自动删除。

## 7. 执行门槛与当前结论

| 进入阶段 | 必需证据 | 当前判断 |
|---|---|---|
| E0 | 可访问服务与只读核验入口 | 可执行；端点身份已观测，完整环境映射待完成 |
| E1 | E0 映射、测试账号/范围、模型来源、资源余量和清理清单 | 尚未验收这些前提；不能把 API 200 当作冒烟通过 |
| E2 | 独立测试库/角色、父子配置一致、新服务就绪、真实 PG/worker 证据 | 基础条件可用，集成入口与测试服务尚未组装验证 |
| E3 | 对应版本的独立故障域、合成/受控恢复集、终止及清理方式 | 尚未建立，不影响先做 E0/E1 |
| E4 | 迁移相关修复及恢复演练通过，原部署切换清单已核验 | 未达到；本轮只纠正方案 |

“没有外部硬阻塞”与“已可直接运行现有命令完成验收”是两回事。
当前可以推进 E0，再按门槛开展 E1；只为具体场景准备 E2/E3。无需先复制完整环境，
也不因 E3 未准备就停下现状核验。既有授权范围内的只读、准备和可逆验证继续执行，
不增加每个步骤都要求用户确认的流程。

## 8. 证据如何更新修复结论

每个用例记录：F 编号、期望契约、使用阶段/实际部署差异、调用路径、实际结果和证据定位。
区分四类：源码事实；隔离复现；现有环境/真实链路复现；待建设或需确认的目标契约。
同一项可以同时拥有多个等级，不能以失败断言数直接计算生产事故数。

F19 的隔离测试证明 healthz 没有存储就绪信号，并没有断开真实数据库；
是否需独立 readiness 端点由既有 T8 契约落实。正常记录缺失/未知状态等增强项，
须先明确产品验收定义，再作为修复门槛。修复后复跑原触发场景，不能只以“换了路径”、
“建了容器”或“测试未报错”关闭任务。
