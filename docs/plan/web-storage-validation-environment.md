### 2.2 2026-09-30 E1 执行结果（复用现有服务与业务库）

批次、账号、Run 与清理清单见[批次登记](../../.scratch/web-runtime-trace-hardening/audit/e1-batch-registry.json)。
两个专用测试账号各自建立指向**本地 mock**（`127.0.0.1:8899`）的默认模型配置，全部模型调用落在 loopback，
未触达真实供应商；未复用任何真实业务会话，并发为 1。

**已通过**：提交（202 + UUID）、worker 子进程启动与轨迹写入、`/trace` 回放、会话消息回填与读取
（`/api/sessions/{id}/turns`）、上传落盘到 `inputs/`、协作式停止（`stopped` / `user_stop`）、
前端 dev server 与 `/api` 代理链路。

**真实链路新复现的问题**（详见批次登记 evidence）：

| 现象 | 说明 |
|---|---|
| 纯文本正常结束被记为 `stopped` | `no_tool_behavior="stop"` → `stopped_by=no_tool` → `status=stopped`；会话中该回答被加上 `_[partial: no_tool]_` |
| `usage_json` 与 token 计数不落账 | 轨迹中已有 `usage`，独立复算聚合正常，但入账被跳过 |
| `started_at` 始终为空 | 本批所有 Run 均无 `started_at`（F20 症状） |
| `llm_snapshot_json` 全库为 JSON `null` | 1263 条运行全部如此，非本批个别 |
| 运行结束后 SSE 无终态事件 | 迟订阅只得 `run_started`/工具事件/`assistant_delta`，无终止帧（F09 症状） |

**本机（Windows 原生）环境级阻断**：该解释器没有 `os.getpgid` / `os.killpg`，
`Orchestrator._kill_handle` 抛 `AttributeError`（不被 `contextlib.suppress(ProcessLookupError)` 覆盖），导致
`_record_artifacts` / `_record_usage` / `_release_slot` 被跳过、会话 drain 任务终止、**worker 池每运行泄漏一个槽位**；
`CurrentSandbox` 的同类回收路径也失败，**shell 工具（bash / create_file / read_file / grep / glob）在本机全部不可用**。
后果：连续 2 次运行后池耗尽，任何新 Run 只能停留在 `queued`；运行无法产生 `/outputs` 文件，
产物索引、下载与回滚类用例在本机**不可验收**。本批通过重启 API 进程收口（orphan reconcile 将残留置为 `failed`）。

**结论**：E1 的提交/轨迹/会话/停止/前端链路可用；工具执行与产物类用例必须在 POSIX 环境（WSL 或容器）
复验，不能以本机结果代替。修复该跨平台缺陷前，本机部署无法产出交付物，且每两次运行即需重启。

**本批处置（2026-09-30）**：测试账号、会话、Run 与运行目录，以及 mock 与前端进程**保留**待后续复验。
待办项：产物索引/下载/diff/回滚（需 POSIX 环境）、浏览器 DOM 层验收（F10/F11，需浏览器自动化或人工复核）、
F08 跨用户越权动态复验（账号 B 已就绪）、真实供应商返回格式差异（需另行批准）。明细见批次登记 `deferred`。
注意：本批结束后 API 仍有 1 个泄漏槽位，再运行一次即需重启进程。

## 4. 启动与配置需要满足的条件

### 第二个 API 不能共用原业务库

[app.py](../../server/app.py) 启动会执行恢复；
[orchestrator.py](../../server/orchestrator.py) 按数据库查全部 queued/running Run，
仅排除当前进程内的 handles。第二个进程看不到原进程 handles，可能将其活跃 Run 标记失败/停止。

因此 E2 必须在启动之前确认独立 DB/角色和独立数据根，不能“先启动再改配置”，
也不能只换端口、只加测试账号或只设不同 session_id。没有验证完整 schema 隔离前，默认选独立数据库，
不把同库不同 schema 当作等价方案。E2 的测试角色不拥有业务库的读写权限。

同时核实原部署的 uvicorn worker 数、副本数及滚动重启方式；同端口多 worker 也有同一风险，
不能只防范“新端口”。跨进程恢复协议未修复前，验证部署保持单 API 进程；不擅自改变现有服务拓扑。

### 父进程与 worker 的配置必须一致

- [config.py](../../server/config.py) 的 get_config 有缓存且加载仓库 .env；
  [worker.py](../../server/worker.py) 另行加载 .env。修改测试进程内的 cfg 对象不能保证子进程继承。
- 启动前设置 SERVER_DATABASE_URL、SERVER_RUNS_ROOT、SERVER_UPLOADS_ROOT、
  服务密钥、模型/工具配置及运行时限；按真实代码路径核对优先级和必要参数，不打印秘密值。
- E2 的合成凭据与模型配置独立创建；若为恢复演练，另按受控流程提供解密备份所需密钥。
  修改 master_key 不能当成恢复已加密数据的方法。
- 本地模型阶段验证实际有效模型端点与请求计数，确认用户默认连接未覆盖预期；
  限制该测试 worker 的出口到允许服务。必要时提供只含合成配置的测试源码副本/启动配置，
  不能靠删除现有 .env 解决隔离，也不能把运行数据复制进源码副本。
- 新服务仅监听需要的本地地址，先检查端口空闲。VITE_API_PROXY 在前端启动时明确指向测试 API；
  验收通过浏览器真实网络请求确认，而不是只看启动日志。跨 Windows/WSL/容器时明确 localhost 所属环境。

环境准备还须覆盖以下边界：

- 在原 WSL/Linux 执行环境核对解释器、uv/Node 的实际路径及锁文件；依赖不足才按仓库约定用 uv 补齐，
  不为测试擅自更新共享虚拟环境或锁文件。先做不调用模型的导入检查，再做真实 worker 冒烟。
- 独立测试库先确认身份、再执行所需 Alembic 迁移并核对 revision；与原库版本不符时记录差异，
  不在应用启动后才发现连错库。核验角色授权与连接目标，不以“新建角色”代替权限验证。
- 浏览器采用独立测试配置文件/上下文，核验认证、CORS 和 SSE；cookie 不按端口隔离，
  只换端口可能仍携带原会话。测试密钥、账号与令牌不能混用，令牌不进入日志或命令行。
- 核验实际工具准入和执行身份。独立 Run 根不等于 native shell/file 工具拥有 OS 隔离；
  E1 只运行明确无外部写入的工具场景，攻击/越界与宿主文件变更用例移至受限的 E2/E3。
- 故障域需实际限制资源：磁盘满在有配额的临时文件系统内注入，不能填满共享宿主磁盘；
  新容器仍共享宿主资源，须设置用量上限，不能把容器名称不同当作完全隔离。

### 测试不能悄悄降级到另一条链路

[tests/conftest.py](../../tests/conftest.py) 自动切换 SQLite，
[run_audit.py](../../.scratch/web-runtime-trace-hardening/audit/run_audit.py) 禁止网络和子进程。
它们保留用于原隔离检查，不通过关闭其保护来连接现有业务库。

E2/E3 使用单独、显式选定的集成入口：实际 DB dialect 必须是 postgresql，库名/角色/Run 根
与本次登记一致，配置不符立即停止。PG 驱动缺失、mock 请求数为零、worker 未生成、落点错误均算未通过，
不能自动回退 SQLite、本地文本替身、真实默认模型或另一个目录。
从真实 API 发起 Run，核对实际子进程、轨迹文件与数据库行，不手工插入终态冒充完成。

## 5. 数据登记、版本一致性与退出

每批登记测试账号、会话、Run ID、文件清单/校验值、所用端口/进程/测试库与执行命令。
敏感令牌只用于本次执行，不写入报告。两个测试账号均由本次创建，F08 跨用户检查只针对它们。
合成资金/成本只用于这些测试身份，明确标记为测试数据；不能写入真实用户的已确认业务事实，
也不能据此宣称真实用户资金或买入价已核实。真实业务仍须由用户明确回答并确认事实来源。

记录当前部署与待修复代码的区别：已有服务可能运行旧代码或自动 reload；测试过程中不能
一边修改它的工作区一边把结果算作固定基线。现有服务身份/源码无法可靠核实时，标为未知；
验证修改版改在 E2，保留两套版本的证据，不以强制重启旧服务取得确定性。

模拟模型先覆盖可控时序及工具协议，再用实际供应商验证返回格式差异。
后者记录模型、连接来源、用量边界与实际调用数；仅凭本地 mock 通过不能宣称供应商兼容。
改换数据库版本、部署方式或安全策略时，要作为差异记录，不能混入存储迁移的验证结果。

异常退出先终止本批拥有的测试 Run/子进程与连接，保留必要脱敏证据；只按登记清单清理本批资源。
不按模糊名称杀进程，不删除整个 server/runs，不删除被其他环境使用的卷。
现有软删除不足以完整清理时，登记残留并由受控清理处理，不能临时直删关系表绕过约束。

## 6. 目录整改与环境复用的关系

F01 的目标仍是源码树之外的长期运行数据目录；复用现有 API/数据库不等于继续保留不合理文件位置。

- 先核实当前服务运行模式和实际身份。交互式 WSL 可采用 XDG 用户数据目录；
  系统服务应显式配置稳定服务数据目录，不能固定写成 administrator 的 home，
  也不能因服务账号不同而静默改变数据落点。
- Docker 目标路径与命名卷按 F01 修复；当前使用本机服务时，先验证本机迁移，
  不为完成该项强制容器化。Docker 打包检查保留为对应交付的验收。
- 迁移前必须具备实际旧路径/引用清单、可恢复备份、可信目标、停写边界、历史读取和回退方案。
  diff/base、manifest、outputs_baseline、messages.spool 等纳入清单；不得只迁 JSONL。
- F15/F17/F18 中影响迁移的恢复、路径和索引问题须处理或给出已验证的兼容方案。
  不把 F20 模型快照、全部前端改进或所有 21 项修复一律设成目录迁移前置。
- 无 schema 改动时不额外做数据库升级；需要引用/结构更新时单独执行已验收的迁移步骤。
  不在现有业务库上试跑 create_all/Alembic 来确认它是不是测试库。
- 回退覆盖切换后新生成的 Run 和文件，不能只改回环境变量。旧数据清理另有验收，不随切换自动删除。
