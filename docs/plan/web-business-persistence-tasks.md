| 项 | 内容 |
|---|---|

“数据持久化”包含保证数据实际进入分析的服务端链路，不只建表。业务数据沿用现有 PostgreSQL
业务库，与语料库分开；运行轨迹和文件继续由既有受控文件存储承担，数据库保存关联和索引。

本文任务编号用于拆分设计。进入实施时按[任务规范](../agents/issue-tracker.md)为每项分别建立 issue，
仅 issue 维护执行状态；本文不增设产品进度真源，不实施迁移，不修改既有排期。
页面任务负责展示与操作，所有者、真实性状态、版本、幂等和预算必须由服务端强制执行。

## 2. 环境与共同接口

### DATA-00 实际环境与验证入口

**需求**：PR-BIZ-04/06；衔接[环境准备](web-storage-validation-environment.md)。

- 核实 API 进程、加载代码、解释器、实际 PostgreSQL 库/版本/schema、Run 根和前端代理；既有观测须刷新。
- 只读/正常测试先复用现有服务；改动版第二 API 使用同 PG 实例独立测试库、受限角色、数据根和按需端口。
- 检查启动孤儿恢复、多 worker/副本与共享库风险；不能新开端口后仍连接原业务库。
- 建立显式 PG 集成入口，防止自动测试夹具切回 SQLite；父子进程配置、模型来源、端口、测试身份均登记。
- 实例/卷故障才另设独立故障环境；不顺带升级 PG，不修改真实用户资金或持仓。
- 记录备份与清理清单；任何阶段的 readiness 都不能只用 healthz 200 证明。
- 复用当前已实现的 /readyz 和目录整改，核验运行服务是否部署对应代码；历史 E0/E1 观测不是当日就绪证据。
- 在 B/C 启用前登记后台 dispatcher/monitor 的启动、退出、自动重启、租约心跳及健康信号；
  可先以单 API 加受管理后台进程部署，无需先引入 Redis/Kafka，也不能只挂在浏览器或请求协程中。

**验收**：环境对应表、版本/路径清单与可执行验证入口齐备；配置不符立即失败，无静默回退。

### DATA-01 共用数据与操作契约

**需求**：PR-BIZ-01—05、PR-DATA-13、PR-WATCH-01—04；PRD §3、§8。

向 UI 和 Agent 工具提供同一份协议，字段/API 路径在此阶段确定，不把 PRD 建议路径当现成接口：

| 契约 | 必须明确的内容 |
|---|---|
| 数值与来源 | 十进制字符串、币种/单位、资产精度、业务时点、记录时间、来源及明确/待澄清状态 |
| 对象读写 | owner 由认证绑定；对象/版本标识、expected_revision、归档状态、前值与变更回执 |
| 幂等与错误 | 同键同内容返回原结果，同键不同内容拒绝；字段定位、冲突、不可用、限额与可重试条件 |
| 分析提交 | JSON/multipart 共用 investment_input；仅保存不建 Run；保存并分析返回原子提交结果和 Run/派发状态 |
| 快照与补数 | 不可变快照、请求状态、回答记录、来源/后续 Run 关联、必要字段准入 |
| 监控与通知 | 规则版本、触发方式、创建/恢复策略、冷却/布防、事件/Run 关系、游标与已读状态 |

状态分属业务对象、监控规则、触发事件、派发任务与 Run，不能将“已触发”“分析成功”合并成一个标志。
定义用途→必需字段/允许计划或实际值→可调用计算工具的服务端规则；客户端和模型不能自行降低要求。
区分未提交的内存草稿与用户主动提交的持久待补记录。版本、草稿、回答和审计不得把不明确值晋升为有效事实。
补齐列表/历史分页、操作结果查询、游标全量同步边界，以及旧 JSON/multipart 客户端的兼容/明确拒绝策略。
业务数据必须精确读取；“是否为用户真实表达”的语义理解仍可能出错，来源校验与歧义暂停是约束，
不承诺服务端能验证现实真伪或可靠识别所有谎言。
现有 RunRequest 不含 investment_input，multipart 分支也未解析它；新业务字段不得被旧解析器静默忽略。
明确业务子结构未知字段/假设覆盖的拒绝结果，同时保留不需要业务资料的旧研究请求。
形成与现有 Run 状态的映射；input_required 先作为明确结束原因，不宣称已有原 worker 暂停恢复。
服务端时间统一存储并在 UI 本地化，区分业务时点、行情观测/接收时间及分析开始时间。

**验收**：提供有效/缺失/歧义/冲突/超时重试/无权的协议样例；未定默认值有明确冻结门槛。

**当前产物（2026-10-02）**：冻结草案见[共用数据与操作契约](../design/web-business-data-contract.md)
v0.1；环境台账与验证入口见[环境基线](web-business-data-env-baseline.md)（DATA-00）。
两者均为设计与核定成果，不代表服务端已实现。

## 3. 业务数据与分析链路

### DATA-02 业务模型与迁移

**需求**：PR-DATA-13、PR-BIZ-01/04；PRD §3、§5.2。

- 建立独立账户、研究所属计划及不可变版本，持仓快照、成交更正链、研究到账户引用、
  独立策略版本与来源引用；计划必须且只能有一个所属研究。
- 金额/价格/数量采用适合资产范围的精确数值；定义比例单位与盈亏比口径，计算值保留公式版本及输入引用。
- 缺失与零分开；计划与实际成交分开；手工持仓和成交不重复累加，多币种不隐式换算。
- 通过外键、唯一约束及服务校验保障对象归属与关系；同一账户可被多个研究引用，
  计划不能跨研究关联或共享；版本不能原地覆盖。
- Alembic 覆盖空库与现有库升级，核验历史行兼容、锁影响与回退/前滚策略；不把旧聊天批量转换为已确认事实。

**验收**：真实 PG 验证精度往返、约束、版本不可变与迁移；当前生产库不用于试跑迁移。
覆盖 AC-01、03、04、09、22、26。

`InvestmentPlan(+Revision)`、`PositionSnapshot`、`TradeRecord`、`ResearchInvestmentLink`、
`StrategyVersion`），迁移见 `server/alembic/versions/0005_business_objects.py`；
真 PG 验收见 `tests/pg/test_business_models.py`（11 项通过，证据与批次见
[环境基线](web-business-data-env-baseline.md) §4.1）。写入服务、准入与幂等仍属 DATA-03。

### DATA-03 统一写入与真实资料准入

**需求**：PR-BIZ-02/04；PRD §3.4、§4.3、§5.3。

- 表单 API、Agent 操作工具使用同一服务；owner 从认证取得，模型不能指定其他用户身份。
- 保存业务变更、版本、审计和幂等结果；使用 expected_revision 防止覆盖并发修改。
- 用户明确资料直接保存，不重复确认；假设、估计、疑问候选仅保留草稿/回答记录，不进入有效计算字段。
- 账户/口径不明必须澄清；附件、历史抽取、模型建议不直接写实际资金/成本。
- 不确定更正保留旧版并标记受影响用途待澄清，不能默默使用旧值完成本轮计算。
- 补偿版本实现业务撤销；同键重试不重复写版本，相同键不同内容明确拒绝。
- 保存可查询的操作记录，明确幂等键的用户/操作作用域、请求摘要、保留期与过期处置；
  服务端返回 operation_id，客户端丢键后能查询自己的最近操作。重试期限内不能因清理记录再次执行原动作。
- 聊天命令绑定原用户消息、目标对象和允许修改字段；不能信任模型传来的“已确认”布尔值，
  也不能将附件指令或外部文本当用户修改授权。未解决歧义需形成可查询阻断状态。

**验收**：表单、聊天、JSON/multipart 均无法绕过；语义不以问号/关键词替代。
覆盖 AC-02、04、05、22、25—28。

**当前产物（2026-10-02）**：写入服务见 `server/business_service.py`（错误码信封、真实输入准入
`admit_group`、用途裁决 `evaluate_purpose`、版本只追加、`expected_revision` 冲突、幂等键与
操作查询），幂等台账见 `server/store.py::BusinessOperation` 与迁移
`server/alembic/versions/0006_business_operations.py`；真 PG 验收见
`tests/pg/test_business_write.py`（13 项）；HTTP 路由见 `server/routes/business.py`
（错误信封处理器注册在 `server/app.py`），路由契约验收见 `tests/pg/test_business_routes.py`
（9 项，随同 DATA-02/03 共 33 项通过，证据与回归对比见

### DATA-04 查询、关联与历史

**需求**：PR-BIZ-01/04、PR-DATA-13；PRD §3.1、§8。

- 提供独立账户及其研究引用列表、按研究归属的计划/持仓/成交/策略列表、详情和版本历史。
- 第一版一个研究至多引用一个账户，同一账户可被多个研究引用；一个研究可拥有多个计划，
  每个计划只属于一个研究。一个 Run 只采用该研究的一个账户和一个计划。
- 当前主计划只能从该研究所属计划中选择；跨研究使用相同意图时创建新的计划对象并保留来源，
  不复用或重新关联原计划。
- 查询按认证归属过滤；无权与不存在不泄漏区别；归档对象不能成为新分析有效选择。
- 保存返回服务端实际版本；避免从浏览器或聊天摘要恢复业务真源。

**验收**：跨刷新、登录、研究绑定一致；双用户直接请求任意对象/版本 ID 均受控。
覆盖 AC-01、03、09。

### DATA-05 Run 快照与重算

**需求**：PR-DATA-13、PR-BIZ-02/04/05；PRD §4.4、§6。

- 保存 schema 版本、对象版本、完整解析有效值、必要字段来源与明确状态；只引用 ID 不算快照。
- 手动 Run 在提交时冻结；排队/执行中资料变化不修改快照。旧非业务 Run 无快照须明确标记，不用当前值回填伪造。
- 保存并分析前完成必要字段校验；不支持假设覆盖。未成交可做支持的计划分析，但不得执行依赖实际成本的计算。
- 重算关联新旧 Run、使用新快照，并通过调度保证停止旧执行后的同研究串行；排队任务采用取消重提。
- 快照查询按 Run 所有者授权，历史报告继续读取旧版本。
- 校验账户引用、计划所属研究、持仓版本与 Run 研究的一致性，并在同一事务读取/冻结；
  拒绝采用其他研究的计划或混用不同账户资料。
- 模型配置快照与业务快照分开。按 F20 剩余工作确定提交配置与实际执行配置的版本/回退规则，
  保存每次实际尝试的模型身份与用量；凭据失效不能无提示改用其他模型并沿用旧成本预算。

**验收**：A/B 不同时点输入固定；JSON/multipart 同规则；跨 worker 仍使用同一快照。
覆盖 AC-05—07、09、10、26、27。

**当前产物（2026-10-03）**：快照模型 `server/store.py::RunInvestmentSnapshot`
（INSERT-only）与迁移 `server/alembic/versions/0007_run_snapshot.py`；解析/冻结/读取见
`server/investment_snapshot.py`（`schema_version=business-snapshot/1`，保存对象版本、解析后的
完整有效值、来源与缺失项）。提交侧见 `server/routes/runs.py`：`POST /api/runs` 解析
`investment_input`（JSON 与 multipart 同一契约），与 Run 行**同一事务**冻结快照并复用
`run.submit` 幂等键；新增 `GET /api/runs/{id}/investment-snapshot`（缺快照报
`404 snapshot_absent`，不用当前资料回填）与 `POST /api/runs/{id}/rerun`（停止旧执行 +
新 Run + 新快照 + `rerun_of_run_id` 关联）。真 PG 验收见 `tests/pg/test_run_snapshot.py`
（13 项，累计 46 项通过，证据见[环境基线](web-business-data-env-baseline.md) §4.1）。
快照注入 worker/workflow 已由 DATA-08 完成。

### DATA-06 原子提交与持久派发

**需求**：PR-BIZ-04；PRD §5.3—5.4。

- “保存并分析”的业务变更、版本/审计、快照、queued Run 与 outbox 在同一数据库事务提交。
- 新服务使用同一个 SQLAlchemy AsyncSession/事务；现有 create_run、append_turn、ensure_session
  各自提交，不能直接依次调用就宣称原子。拆出不自行 commit 的仓储操作，保留旧入口兼容回归；
  本次用户消息及其顺序/Run 关联也纳入提交契约，派发不得再次追加相同消息。
- 文件上传不属于数据库事务：用受控暂存区、唯一存储名、内容摘要与持久上传清单，
  先完成大小/重名校验，数据库记录发布意图，附件可读且校验通过才允许 worker 领取。
  失败有可重入补偿/孤儿清理，不能回滚 DB 后留下不受管文件，或数据库成功但启动缺文件的分析。
- worker 仅在提交后领取任务；失败回滚不显示完整成功，提交成功但启动失败保留可恢复派发状态。
- 用唯一约束、租约/领取版本和研究级互斥实现重试与串行；租约过期要核定旧 worker 状态，不能仅重新领取就启动第二个执行。
- 派发重试复用原 Run，不重复业务写入；外部调用不确定结果记录尝试并限制重试，不承诺绝对只计费一次。
- 与既有孤儿恢复统一职责，避免内存 handles 扫描把其他存活进程任务错误收尾。
- 明确逐研究排队顺序、停止超时、队列上限及失败终止条件；租约版本随写入和完成回报校验，
  过期 worker 不能覆盖新领取者结果。存在 native 文件副作用时，未确认旧进程停止不得并发重启。

**验收**：事务各边界故障、启动失败、崩溃领取、重复投递及并发派发不丢任务、不重复创建 Run。
覆盖 AC-05、15、23；同研究不并发执行。

**当前产物（2026-10-03）**：outbox 模型 `server/store.py::RunDispatch`（与 Run 状态分离的
`pending/claimed/dispatched/retryable_failed/abandoned`）与迁移
`server/alembic/versions/0008_run_dispatch.py`；领取/租约/回收/取消见
`server/dispatch_outbox.py`（`SKIP LOCKED` 领取、租约 + 领取版本、过期先核定旧 worker
状态再决定重投、失败退避、研究级互斥基于库判定）。提交侧 `server/routes/runs.py`：
业务 Run 的 session/run/turn/快照/附件清单/outbox **同一事务**（不自行提交的
`store.append_turn_in`，`orchestrator.submit(backfill_turn=False)` 保证派发不重复追加
用户消息）；新增 `GET /api/runs/{id}/dispatch`；重算对排队任务执行"取消重提"（outbox
