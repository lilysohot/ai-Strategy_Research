## 1. 希望改善什么

目前 search 的返回体较大，但很多空间用于定位、身份、范围和重复计划。正文片段则可能在组装和预算压缩时被截短。Agent 因此可能既看到很多工具信息，又缺少判断资料是否有用的关键上下文。

本轮主要关注：

- 搜索返回的段落是否能独立理解，是否截掉了条件、原因或数值口径。
- 多块命中是否只展示了第一块，遗漏真正回答问题的部分。
- 返回预算是否花在重复元数据上，挤占了正文。
- fetch 是否取到了当前所需内容，有没有无意义地重复读取。
- 增加搜索正文后，回答是否更准确，整体成本是否合理。

目标不是一律取消 fetch，也不是让 search 返回全文。工具分工可以保留弹性，但已经取得且足够使用的有效内容不应例行重读。

## 2. 当前实现的事实

| 位置 | 当前情况 |
|---|---|
| 原文准备 | 先解析、切块并建立原文映射，供检索和读取共同使用 |
| native search | 本地实现默认最多展示两个互补块、每块 600 字正文预算；优先有界原文段落，长段落回退句窗。保留足够相关的首位块、降低目录干扰；标真实块序、页码与原文字符位置，其余块保留句柄并标数量。最终工具预算仍按整条命中压缩 |
| search 预算压缩 | 已改为按整条命中让位并标 `hits_elided`，不再把 snippet 统一压到 120 字符；原生命中去掉了与 `context_locators` 重复的 `fetch_plan` |
| 多块命中 | 定位数组可包含多个块，展示内容不等于这些块的完整正文 |
| fetch | 按合法句柄回读指定原文，校验身份与范围；内容过长时分页 |
| 本地引用契约 | 原生 search 的 evidence_spans 标记范围在实际送达后可逐字引用；旧 snippet/preview、未标记文本与句内节选仍需补读 |

依据：[search](../../plugins/tools/corpus_search.py)、[native 检索与回读](../../plugins/corpus/retrieval/native_live.py)、[fetch](../../plugins/tools/corpus_fetch.py)。

引用资格依赖原文核验、明确标记与实际送达；仅把 snippet 加长不会自动取得引用资格。

## 3. 优先讨论的改进方向

### 上下文依据与接入位置

上下文依据包括行业、产品、公司、宏观、实物、执行内容、时间和当前讨论对象，以及主体之间的关系、条件与观点归属。各维度可重叠，不要求逐项填满；当前研究命题决定选读重点，不改变原文表达。

先利用章节和相邻原文确定对象、角色、行动状态和时间，必要时试验简短的片段说明参与检索；说明与可引用原文分开。检索后由 search 组装解释命中内容所需的原文，因此上下文感知与 search 优化可以同步迭代，不必等待全库增强完成。

本稿负责内容返回与补读；上下文定义、索引接入、执行阶段和样例验证以 [混合检索方案 §30](corpus-contextual-vector-retrieval-pilot.md#30-面向研究命题的上下文感知与执行安排) 为准，片段上下文的字段、存储与验收见 [§31](corpus-contextual-vector-retrieval-pilot.md#31-片段上下文组织方式第一步口径)，不另设一份上下文任务清单。

### 3.1 围绕命中点选择内容

避免固定展示首块开头。优先定位真正回答问题的句子或段落，从那里组织展示窗口。

例如，问“交付为什么延迟”，应优先展示解释原因的部分。一个命中涉及多个相关块时，可以分别展示关键段落，而不是把其余块都藏在句柄中。无需规定每个块都必须展示，也不预设固定段落数。

### 3.2 尽量保留完整句段和必要上下文

以自然句段作为展示边界，并根据具体内容保留必要解释：

- 数值尽量带上对象、指标、期间和同比/环比口径。
- “上述”“因此”“该业务”等表述，尽量带上可理解的前文。
- 转折、否定、预测、适用条件和观点归属，避免只保留其中一半。
- 比较问题尽量让双方相关内容都可见。

这是一种选择策略，不要求先建立完美的语义依赖图，也不增加一个模型来逐次审批。不能确定时，明确它仍是部分上下文。

### 3.3 先挑完整内容，再控制预算

优先保留少量高相关、可理解的原文单元，减少到字数上限就硬切的情况。装不下的部分可以说明未展示并保留合法读取位置。

较长但关键的段落不能因为占空间就被悄悄跳过；可以保留有用预览并说明需要补读。预算、窗口大小、命中数量作为可调参数，在实际样例中比较，不在讨论阶段固定数值。

### 3.4 减少重复信息，给正文留空间

检查重复的 doc_id、locator、context_locators、fetch_plan 等字段。能够共用身份或由后台保存的重复信息，考虑紧凑表示。

同一位置的重叠文本可以去重。不同位置的段落仍要分别标识，不拼接成看似连续的原话。不能为了减小返回体丢掉 fetch 或现有引用流程需要的身份与范围信息。

### 3.5 让 fetch 补需要的内容

Agent 应能说明当前还需要什么，例如缺期间、另一家公司、适用条件或指代前文。有合法定位就补读对应范围，位置未知则继续检索。

“已经有足够内容就不重复取”保留为原则。无需把每次调用都设计成一张复杂审批表，也不强制固定五项字段或某个枚举。缓存、重复范围和错误恢复等确定性问题由系统协助处理。

内容已经读到但暂未理解、清单字段错误或报告锚点不匹配，通常不需要重新取原文。若工具调用失败，应处理故障，不把相同范围的反复读取当作研究进展。

## 4. search 与 fetch 的两种可选关系

目标是足够且已合法交付的证据直接使用。以下两种方式代表不同实现幅度：改善导航可作为过渡，但不能据此宣称已经实现“足够时无需 fetch”；是否在同一批次接通直接证据，结合局部适配成本决定。

| 方式 | search 的作用 | fetch 的作用 | 本轮考虑 |
|---|---|---|---|
| 改善搜索展示，保留现有引用流程 | 返回更相关、更完整的导航正文与合法位置 | 完成当前契约下的取证及必要补读 | 可以先观察展示改善是否帮助 Agent 选读；尚未取证的内容仍不能直接引用 |
| search 直接交付可引用原文 | 一次返回经过核验并实际送达的完整证据 | 只补缺失内容 | 需要同时适配证据登记和引用校验，不能只改 hint 就启用 |

第一种改动较集中，但 Agent 可能仍要为正式引用读取已经预览过的内容；第二种更接近减少重复交付的目标，但实现范围更大。两者取舍看真实行为、质量和总开销，不单看 fetch 次数。

如果本轮决定采用直接证据交付，相应的账本/引用适配是该选择所需的局部配套，并不意味着同时启动 Claims/items 重整或整个资料库重构。

## 5. 可用样例讨论和验证

不必一开始制定很重的评分体系，可以先拿代表性问题看新旧结果差异：

| 样例 | 观察重点 |
|---|---|
| 查询段落后半部的原因 | 是否仍只展示正文开头 |
| “增长30%”后跟一次性因素说明 | 条件与解释是否一起保留 |
| 同一个命中包含多个正文块 | 关键内容是否只因不是第一块而不可见 |
| 比较两家公司 | 是否只展示其中一家 |
| “上述条件成立时” | 指代是否可以理解；不足时能否准确补读 |
| 多次需要同一证据 | 是否重复取回相同内容 |
| 结果总量较大 | 是正文过多，还是重复定位和诊断占用空间 |
| 没有找到相关材料 | 是否如实表述查询范围，避免说成全库不存在 |

先比较工具返回和回放，再决定是否进行小范围真实 Agent 对照。真实试验应保持问题、来源版本和模型条件可比较，并计入失败和重试。

首要标准是：仅看 search 最终实际返回的内容，能否准确理解并支持当前研究问题；对照必要原文后，是否遗漏会改变理解的信息。完整句子和更多字符均不自动等于足够上下文。已命中但解释缺失，检查组装与补读；未命中关键内容，检查上下文辅助检索、召回与排序；原文未说明时保留不确定性。耗时、token 用量和重复 fetch 作为辅助观察，不预设降幅，不以减少工具调用替代内容目标。

## 6. 暂不纳入本轮

- Claims/items 的重新抽取、发布与数据迁移。
- material_relations 的恢复或重做。
- 三视角团队研究的产品入口与协作接线。
- 为所有来源建立完整语义依赖图。
- 自动修改结构化 store 的启动要求。
- 全库重建索引、扩大 OCR/表格范围。
- 一次性替换全部工具协议或建立新的通用研究框架。

如具体 search/fetch 改动确实依赖其中某项，应先说明原因和最小必要范围，再讨论是否纳入，不能自动扩大任务。

## 7. 下一步讨论顺序

1. 建立片段上下文组织方式：以最新发布清洗内容为依据，用原文与文档结构关联行业、产品、公司、宏观、实物、执行内容、时间和讨论对象，保留必要的关系与条件，字段可追溯到原文（口径见混合检索方案 §31）。
2. 对照真实问题与原文，区分检索没找到、返回时丢失和原文未说明，再判断上下文是否足够（盘点口径见混合检索方案 §31.6）。
3. 同步改善 search 的原文窗口、多块展示及元数据去重，不等待全库上下文完备。
4. 按 search 实际交付的内容衔接 fetch；直接使用证据时配套登记和引用校验。
5. 以内容是否足够为主比较结果，再确定实现细节与启用范围；执行产物见混合检索方案 §30.4。

现有版本、范围、权限和引用规则在实现正式调整前继续有效；这不要求把优化方案写成僵硬流程。展示选择的本地实现进展见页首；其余讨论不表示已经批准某种新协议或开始生产改造。

## 8. 2026-10-24 返回结构精简（兼容版）

用户在正式发布后提出“那么先从返回结构上做优化”，本阶段只调整工具输出适配器
`plugins/tools/corpus_search.py`。上轮检索排序、来源过滤、片段选择与索引冻结继续有效；
102 个原冻结文件中只有该工具适配器变化，其余 101 个哈希不变。

### 已实现

- 原生正常命中的重复 `hint` 从 712 字符缩为 93 字符。固定证据资格、成员映射、
  Unicode 坐标、分页、范围边界规则移至工具定义的模型可见说明（位于 Args 之前）。
  没有有效证据区间的预览结果使用单独提示，明确需 fetch；预算省略时追加省略提示。
- 每条命中先放标题、日期、正文和证据坐标，再放长句柄数组及统计。字段值保持原样，
  原生 JSON 去除键值分隔处的空格；不会改动字符串内部的空白、换行或证据偏移。
- 新增顶层 `delivery.evidence_characters` 与 `delivery.evidence_blocks`，统计实际
  返回消息中可校验的原文字符数、不同证据块数。使用同一证据解码器验证区间和哈希；
  不把标签、句内预览、索引说明或未展示候选算入。块数按 doc_id + locator 去重；
  字符数是展示证据区间长度之和，不代表全文覆盖率或结论充分性。
- 原生结果被预算裁剪后，`count` 等于实际保留的命中数；`hits_total` 与
  `hits_elided` 保留原数量和累计省略数。每次裁剪重算 delivery，不沿用裁剪前统计。
  命中仍按尾部整条省略，不截断正文、证据描述或候选数组。
- `coverage.native.body_characters` / `blocks_returned` 保留原候选范围统计，
  在工具定义中明确其与 delivery 的区别。`title` 仍是首命中块标题，本阶段不
  新增元数据查询或将章节名冒充文档名。

例如工业富联样例新增的字段为：

```json
"delivery": {"evidence_characters": 807, "evidence_blocks": 2}
```

它与候选范围的 7135 字、17 块是不同口径。只剩预览时两项为零，不代表没有资料。

正文、句柄、顺序、区间、哈希和 coverage 逐项相同，差别仅为字段排列、hint、
delivery 和 JSON 分隔空格。引用经真实 PG fetch 和账本 resolver 校验通过。

该阶段取代 §8 的默认原生返回，v1 解码及存储故障时的完整 v1 返回继续支持。

### 模型看到的结构

每条命中保留 `doc_id`、`title`、`published`，正文改为
`excerpts: [{text, ref}]`；`scope_ref` 指向原有完整候选范围，`available_blocks`
给出候选总数。`evidence_contract=native-search-evidence-v2`。句内节选等未获
证据资格的内容单独放入 `preview`，不会被隐式升级为证据。

`evidence_spans`、整组 `context_locators`、`by_kind`、重复 source/build/chunk
字段不再默认交给模型；它们与原 snippet 一起保存在完整收据中。

- 引用：`evidence.doc_id=hit.doc_id`，`evidence.locator=excerpt.ref`，quote 取 text。
- 补读该段所属整块：`corpus_fetch(doc_id, locator=ref, view="compact")`；
  返回规范 native 句柄，分页沿用原 next_cursor，仍需读取全部申请页才能声称完整。
- 选择其他候选：`corpus_inventory(doc_id, scope_ref=scope_ref)`；清单按原范围和
  原顺序展开，通过当前源检查后返回结构，不把后台读取登记为 Agent 已读。

`eref:<receipt-sha256>:<index>` 和 `sref:<receipt-sha256>` 是不可拼接的别名。
不是把原校验信息编码成另一个长 token，而是按内容哈希寻址服务端的完整 JSON
收据。收据绑定目标库、doc_id/build、候选范围、展示区间和哈希；加载时核对文件
哈希与绑定项。原证据解码器复用 v1 校验，再检查实际消息中的 text 与对应记录
逐字相同。仅出现 ref、scope_ref、摘要或后台文件，均不获得送达资格。

### 持久化及兼容

新模块 `plugins/corpus/search_refs.py` 负责收据存储和别名解析。默认目录为仓库
`data/corpus-search-refs`，可用 `CORPUS_SEARCH_REF_ROOT` 指定。使用临时文件、
fsync 与原子替换；目录新建权限 0700、文件 0600。API 和所有研究 worker 必须共享
此持久目录；当前 Compose 的 `/app/data` 已有持久挂载。更换主机需同步该目录，
没有自动过期清理。仅有 v2 历史消息而丢失收据时，显式报告引用不可用并重新检索，
不猜测映射或冒称已取证。目录不可写时 search 自动回退完整 v1，显式标记
`reference_storage=unavailable_v1_fallback`。

账本区分“收据中的完整候选范围”和“实际送达的 excerpts”；预算丢弃的命中即使
仍有后台收据也不能借用证据。报告清单、fetch 与 HTTP fetch 解析 eref 后继续走
当前权威来源检查；来源撤销或投影哈希变化不会借缓存绕过。旧 v1 工具消息及旧
native 句柄仍可读取。service 层 SearchHit 和资料搜索 HTTP 返回保持原格式，
v2 是 Agent 工具输出协议。

真实验证发现旧 `context_inventory` 将 native 投影句柄当作原 chunk_id 查询，
导致全被标成 unknown。已补上 native 分支：逐成员校验现有句柄，只返回对应
权威块的标题、章节、页码和 kind；未知表格关系/区域不补造。另修正 inventory
分页预算，完整计算游标和页身份，游标使用已有压缩格式。单成员装不下时明确
返回预算错误，不返回超预算页。
