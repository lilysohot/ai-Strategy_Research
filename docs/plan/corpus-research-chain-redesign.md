# 资料库研究链路改造方案

> **2026-10-22 当前讨论范围调整：** 本轮仅讨论 search/fetch 的内容保留与必要补读，Claims/items、团队链路和全库结构化整改暂缓。以下为较早的完整架构讨论，不作为本轮实施清单；此前协议与触发门均不是已定方案。当前讨论以 [search/fetch 内容保留优化讨论稿](corpus-search-evidence-delivery-redesign.md) 为准。

版本：v1.1  
日期：2026-10-22  
状态：设计交付，未实施、未验收。  
适用仓库：/home/administrator/FrontierAgent。

本方案将日常材料研究组织为“上下文辅助检索并直接交付完整证据 → 个股、行业、宏观研究 → 只补缺失内容 → 引用校验”。原文证据是开放式研究的主路径；Claims 为比较、计算及重复跟踪提供按用途校验的记录；R2 items 保留为可选查询能力，material_relations 不恢复默认抽取。

v1.1 按用户确认修订：search 已返回完整证据就直接用，只有缺少必要内容才 fetch；具体执行以 [corpus_search 专项整改方案](corpus-search-evidence-delivery-redesign.md) 为准。

本方案不改变“搜索预览不是证据”的规则，不把上下文增强描述成已经正式启用，不删除既有结构化工件，不修改旧金标、失败记录或签认。这里只交付链路设计和整改工作包；实施进度仍归 [跨层执行总计划](claims-market-closed-loop-plan.md)，团队产品入口与续接遵循 [Web 团队研究方案](web-agent-team-run-mode.md)。后续实施应按仓库规则建立独立 spec 和逐票 issue，不将本文作为第二套执行台账。

## 1. 改造决定

| 范围 | 目标决定 | 理由和限制 |
|---|---|---|
| 原文解析、准入、范围、不可变版本与定位 | 保留 | 是两条证据路径共同的基础 |
| 混合检索 | 保留，继续验证实际问题上的相关性 | 已发布不代表全库覆盖或所有题目回答正确 |
| 上下文感知 | 分来源识别、片段定位、原文语境三层改造 | 不把标题等重复前缀一律加到片段向量上 |
| corpus_search | 发现来源并直接交付完整原文证据，支持研究线索 | 新版完整证据可引用；snippet/preview 仍不写入 evidence |
| corpus_fetch | 仅补当前问题缺失的必要原文与依赖 | 已存在的有效内容不重复读；不能改写句柄扩读 |
| corpus_semantic_query | 按需求消费已发布的完整证据单元 | 不作为每次原文研究的强制中间步骤 |
| Claims | 保留，用于指标比较、计算和重复跟踪 | purpose、单位、期间、归属与依赖必须满足用途 |
| R2 items | 不作为新增普通材料可研究的前置条件；既有结果按需使用 | 是否继续批量提取由增量收益决定 |
| material_relations | 保持当前非默认状态 | 已有价值裁决不能因本次架构讨论自动撤销 |
| 三视角研究 | 团队模式首轮独立问题与检索，之后交叉核验 | 单 Agent 的三个标题不等于三个独立上下文 |
| 消费账、报告清单、A4 | 保留并补齐团队送达与聚合验证 | 正文已保存、工具已返回、模型已收到、报告已引用是不同状态 |
| 生产数据库与历史工件 | 保留现有存储路线，按需修复对应关系 | 不以重新入库、全库重抽或新建数据库作为默认整改 |

## 5. 上下文感知分层

| 层次 | 内容 | 用途 | 不允许的替代 |
|---|---|---|---|
| 来源上下文 | 有依据的标题、机构、发布日期、研究对象、材料类型 | 来源定位、日期与对象消歧 | 发布者不自动等于观点表达者；未知日期不猜测 |
| 片段上下文 | 章节路径、原文片段、相邻解释、指代来源 | 选择相关正文，减少同报告内部错排 | 不以同一标题反复强化所有片段的向量 |
| 证据依赖 | 否定、条件、归属、期间、单位、必要表头脚注 | 判断证据是否足够支持用途 | “附近有文字”不等于必要依赖已核实 |

首版建议采用来源元数据辅助来源排序、正文与章节辅助片段排序。现有上下文前缀试验曾出现同报告内部排序回退，不能直接将试验 profile 切为生产默认。

上下文线索可以帮助生成研究问题。例如“交付延迟”可产生供应约束、产品结构变化、客户验收周期三种假设；在取证前都属于待验证假设。不能从检索预览直接确认“供应短缺”，也不能把 Agent 推测写成来源作者的观点。

表格和 OCR 沿用现有准入与完整性规则：未验证完整的表格不进入正式数值消费，标题不证明表体，正文中的图表引用不补足被排除的图表内容。扩大这些范围需要独立改造与验收。

## 6. 工具职责与证据路由

本节按用户确认修订：corpus_search 已返回完整证据就直接使用；只有当前问题缺少必要内容才调用 corpus_fetch。具体 schema、送达迁移和实施步骤以 [search 专项方案](corpus-search-evidence-delivery-redesign.md) 为准。

首版不增加“万能研究工具”。search、fetch、semantic_query 共用内部证据单元及校验，但保留真实来源工具；完整原文和必要依赖成为合法证据的条件，不再与是否调用过 fetch 绑定。

| 工具或已有能力 | 改造后职责 | 约束 |
|---|---|---|
| corpus_inventory / data_coverage | 发现原文及按 build 的结构化可用性 | 未知、未处理、故障分开；不触发模型 |
| corpus_search | 检索并直接返回高相关完整原文证据单元、候选和内容缺口 | preview 与证据分开；预算不足省略完整单元并支持恢复 |
| corpus_fetch | 只补当前问题所缺少的必要正文或依赖 | 有合法定位和具体缺口；已有有效证据不重复读 |
| corpus_semantic_query | 按实际用途复用同 build 已发布记录 | 非前置；用途、版本、依赖与送达仍验证 |
| corpus_submit_manifest | 将报告结论绑定已送达证据 | search/fetch/semantic 均可提供合法证据；最终 A4 不因零 fetch 而跳过 |
| 市场与确定性计算工具 | 获取带时点观测、执行计算 | 材料 Claim 不自动升级为真实观测或可比数字 |

结构化没有记录不构成重读已有正文的理由。当前判断缺了什么由具体任务决定；“搜索有更多候选”不自动意味着必须全部读完。

### 6.1 描述与全部 hint 一起调整

旧 snippet/preview 继续只供导航；新版 evidence_units 经权威范围校验且实际送达后可以直接引用。正常结果、native/legacy、preview、预算裁剪、no_match、abstain、降级、游标、manifest 反馈及研究纪律使用一致规则。

禁止把格式错误、报告锚点错误、delivery pending 或 A4 基础设施故障解释成缺原文。对应情况分别修正清单、锚点、等待确认或记录未验证，不反复 fetch。

### 6.2 分页与范围

新增协议区分“已交付证据单元完整”与“所有候选遍历完”：已有单元满足当前问题时，可以不读取其他候选。单元预算放不下时整单元省略并提供可恢复续页，不能字符截断正文后仍标完整。

fetch 只读取必要的合法缺失区间；native1 句柄不改写，不任意拆散依赖。分片汇齐必要区间和依赖后才能形成完整单元；exhausted 不掩盖 unresolved。

旧 fetch/旧搜索协议的原有分页要求继续用于旧格式。新增按单元消费的行为必须与 fitter、账本和 A4 同批验收，不通过仅改提示词先行放宽。

### 6.3 缓存与重复读取

缓存身份包括来源/build、授权 scope、精确范围、内容身份和读取视图；语义记录还包含 publication、purpose 和依赖状态。有效内容在本运行已送达时直接使用，不能因工具名不同而重新读。

内容已存在但当前角色尚未收到时，使用共享交付模块重送缓存并确认请求；单独计为 redelivery，不能伪装成新的原文 I/O。缓存不绕过撤回与权限检查。首轮不同研究视角可共享合法原文缓存，但不共享初步观点或结论。


## 7. 覆盖状态与失败处理

| 状态 | 允许得出的结论 | 下一步 |
|---|---|---|
| 本次查询 no_match | 本次范围和查询未命中 | 在预算内改写关键词、换视角或换来源类别 |
| 有候选但 abstain | 当前候选不足以回答 | 检查对象/问题是否匹配；必要时另起有差异的查询 |
| 部分处理 / 范围受限 | 只检查了指定范围 | 展示范围限制；不能推断全库不存在 |
| budget_limited / hits_elided | 可能有结果尚未送达 | 收紧问题、减少单页、按有效游标续取 |
| 结构化 missing / not_extracted | 该 build/角色尚无可用结构化结果 | 转原文；不隐式启动抽取 |
| version_mismatch / cursor_stale | 当前证据路径或续页版本不适用 | 重查当前版本；历史研究则显式固定历史版本 |
| dependency_missing | 当前证据不满足指定用途 | 补合法原文或降低用途/缩小结论 |
| store / provider 不可用 | 无法确认，不是没有资料 | 记录故障，按模式允许的路径降级 |
| 有明确登记的内容缺口 | 已知某范围尚未覆盖 | 说明具体缺口；不把普通 no_match 扩大成同样结论 |
| 证据来源之间冲突 | 结论尚有分歧 | 对齐日期、口径与归属，补查后保留未解分歧 |

改写必须增加新的检索意图，不能无意义重复同一句查询。建议首轮试验对每条失败检索最多允许两次有差异的改写；这是待冻结的预算参数，不是“查两次就证明无资料”。

不再因局部 no_match 强制输出“无研报覆盖”。市场数据只在用户问题需要且端点支持时使用；查询材料观点失败，不自动变成行情技术面任务。

## 8. 三视角研究与发散闭环

三视角是一种团队研究策略，不改变“运行模式属于本次 Run”的产品决定。简单查数或短追问可继续单 Agent；明确要求全面研究或启用三视角策略时，工作流必须检查三个视角都有结果或明确的缺口状态。单 Agent 依次分析三个角度可作为对照，但不宣称独立研究。

~~~mermaid
flowchart TB
    Q["原始问题 / 时间窗 / 用户约束"] --> B["共同事实简报<br/>标明已知来源、历史判断与待验证假设"]
    B --> S["个股视角<br/>经营变化 / 公司差异 / 财务口径"]
    B --> I["行业视角<br/>供需 / 同行 / 产业链 / 竞争"]
    B --> M["宏观视角<br/>需求 / 利率汇率 / 政策传导"]
    S --> SR["独立问题与检索 / 取证 / 反证"]
    I --> IR["独立问题与检索 / 取证 / 反证"]
    M --> MR["独立问题与检索 / 取证 / 反证"]
    SR --> C["首轮结果冻结后汇总"]
    IR --> C
    MR --> C
    C --> D["分歧和方向筛选<br/>影响 / 增量 / 可验证性 / 证据状态"]
    D --> V["针对关键分歧第二轮补查"]
    V --> F["研究结论、候选方向、失效条件与资料缺口"]
~~~

首轮不传递统筹者的倾向性结论和其他角色的初稿；保留完成任务所需的用户上下文，并区分用户假设与已核实事实。独立性来自问题、检索路径和上下文隔离，不依赖使用不同模型或提高随机性。

每个视角返回“研究线索卡”，建议字段如下；它是研究运行的产物，不是新增语料库抽取层：

| 字段 | 内容 |
|---|---|
| research_question / perspective | 要回答的问题及视角 |
| trigger | 触发线索的来源、版本、位置；标记 preview_only 或 evidence_delivered |
| hypothesis / alternatives | 可验证假设及替代解释 |
| significance | 假设成立会改变哪个研究判断 |
| evidence_refs / counterevidence_refs | 支持与反证；保留归属和时间 |
| dependencies / unknowns | 尚缺的条件、单位、期间、证据 |
| next_queries | 下轮查询及预期解决的具体缺口 |
| status | proposed / supported / contradicted / unresolved；不是事实真伪认证 |

优先跟进变化、同行差异、信息矛盾、传导变化和约束出现；不能把提及次数多当作市场共识，也不能从材料讨论少推出“市场尚未定价”。

建议试验起点：各视角最多提出三条候选方向，统筹者挑两到三条继续，一轮关联扩展后再评估。每个视角保留基本探索预算，剩余预算按新增有效证据分配。所有预算属于整队总额，不把单 Agent 上限直接复制三份。

停止条件包括：关键问题已被足够证据回答、连续扩展只重复旧内容、缺少合法可读范围、预算到达、方向与任务关联过弱。停止必须保留尚未解决的缺口；不得为了凑齐三段而编造宏观联系。

### 8.1 团队证据传递

子 Agent 查到并送达的证据，不自动等于协调者已读。研究摘要须带完整、可核验的必要原文及引用身份，沿同一消费机制记录“传给协调者并进入实际请求”；只传结论或 record_id 不足以确认协调者送达。

报告清单保留 owner_role；不同角色清单按既有规则聚合，同一角色新清单取代旧候选。协调者重写结论后须登记最终报告锚点，不能把子 Agent 摘要中的锚点当最终报告锚点。团队持久化、取消、成员失败、部分成功及全队计量按团队产品方案实现。

## 9. 结构化提取与版本生命周期

Claims 与 R2 的变化是职责收敛，不是删除接口或丢弃既有成果。

| 情况 | 处理 |
|---|---|
| 普通材料新入库 | 原文准备、索引与证据路径达标即可用于对应范围研究，不等待 R2 |
| 已有同 build 合格记录 | 按用途查询和复用，不重复抽取 |
| 需要批量比较/计算，但没有合格记录 | 先判断能否用合法数据观测或已取证原文完成；确需持久结构化时提交明确后台任务 |
| 新 build 替换旧 build | 新增可用性记录；旧结果保留历史使用资格，不重标为新版本 |
| 原文内容相同但解析坐标改变 | 必须重新验证映射与依赖，生成新版本发布；不能仅改 build_id |
| 结构化抽取或质量门失败 | 记录失败与覆盖缺口，不阻断本来合法的原文研究；比较/计算用途可能仍不可用 |
| 准入撤回或用途收紧 | 停止对应用途，报告交付前复核；缓存命中不绕过撤回 |
| material_relations 需求出现 | 独立价值论证和有界试验，不并入本次默认整改 |

查询、研究启动、补读均不隐式启动 M_extract。提取任务固定来源/build、角色、用途、范围与预算，继续使用独立配置与调用账；抽取成功不代表已经发布，发布成功不代表已经送达。

### 9.1 Web 结构化 store 前置条件

建议增加明确的运行能力配置（名称为设计值）：

- raw_only：不暴露语义查询工具，原文研究不要求 structured store 存在。
- optional：有可验证的只读 store 才暴露语义查询；不可用时明确记录能力缺失，允许合法原文研究。
- required：任务明确依赖结构化消费，沿用严格只读与完整性检查，不能静默降级成“已完成结构化研究”。

移除全局强制不等于放宽已选择语义路径的检查。损坏、撤回、可写 store 不得被当作正常来源；optional 可以隔离该能力继续原文，required 必须明确失败或要求调整任务。配置缺省值、已有部署迁移和权限行为须在实施 spec 冻结，并在实际 worker 启动前验证。

## 10. 实施顺序与验收门

工作包表示建议顺序，不代表已经开始。改动均以当前工作副本为基准，保留并行修改和历史证据。

| 工作包 | 改造内容 | 交付与验收 | 依赖 |
|---|---|---|---|
| P0 基线与契约 | 固定实际入口、profile、工具集、原文范围、build、结构化 publication、预算及 A4 状态；盘点所有提示分支 | 输出 source/build/role 可用性矩阵与代表性运行轨迹；区分历史记录和当前观测 | 无 |
| P1 路由与状态修复 | 统一 description/hint/研究纪律；修复 no_match 过度结论；明确 raw/optional/required | 同一状态在所有分支含义一致；原文模式不因缺结构化 store 阻塞；语义模式保留严格检查 | P0 |
| P2 上下文检索 | 来源与片段信号分离；多视角查询；限定来源/时间；合法核心取证计划试验 | 独立题上关键证据和反证不退化；版本、scope、未知日期保持正确 | P1 |
| P3 完整证据交付 | search 直接交付、缺口 fetch、分页、内容复用、裁剪、统一送达与引用回验 | 经过实际消息裁剪后仍保留依赖；无伪 delivered；不跨版本/范围；最终 A4 可追溯 | P1；核心计划依赖 P2 |
| P4 三视角团队 | 对接团队入口、角色工具、独立上下文、线索卡、交叉补查、协调者送达、总预算 | 三视角可追溯；无重复计数；成员失败明确；跨角色引用与最终锚点通过 | P2、P3、团队入口对应工作包 |
| P5 按需结构化 | 当前 build 可用性发现、用途过滤、历史版本隔离、显式抽取任务 | 不自动重抽；旧 build 不冒充当前；比较/计算的条件与用途不丢失 | P1；与 P2—P4 可独立排期 |
| P6 端到端对照与发布 | 分别测上下文、结构化、团队三种增量；有界真实运行、发布和回滚验证 | 质量及硬门通过后才扩大流量；功能与预算各自报告 | 相应试验臂依赖的工作包 |

推荐先完成 P0、P1，再跑单 Agent 的 P2/P3 基线；原文研究不用等待 P5 全量补齐。只有看到可靠资料读取后，再评估 P4 是否带来更好的研究方向。

## 11. 验证设计

先做零模型契约回放和本地测试，再按已冻结范围与预算开展真实模型试验。已有 32/57 题继续作为开发回归，不冒充独立泛化测试。

### 11.1 必测场景

| 场景 | 必须观察到的行为 |
|---|---|
| 单一明确事实 | 读取足够证据后作答，无无意义重复 fetch |
| 多公司同指标比较 | 两侧证据都送达；单位、期间与口径一致或明确不可比 |
| 条件、否定、观点归属 | 不因片段裁剪或摘要丢失，不把预测当事实 |
| 同报告相似章节 | 正确目标正文排序不被重复来源前缀挤走 |
| 反证藏在其他来源 | 有独立反证查询；没有找到时保留检索范围 |
| 宏观传导问题 | 给出与行业/公司的具体机制和证据，不强造关联 |
| 已发布正文无结构化结果 | 原文研究可继续；不自动抽取 |
| 旧结构化 build 与新原文 build 不同 | 显式拒绝跨版使用，可按当前合法原文继续 |
| 预算裁剪与分页未完 | 不误报完整；续页或缩小结论 |
| 表格不完整/标题/排除的 OCR | 不绕过现有完整性与范围限制 |
| no_match / abstain / 系统故障 | 不概括成“全库无资料”，不自动改变研究目标 |
| 子 Agent 成功、协调者未收到证据 | 不能登记协调者 delivered；补传或撤去对应引用 |
| 版本撤回、权限变化 | 缓存不绕过检查；历史报告与当前用途分开 |
| 成员失败/超时/取消 | 总预算准确，结果标部分完成，其他成员不伪造缺失视角 |

### 11.2 分离变量的对照

- A：现行单 Agent 原文检索和取证，作为行为基线。
- B：同模型、同来源快照、同问题，增加上下文检索与选读；不强制结构化。
- C：在 B 基础上，仅对适合的任务提供合格结构化记录，检验其增量。
- D：在 B 基础上引入独立三视角研究，检验研究覆盖与方向质量；需要结构化的任务另做与 C 对应的比较。

先用代表性少量任务验证运行与计量，再扩展到独立、预先冻结的题目。真实调用总预算包含失败、重试、全队各成员、embedding 和评判成本，不能只统计“有效轮”。不直接使用受保护留出材料，也不把既有错误改写成新基线通过。

### 11.3 指标与发布标准

| 维度 | 指标口径 |
|---|---|
| 检索 | 对预先标注重要证据单元的召回；来源与片段分别统计；反证单独统计 |
| 交付 | 应交付单元中进入实际模型请求的比例；完整依赖保留；跨角色传递 |
| 答案 | 关键事实准确、条件/归属正确、可回答任务完成率、空结果表述正确 |
| 研究方向 | 方向能追溯触发证据，有可验证问题、替代解释与下一步资料；人工盲评价值 |
| 效率 | 真实 search/fetch/semantic 调用、重复读取、全量请求 tokens、缓存 usage、墙钟时间 |
| 覆盖 | 原文准入范围、解析覆盖、结构化角色覆盖、查询范围和交付范围分别报告 |
| 运行 | 总预算、成员状态、终止原因、最终 manifest/A4 与实际报告一致 |

硬门：无伪造引用、无跨版本/权限/范围读证、无把 preview 当 delivered、无无授权隐式提取、关键依赖不被静默丢弃、no_match 不被扩大成全库不存在。已登记的非通过状态必须保留，不以功能通过覆盖预算失败。

质量与效率阈值应在真实比较前冻结：首先要求重要证据、反证和关键用途质量不退化，再讨论时延和费用收益。不能用一个平均分抵消高危错误。小样本报告逐题差异和不确定性，不从单次快慢推导稳定提升。

## 12. 发布、回滚与监测

1. 先在隔离环境修复契约与运行接线，再运行端到端回放；当前生产默认保持直到该批次验收完成。
2. 能力开关应分别控制上下文排序、核心取证计划、结构化消费和三视角策略，避免一个开关捆绑所有变化；名称在 spec 冻结。
3. 按 source/build 验证当前版本可用性；原文发布不自动宣称结构化同步完成。
4. 先验证单 Agent 新路径，再验证完整团队入口、续接、停止、计量和报告；不要只证明子 Agent 能单独调用工具。
5. 回滚恢复上一版已验证路由/profile/排序，保留不可变原文、历史工件和引用身份；不通过删库或删除发布历史回滚。
6. 增加运行级观测：路径选择原因、semantic 不可用原因、有效新增证据、重复 fetch、分页未完成、每视角证据来源、最终 A4 状态。
7. 对无范围越界但收益不确定的实验保持可关闭；出现证据越界、伪送达或版本误用时停止扩大，保留失败轨迹定位。

## 13. 首版交付定义

首版完成意味着：用户提出一个需要全面研究的问题，团队能够分别从个股、行业、宏观寻找资料；由 search 直接取得有限的合法完整证据，仅对必要内容缺口补读；用已送达证据生成可核验的研究方向；对冲突和缺口补查；结构化记录有用且版本合格时复用，没有时普通原文研究仍可完成；最终报告具有真实消费账和引用校验。

不以“新增三个角色”“检索接口可调用”“返回 JSON 正确”“fetch 次数减少”或“测试数量增加”单独宣布完成。本方案的核心验收对象是：重要证据有没有被找到、完整送达、正确解释并用于回答用户的问题。
