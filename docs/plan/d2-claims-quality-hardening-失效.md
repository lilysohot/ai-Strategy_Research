## 1. 目标与原则

本计划解决的不是“让模型多抽一些文本”，而是让进入下游聚合的每个 claim 都具备可靠的：

- **候选召回**：有价值的数字与纯评级观点不会在 LLM 调用前被过滤掉；
- **领域坐标**：公司、行业、宏观三类文档使用正确的主体、地域、口径和数据状态；
- **结构正确性**：指标、期间、单位、时点能被校验，错误值不会静默混入共识；
- **可追溯性**：每一项结论都能回到文档块、抽取版本和分类原因；
- **安全迭代**：规则或提示词升级前后可量化比较，且支持按块重跑。

实施时遵守以下约束：

1. 先建立可复现基线，再改变线上行为；
2. 不自动写入 `doc_kind_override`，人工覆写必须是显式动作；
3. 无法确定的数值、期间或坐标留空或标记待复核，不能猜测补全；
4. 保持 `triage_blocks`、`extract_from_block`、`claims_from_payload`、`classify_doc_kind` 的调用接口稳定；
5. 未通过抽样审计和回归集前，不触发全量重抽。

## 3. PR-1：审计基线与金标集（P0）

### 3.1 审计报告

- [ ] 新增只读审计入口，接受 `doc_id`、抽样数量或输出路径；不得调用 LLM，不得修改数据库。
- [ ] 对每个块输出：`doc_id`、`seq`、文本长度、triage 结果、拒绝/接纳原因、文档类型、类型判定原因、表格判定、已有块运行状态。
- [ ] 对每次运行输出汇总：三类 `doc_kind` 分布、候选率、各拒绝原因占比、长块比例、表格比例、`ok/failed/dead` 块数。
- [ ] 输出 JSONL 作为机器输入，并输出 Markdown/CSV 作为人工复核摘要。

### 3.2 金标样本

- [ ] 分层抽取至少 180 个块：公司、行业、宏观各至少 60 个。
- [ ] 强制覆盖：纯评级、带数字预测、宏观实际/预期/前值、普通表格、压平长表格、目录、免责声明、联系人页、无信号正文。
- [ ] 每个样本人工标注：是否应进入候选集、正确 `doc_kind`、是否为表格、应有/不应有的 ticker、期间与数值是否可可靠抽取。
- [ ] 将可公开或脱敏的样本固化为测试 fixture；私有原文只保留 `doc_id + locator + 标注结果`。

### 3.3 基线指标

- [ ] 记录候选召回率、噪声放行率、`doc_kind` 准确率、表格识别 precision/recall、字段有效率、空结果率、失败率、平均 token 与耗时。
- [ ] 报告中区分“候选层漏失”“LLM 输出错误”“Python 解析/落库错误”，避免将三类问题混为一谈。

**验收**：相同数据库和参数下报告结果可重复；金标样本、标注规则和指标定义均进入版本控制。

## 4. PR-2：修复纯评级召回（P0）

当前 `has_signal()` 以数字作为硬前提，但 claim 定义已经承认“买入、增持、中性、减持”等评级观点；两者应保持一致。

- [ ] 将 triage 内部判断拆为“是否候选”和“原因码”，至少支持 `numeric`、`rating`、`noise`、`no_signal`。
- [ ] 允许不含数字的评级文本进入候选集，例如“维持买入评级”“上调至增持”。
- [ ] 继续过滤评级说明页、免责声明、分析师名单、联系人页等噪声文本。
- [ ] 增加中英文测试：买入/增持/中性/减持、Buy/Neutral/Overweight，以及至少三类误放行反例。
- [ ] 在审计汇总中单列 `rating` 候选数、有效输出数和空输出数，用真实数据评估成本收益。

**验收**：金标中纯评级候选召回率不低于 95%；现有噪声金标不新增误放行；普通数字类召回不下降。

## 5. PR-3：文档类型分类治理（P0）

`doc_kind` 决定提示词插槽、ticker 保留规则和指标坐标，是高杠杆判断，必须可解释且可人工校正。

- [ ] 保留 `classify_doc_kind()` 的现有返回接口；新增内部判定详情对象，包含 `kind`、`reason`、`confidence`。
- [ ] 统一原因码：`manual_override`、`title_ticker`、`single_body_ticker`、`multiple_tickers`、`industry_title`、`macro_title`、`fallback`。
- [ ] 为以下边界案例补充 fixture：策略周报、宏观周报、行业报告含多公司代码、公司报告含同业比较、无代码且无标题提示的行业文档。
- [ ] 审计所有 `fallback` 与低置信度文档，生成按原因分组的人工覆写候选清单。
- [ ] 确认 `documents.doc_kind_override` 在抽取入口中的优先级最高；新增覆写读写的最小操作说明，但审计命令只建议、不写入。
- [ ] 每个块运行记录或关联审计记录应包含最终类型及其来源，便于历史结果解释。

**验收**：金标 `doc_kind` 准确率不低于 95%；所有覆写优先于规则；任何分类结果均可给出原因码。

## 6. PR-4：指标坐标 lint 与别名治理（P1）

目前 `metric` 同时承载公司指标、行业“主体.指标”和宏观“地域.指标.口径/状态”。第一阶段不迁移 schema，而是先把这套约定变成可验证的内部模型。

- [ ] 定义内部 `MetricCoordinate`，至少表达 `scope`、`subject_or_region`、`metric`、`basis_or_state`。
- [ ] 实现 `parse_metric_coordinate()` 与 `lint_claim_coordinate()`；lint 只报告，不应阻塞历史数据读取。
- [ ] 校验不变量：
  - [ ] 公司 claim 不使用宏观三态；
  - [ ] 非公司 claim 不携带公司 ticker；
  - [ ] `actual`、`consensus`、`previous` 不可混为同一坐标；
  - [ ] `period`、`as_of`、`unit` 为空时不得伪造默认值；
  - [ ] 同一坐标的单位或数值异常冲突必须被报告。
- [ ] 将 `METRIC_ALIASES` 的新增改为“样本依据 + fixture + 不误合并反例”三件套，避免广义字符串替换。
- [ ] 输出非法格式、坐标冲突、单位冲突、疑似别名分裂的审计报告。
- [ ] 下游聚合接入 lint 结果：被判定为非法的 claim 不进入共识计算，并输出可见告警。

**验收**：金标合法坐标全部可解析；金标非法坐标全部被报告；第一阶段不要求迁移 `claims` 表。

## 7. PR-5：表格、期间与长块截断（P1）

### 7.1 表格识别

- [ ] 建立表格 fixture：真实预测表、正文数字段、目录、联系人页、脚注、横向/纵向压平表。
- [ ] 以金标统计 `is_flat_table()` 的 precision 与 recall；记录每一种误判的文本特征。
- [ ] 调整启发式前必须在基线报告中展示预期改善，而不是仅凭单个样本修改阈值。

### 7.2 期间锚定

- [ ] 实现安全的期间等价归一，如 `2026H1` 与“2026 年上半年”。
- [ ] 为 `2026E`、季度、月度、同比/环比等形式分别测试；不允许根据上下文猜测缺失年份。
- [ ] 表格 claim 的期间无法在原块中可靠锚定时，标记待复核或拒绝落入常规聚合集，而非推断填充。

### 7.3 长块压缩

- [ ] 审计超过 `PROMPT_MAX_CHARS` 的块，统计标题、表头、单位和数值行是否落在截断后。
- [ ] 对表格采用结构优先压缩：保留标题、表头、单位、期间行和数值行；正文仍使用受控长度截断。
- [ ] 记录压缩前后长度与是否为表格，保持 token 预算可预测。

**验收**：表格金标的期间错配为 0；长表格 fixture 保留表头、单位和至少一组正确的期间—数值关系；不得引入虚构年份。

## 8. PR-6：回归、运行治理与版本纪律（P1）

### 8.1 黄金回归集

- [ ] 覆盖：纯评级、公司 ticker 回填、行业多代码、宏观三态、截断 JSON 恢复、单位/负号解析、`as_of` 兜底、失败重试与死信。
- [ ] 所有 LLM 相关测试都经注入的 `LlmFn` 返回固定 payload；不在单测中调用真实模型。
- [ ] 测试从模块的公开 interface 进入，不以大量内部函数白盒测试替代端到端行为验证。

### 8.2 重跑与版本

- [ ] 建立版本变更表：提示词、解析、分类、坐标规则任一语义变化，都必须评估并更新 `_EXTRACTOR_REV`。
- [ ] 先在金标和小范围 `doc_id` 上重跑，比较新增、删除、改变坐标和改变数值的 claim；确认后才能全量重跑。
- [ ] 版本变更后确认块级替换语义正确，避免同一块混入两代结果。

### 8.3 运行可观测性

- [ ] 扩展 dry-run：按文档类型的候选量、triage 原因、已完成/死信块数、预计 token、待人工覆写文档数。
- [ ] 提供死信复核导出：错误内容、重试次数、模型、抽取版本、文档定位。
- [ ] 若修改 `claims` schema，同步更新备份列映射及相应测试，防止备份静默遗漏字段。

**验收**：任一次重跑前都能得到影响预览；失败块可定位、可复核；版本变更不会悄悄复用旧结果。

## 9. 模块整理（P2，行为稳定后）

`claims.py` 当前是一个有价值的深模块：调用方交给它块、领域和 LLM，即可获得可追溯 claim。不要仅因文件变长而过早拆分。

- [ ] 先确认新模块有真实的第二个消费者，再抽出 schema 或坐标模块。
- [ ] 若引入第二个生产级 LLM provider，再将默认 LLM 客户端提为 adapter；现有 `LlmFn` 注入已经足以支持测试。
- [ ] 若拆分，外部 interface 不变，测试仍通过 `extract_from_block()` 等公开入口跨 seam 验证。
- [ ] 删除无效的中间层与重复转换，避免把一个深模块拆成大量浅模块。

**验收**：重构前后的黄金回归集结果一致；`CorpusService.extract_claims()` 的调用方无需理解新增内部细节。

- [ ] 金标指标没有回退，或回退已被明确记录并批准；
- [ ] dry-run 已确认候选量与 token 成本在预期范围；
- [ ] `fallback` 分类与死信块已人工抽查；
- [ ] 新旧版本差异报告已归档；
- [ ] `claims` 备份/恢复路径已做一次验证。

## 11. 明确不做的事

- 不把叙事、主题或逻辑链硬塞进 `claims`；它们需要独立的数据载体。
- 不依据低置信度规则自动修改文档类型。
- 不因当前只有一个生产实现就提前制造复杂的 LLM adapter 层。
- 不用“更多 prompt 字段”替代 Python 侧可确定完成的单位、数值和格式校验。
- 不在缺少质量报告时进行昂贵的全量抽取。
