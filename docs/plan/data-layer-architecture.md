## 1. 背景：选型前提已经变了两次

**验证期**：SQLite（17 份、零运维）用来验证「算术不出 LLM / 数字可溯源」。它完美胜任。
**P0 通过后**：语料 → 8000 份 + 每天 10–30 份，要长期运营。
**现在**：要求 **host:port 网络接入 + Windows 直连 + web 端 + 未来多人共享**。

> 此前用「规模够不够」回答是错的框架。真正的变量是**共享方式、写入并发、管理要求**。

## 2. 已确认的业务事实

| # | 事实 | 对选型的含义 |
|---|---|---|
| 1 | **单人、本地使用** | 暂不需要多人权限体系，但**要能网络访问** |
| 2 | **会有多个进程同时写入** | SQLite 单写入者 → **硬边界，已不可接受** |
| 3 | 研报**先手动拷贝**进 `data/`，自动同步先不考虑 | 写入是按需跑批，非常驻 |
| 4 | 当前可用 SQLite；项目完整度提高/面向市场时**升级 PG** | —— |
| 5 | **需要服务端地址与端口，从 Windows 接入数据库** | **SQLite 是文件库，无 host:port 概念 ⇒ 直接排除** |
| 6 | **Windows 上有 Docker** | PG 可用容器部署（见 `pg-migration.md` §2） |

## 3. 结论

### 3.1 存储：PostgreSQL（中文全文 zhparser + pgvector 留位）

| 能力 | 方案 |
|---|---|
| 结构化台账（状态 / 系列 / 取代关系） | PG 原生关系表 |
| **中文全文检索** | **zhparser**（PG 内置 FTS **无中文分词**，必须装扩展） |
| **向量检索** | **pgvector 留位**——判据未满足，暂不建列；需要时同库启用，**不引入新系统** |
| 网络 / 多人 / web 后端 | PG 原生 host:port，Windows 可用 DBeaver / pgAdmin 直连 |
| 备份 | `pg_dump` / PITR（比复制文件可靠） |

### 3.2 为什么推翻 v1.0（触发条件已满足）

v1.0 写死了升级触发条件，现已满足**两条**：

- ✅ **多进程并发写**（事实 #2）——SQLite 硬边界
- ✅ **需要跨机 / 网络访问**（事实 #5）——文件库根本做不到

**现在换的成本最低**：语料仅 17 份，迁移是分钟级；若等全量 8000 份之后再换，要回填 + 重做中文检索，成本高一个量级。

### 3.3 架构：**服务层收口 + 存储可替换**（不变，且更关键了）

所有 DB 访问经 `plugins/corpus/service.py`，**调用方一律不直连**。
换 SQLite → PG 时，**调用方（`corpus_search` / `corpus_fetch` / `verify` / `golden`）零改动**，只改服务层实现。

> 这条在 v1.0 就定了，现在证明是**最省钱的一个决定**——正因为有这层，换存储才是"改一处"而不是"改 N 处"。

### 3.4 并发：PG 原生支持，v1.0 的 SQLite 加固作废

以下 v1.0 计划**全部作废**（PG 不需要）：WAL / busy_timeout / 写重试 / 影子表重建索引 / `VACUUM INTO` 快照。
替换为：连接池（`psycopg` + pool）、**GIN 索引维护**（`tsvector` 更新）、`pg_dump` 备份。

> 尤其"重建索引的长事务"问题在 PG 下消失：`tsvector` 可增量维护，无需全表重建。

## 4. 关键风险：BM25 ≠ ts_rank（**已校准 · 2026-09-08 关闭**）

**风险预判成立**：PG 原生没有 BM25，切过去后黄金集 Recall@5 一度跌到 **0%**
（详见 `pg-migration.md` §4.7 的完整过程与逐项 Recall 变化）。

**校准结论**：在 `ts_rank` 基础上补齐四项语义后回到 **100%（20/20）**——

| # | 补齐项 | 为什么必须有 |
|---|---|---|
| 1 | **AND → OR 兜底** | 黄金题是自然语言长问句，`plainto_tsquery` 纯 AND 要求单块含全部词元 ⇒ 必空。空结果退回 OR（对齐 P0 的 FTS5 行为） |
| 2 | **标题 5× 显式加权** | `setweight('A')` 的默认权重**不等价** BM25 的 5.0×，须在服务层显式加权 |
| 3 | **正文用 `ts_rank` 而非 `ts_rank_cd`** | `ts_rank_cd` 是**覆盖密度**算法，不按词频/稀有度加权 ⇒ 稀有词（MDB / EXE）拉不开同系列兄弟文档 |
| 4 | **按 `doc_id` 去重** | 按「块」排序时，一份多块长文档会用它 N 个块霸占 top-k，把真正相关的其他文档挤出候选集 |

另加 **时效偏置**（含「最新/近期/最近」的查询对 `published` 加权），
用于「最新一期」这类**没有关键词信号**的时效题——纯 FTS 无法判断时序。

⇒ 原定三种应对中，**采用了 1 的变体**（`ts_rank` + 显式加权 + 服务层后处理）；
**未引入** `pg_textsearch`，也**未做**服务层 rerank——两者暂无必要，留作日后 Recall 掉分时的备选。

**另一最大风险：数字检索**。我们花力气解决的「数字+单位整体绑定」（`47.3亿`、`30%`、
`24.50`）依赖 jieba 预分词 + FTS5 `tokenchars '.%'`；zhparser 对数字与单位的处理**不同**，
可能切碎或丢弃。

- **现状**：黄金题「数字」类 8 题 **Recall 已 100%**（功能层面通过）。
- **仍待办**：切分形态本身（`to_tsvector('zhcfg', ...)` 对 `47.3亿` / `30%` / `24.50` 的切分）
  尚未逐条复核；若发现被切碎，再启用 `pg_trgm` 兜底（详见 `pg-migration.md` §8）。

## 5. 为将来预留的边界（写代码时遵守）

| 约束 | 理由 |
|---|---|
| 调用方只调 `search()` / `fetch()` / `document_text()` 等服务层接口 | 换存储时调用方零改动 |
| 服务层不向外暴露具体驱动类型（`sqlite3.Row` / `psycopg` 游标 / 连接对象） | 否则驱动类型泄漏到业务代码，换库连坐 |
| 检索能力（分词、权重、排序）**完全关进服务层** | zhparser / ts_rank / 将来 pgvector 都只影响这一层 |
| 写入语义保持「落库 + 索引可用一次完成」 | P0 踩过的坑（入库未建索引 → 检索静默失效） |

## 6. 业务流程（当前形态）

```
手动拷贝研报 → data/corpus/（源区，只读归档）
             → 跑一次入库命令（按需，非常驻）
             → 服务层 → PG：解析 → 去重 → 落库 → 更新 tsvector
             → Agent 检索 / 取证（经服务层）
             → 产出（策略卡 / 报告）
             → web 端（经 API）/ Windows 客户端直连 PG
             → 备份（pg_dump）+ 梳理（去重 / 修订 / 系列）
```
