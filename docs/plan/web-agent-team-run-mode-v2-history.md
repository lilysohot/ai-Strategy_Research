## 1. 结论与产品语义

**推荐：保留现有 stateful-react-agent 作为唯一用户主 Agent，在用户选择“团队研究”的回合增加一个独立、有限的团队研究阶段。**

“单 Agent / 团队研究”仍属于每次 Run，同一研究内可逐轮自由选择；它表示本轮是否调用团队研究能力，不再表示把会话所有权交给另一套主工作流。

- 单 Agent：现有原生回放 → 主 Agent 处理问题 → 保存原生快照。
- 团队研究：读取主会话上下文并准备任务 → 隔离团队研究 → 材料交给主 Agent → 主 Agent 结合原生历史与本轮业务快照回答 → 保存原生快照。
- 主 Agent 始终负责用户对话、账户与计划、补资料请求和最终个性化判断。团队 coordinator 只是研究阶段的内部调度者，不接替业务主 Agent。
- 研究 ID、账户、计划、消息和产物归属不变；正在执行的 Run 不切换模式，停止并清理完成后可重新发送。
- 团队模式不意味着每个请求都强制派人：缺少必要输入时，主 Agent 先澄清并说明本轮未开展团队研究。

本方案保护的是现有单 Agent 的上下文能力及原生载荷。团队成果作为新增材料进入主会话是正常语义，不是零影响；禁止把团队原始推理轨迹、工具消息和独立会话快照混入主会话。仍受现有回放窗口、压缩和模型上限约束，不承诺无限历史逐字常驻。

## 2. 为什么选择这条路线

| 路线 | 与本项目的匹配 | 结论 |
|---|---|---|
| 每轮直接切换 stateful-react-agent / agent_team | team 无原生续接；需迁移两种快照、维护交接覆盖、业务所有权转移及双向恢复 | 撤回作为首版路线；复杂度主要花在兼容迁移上 |
| 给主 Agent 增加 create_subagent 等完整团队工具 | 工具需 AgentBus、runtime、SpawnGuard 等环境；新增工具集合影响现有回放校验与前缀；主循环、权限、清理耦合加深 | 暂不采用；不是“加一个工具”就能完成 |
| 固定主 Agent，应用编排可选团队研究阶段 | 复用既有主会话续接、业务工具和 team 研究能力；新增复杂度集中在研究阶段及观察/控制适配 | **推荐先验证，再实施** |

取舍：首版采用顺序阶段，不能像长期存活团队那样让主 Agent 随时多次发起协作。团队轮次有准备与整合开销，但普通单 Agent 回合不增加这些开销。先实现一次团队研究、一次主 Agent 整合；不做轮内无限反复派工。

“固定主 Agent”指同一职责、原生会话链及兼容配置，不是跨轮常驻同一个进程。“一次团队阶段”限制主 Agent 与团队之间的往返次数，不禁止 coordinator 在该阶段内检查报告、追加任务和要求成员补查。该路线适合批次研究；其交互灵活性和维护条件见 §13，不能据此宣称已经支持主 Agent 与团队实时协作。

## 4. 一个 Run 内的执行顺序

```text
提交问题并冻结 mode、模型配置引用、业务输入、总预算
    │
    ├─ single ─────────────────────────────────────┐
    │                                             │
    └─ team → 准备研究任务 → 隔离团队研究 → 校验材料 ┤
                  │ 缺必要输入/不适合团队            │
                  └─ 带明确原因交主 Agent ──────────┤
                                                  ↓
                        原有主 Agent：原生回放 + 本轮输入
                                                  ↓
                              保存主会话快照、发布结果、收尾
```

这是同一个产品 Run 的多个阶段，不生成多条用户消息，也不创建另一个研究。Run 根 pipeline 保持 stateful-react-agent；内部阶段记录 agent_team 的 pipeline 和角色。mode 独立持久化，不能继续以 pipeline_id 等同于用户模式。

建议由现有 parent orchestrator 统一持有 Run 与阶段进程：准备、团队、主 Agent 顺序执行，阶段 worker 只报告阶段完成。只有 parent 能发布产品 Run 终态。内部 team main_agent 结束不能使主 Agent 尚未执行的 Run 提前 completed。

本轮预算包括准备调用、team coordinator、所有成员、主 Agent 整合以及压缩/总结调用。启动团队前预留主 Agent 整合和收尾预算；团队预算不足返回明确部分结果，不侵占保留预算。团队默认最多 2 个研究成员、禁止成员再派生团队；具体 token/时长配置由 M0 测量后冻结。

## 5. 任务准备与研究 Module 的 Interface

### 5.1 任务准备不是第二条主会话

准备阶段属于主 Agent 的编排职责，以只读方式使用工作流校验过的原生上下文、本轮用户问题和冻结业务资料，生成有限研究任务。由工作流侧 Adapter 提供上下文视图；server 继续只搬运 opaque payload，禁止从 turns 重新拼历史、恢复 history.txt 或添加 conversation_history。

推荐先实现一次无工具的只读准备调用：把经校验的上下文视图作为数据读取，输出任务，不作为主会话回复提交。它使用独立调用身份、单独记录用量，不假装复用主循环的原始工具会话，也不重写主快照。若需要账户补数或业务工具计算才能决定研究任务，交给正常主 Agent 澄清，本轮不盲目启动团队。首版不实现“准备阶段先跑一整套业务主循环”。

准备可能遗漏信息，因此关键约束保留原文及来源标识，附上任务范围与不确定项；没有足够上下文时显式报缺口，不把简报解释为无损历史。最终主 Agent 仍独立读取原生历史，负责核对团队任务与当前用户意图。

### 5.2 团队研究的外部 Interface

下列为语义契约，物理字段由 M0 冻结：

| 输入 | 约束 |
|---|---|
| ResearchBrief | 研究问题、任务范围、必要用户约束、已知事实/证据引用、冲突与待验证项、来源主会话 revision、业务快照版本 |
| AllowedInputs | 只读且按需授权的附件、历史产物和证据；不传原始主会话、完整账户/计划或业务工具凭据 |
| RunLimits | 总截止时间、团队 token/成员数上限、主 Agent 预留预算、取消信号 |
| EventSink / ApprovalChannel | 注入可审计的身份、事件、工具审批及取消通道；不是成员自行接入 Web |

| 输出 ResearchResult | 约束 |
|---|---|
| status | completed / partial / failed / cancelled，保留失败与缺口 |
| findings | 结论、相互矛盾的观点、未经验证的假设，不把团队多数票当成事实 |
| evidence_refs | 来源类型、版本/哈希、定位、时间和必要摘录；缺失或不可读必须标明 |
| artifacts | 经授权发布的持久产物 ID；不返回不可持久的成员临时路径作为证据 |
| usage / provenance | 各阶段/成员用量、完整度、输入版本、任务 ID、结果哈希 |

研究 Module 内复用 agent_team、AgentBus、SpawnGuard 与原有报告机制，由具体 Adapter 隐藏启动、工具白名单、成员事件和进程清理。首版只实现实际需要的执行路径，不预建通用工作流市场、任意拓扑或可插拔引擎体系。框架内核不导入 server 或 benchmarks。

团队进程拥有独立工作目录和输出目录；只读挂载输入，不能写主 Agent 的 workspace 或 conversation.json。结果由 parent 校验、登记后交给主 Agent。历史材料优先按授权 manifest 只读暂存；首版不以实现通用跨 Run 文件 broker 为前置条件。

### 5.3 将结果交回主 Agent

主 Agent 继续使用现有 system、tool schema/顺序、thinking 格式、会话身份及原生 replay。新的研究材料作为本轮动态数据追加到输入尾部，带来源和状态，明确它是参考材料；不得作为系统指令、用户新命令或已执行的主 Agent tool message 插入。

保留原用户问题，不把整段团队报告冒充用户原话。材料设置独立大小预算，超长时提供有限摘要及可读持久引用；只缩减新增材料，不能为了塞入团队轨迹主动替换已有历史。超过模型总限时仍遵守原有窗口/压缩规则并给出诊断，不能承诺团队轮次绝不触发压缩。

注入标识绑定 Run、阶段代次、result hash；同一执行重试不得重复追加。主 Agent 生成的原生快照会包含本轮已接收的有限材料及主回答，后续任何模式沿用这条历史，不再维护独立“团队会话记忆”。

## 6. 账户与计划的唯一所有者

| 行为 | 主 Agent | 团队 coordinator / 成员 |
|---|---|---|
| 账户/计划讨论、读取完整绑定资料 | 允许，使用本轮授权快照 | 不允许；只有任务所需的最小约束 |
| 补资料请求、处理业务回执 | 唯一 Agent 入口；服务端仍为数据真源 | 报 needs_context 给主 Agent，不创建用户待办 |
| 个性化仓位、风险及计划整合 | 主 Agent 使用业务工具计算与解释 | 研究公开市场、行业、公司与指定证据问题 |
| 工具审批 | 正常主流程 | 研究工具也必须按角色授权；不能借审批获得业务工具 |

这是运行时工具白名单、进程输入和授权检查的限制，不能只写在 prompt 里。团队工具只保留获准研究能力，不能通过通用 shell、网络或继承环境取得账户服务访问权限；启动环境和挂载按实际所需构造。主 Agent 自身重复调用补数工具的幂等问题继续保留，不能因取消成员业务工具便宣称已解决所有竞争。

用户中途更新账户或计划不改变本轮冻结快照；下一轮读取新版本。团队结果带旧版本来源，由主 Agent 检查适用性，不让旧研究覆盖新业务资料。

## 7. 上下文与 KV cache 的保证边界

| 事项 | 能建立的工程保证 | 不能作出的保证 |
|---|---|---|
| 纯 single | 不进入准备/team 路径；同配置输入下原请求结构、载荷、压缩与亲和策略保持基线；额外调用为零 | 超出已有窗口后仍逐字保留无限历史 |
| 混合模式 | 主会话始终只有一条原生链；主回答包含团队成果，下一轮继续该快照；不切换 root pipeline/tools | 团队简报无损，或模型永不遗漏/误解 |
| 团队成员 | 使用本轮明确简报及授权证据，任务来源可追溯 | 每个成员拥有主 Agent 全量私有上下文 |
| 缓存 | 动态材料放尾部，保护原有可复用前缀；按角色记录实际 cached tokens 和耗时 | KV 永不淘汰、固定命中率、跨模型/角色直接共享 KV |

稳定的主工作流消除了本方案引入的跨模式原始消息转换，但没有消除原有 compaction、模型窗口和业务资料时效问题。冷缓存下也必须正确续接；缓存只影响性能，不作为持久记忆或语义正确性的前提。

团队阶段独立的 session/cache 身份不混用主身份；不宣称主 Agent、team coordinator、成员的 KV 可以直接互通。额外模型调用也可能挤占提供方缓存容量，即使前缀稳定，团队轮次的命中仍需实测。

保留 tests/test_context_inheritance.py 既有长对话回归；新增模式往返、用户修正、冷缓存、临界窗口及材料超限场景。scripts/replay_stats.py 的原指标用于主 Agent，团队和准备用量单列后再聚合，不能拿总用量计算成主 Agent 的缓存命中率。

## 8. 轨迹、控制与故障语义

### 8.1 轨迹与用量

主 Agent 保留 react_agent 轨迹与旧 single 消费方式；团队阶段有独立 manifest 和来源身份。新增事件至少标识 run、stage、execution attempt、agent、local sequence，工具及审批 ID 同样带命名空间。恢复按来源游标去重，不把成员相同的 turn=1 合并。

UI 在同一 Run 下展示“准备研究 / 团队研究 / 主 Agent 整合”，成员流与主回答分开；团队报告不会自动成为聊天中的最终 assistant 回复。刷新能恢复阶段、成员报告、待审批及 Run 状态。实时与落盘读取必须归一，不能刷新后重复计费用量。缺失用量标记 incomplete，不能当成零。

### 8.2 停止、审批、插话

- stop 由 parent 覆盖排队及全部阶段，撤销待审批，终止 coordinator/成员及其进程树；确认无存活执行者后才允许同研究下一 Run。必要时强杀，超时不假报已清理。
- 多成员审批具有独立身份与请求 ID，响应只到对应工具；旧 single 审批语义保留。不能继续使用一个 pendingApproval 槽覆盖并发请求。
- steer 先归主 Agent。团队期间的新指令持久化并使旧任务标记过时；影响研究目标/硬约束的插话停止旧团队并将已得材料标为部分，由主 Agent处理；一般补充在主 Agent 整合时读取。首版不承诺把自然语言修改自动精准分发到全部正在执行的成员。
- reporter 首版关闭，team 的内部总结只是 ResearchResult；最终用户答案仅主 Agent 发布。

### 8.3 异常与恢复

团队部分失败时，只要未被用户停止且预算允许，主 Agent可基于已校验材料继续，明确哪些研究未完成；不能静默伪装成完整团队研究。用户 stop 则停止所有后续模型调用，不强制再做一次主 Agent 总结。

准备/team 阶段没有写主快照：这些阶段失败或被停止后，旧主快照仍有效，但本轮新问题/插话也尚未进入它。必须持久化一份**只含未提交用户输入、停止状态及可用材料引用**的 Run journal；下次主 Agent 启动通过工作流 Adapter 在尾部一次性补入，标明“未完成回合”，提交成功后确认消费。不得重放全部 turns 或把失败轮伪造为已回答。材料可选，未处理的用户约束不能静默丢失。

这是异常输入补偿，不是第二套长期会话摘要。M0 必须验证消费确认与主快照提交的一致性；进程崩溃、重试、重复完成帧不能导致重复输入或旧快照覆盖。主 Agent 已开始后的故障沿用现有快照恢复规则，记录实际保存进度；保存失败可见，禁止将上下文未提交标成可安全续接。

单研究互斥、执行代次与提交所有权覆盖准备到收尾的全程；删除研究、停止、迟到结果或重试时校验 Run 所有权。业务 outbox 与普通入口不能各用一套互不相识的互斥。新设计减少快照类型，不自动解决这些并发问题。

## 9. 旧方案保留与撤回

| 处理 | 内容 |
|---|---|
| 保留 | 同一研究逐轮选模式；主 Agent 专属业务；团队工具隔离、完整取消、并发审批、轨迹恢复、全队预算、证据和产物来源、版本与执行所有权 |
| 撤回 | UI mode 映射两个 root pipeline；single/team 原生快照互转；独立中性长期记忆、native coverage 与双向 head 合并；每轮维护交接摘要 |

| 另行评估 | 全平台模型配置治理、任意 pipeline 切换、自动路由、通用历史 broker，不借本功能扩大为平台重建 |

历史 v1.4 的 A01—A40 是风险查漏资料，不再逐项照抄实现；与新路线有关的发布条件集中在 §11。原先 20–31 人日等粗估失去适用条件，不继续引用。

## 10. 执行顺序与决策门

| 阶段 | 交付 | 进入下一阶段的证据 |
|---|---|---|
| M0：有限可行性验证 | 捕获现有 single 基线；只读 brief Adapter；独立 team worker；有上限材料尾部注入；异常 journal 的提交契约 | 同一测试研究完成 single → team → single；工具/system/replay 不因 mode 改变；主 Agent 读到新材料；子进程停止；失败轮约束不丢失 |
| M1：服务端闭环 | 持久化 mode/stage、预算与执行所有权；准备/团队/主 Agent 顺序编排；业务工具隔离；产物登记和恢复 | 假模型/故障注入跑通停止、超时、审批、崩溃及重试；主快照只由主 Agent 写 |
| M2：Web 与可观测 | 模式选择、阶段/成员展示、多审批、断线回放、完整用量与历史兼容 | 浏览器刷新/重连与后端落盘一致，旧 single 请求及历史不退化 |
| M3：真实任务与发布 | 小规模真实投研任务对照、长上下文、provider/沙箱与停止验证；默认关闭开关灰度 | §11 硬门全部通过，报告质量/成本实测后才启用 |

M0 先用确定性模型替身验证结构，随后在明确预算内做真实模型验证。选三类具有代表性的任务：已有研究快速追问、两个独立证据方向的深度研究、账户绑定且用户中途修正约束的多轮研究。与同配置 single 对照证据正确率、遗漏关键约束、有效来源、耗时、总 token/cost；不以“派了多人”作为收益。

**止损条件**：若必须改主 Agent 工具/system 才能完成；若团队结果无法在预算内有证据地交付；若多阶段失败无法可靠恢复；或真实任务质量没有可解释收益而成本显著上升，则不发布团队模式。保留现有 single，先修复验证暴露的问题，不返回旧双工作流迁移路线继续堆复杂度。

本次推荐只确立实现方向及验证顺序；不代表已启动所有暂缓的 Web 工作，不重排资料库和市场数据链路的既定优先级。

## 13. 灵活性与维护评估（v2.1）

### 13.1 具体含义及容易混淆之处

例如用户选择团队研究并问“结合我的计划，评估某公司的投资风险”：准备调用从已有会话提炼研究目标和允许下发的约束；team coordinator 安排行业与公司证据研究，可在预算内要求成员复核分歧；团队返回材料后，stateful-react-agent 读取原生历史、当轮完整业务快照和材料，用自己的工具计算、核实并形成最终回答。下一轮单 Agent 追问直接继续这条原生主会话。

这里存在三个不同职责：只读任务准备、团队内研究调度、用户主 Agent。准备调用不是用户主 Agent 已经跑过一遍完整业务判断；它是额外的任务提炼步骤。若描述成“主 Agent 全程指挥团队”，会夸大当前设计的能力。准备失误会导致团队查错问题，最后主 Agent 即使识别错误，也只能自行补查、说明缺口或留到下一轮，不能恢复已花掉的成本。

独立表示执行状态、工具权限、工作目录和生命周期隔离；不表示与历史研究完全无关。有限表示截止时间、用量、成员和主 Agent—团队往返次数受控；不表示团队内部必须是一张固定、不可修改的任务表。

### 13.2 灵活性逐项判断

下表评价目标设计；除明确指出的团队内部机制外，Web 接线均未实施。

| 使用方式 | 当前方向的能力 | 限制或代价 |
|---|---|---|
| 同一研究逐轮 single/team 切换 | 适合；主会话不换所有者 | 团队每轮重建，复用材料而非存活成员 |
| 团队内部拆分、复核、补查 | 可保留现有 create_subagent / assign_task / collect_reports / stop_subagent | 受预算、成员限制及现有单成员任务次数上限约束；需 Web profile/权限验证 |
| 用户在团队运行时补充背景 | 可排队交最终主 Agent | 不代表运行中成员已采用补充；需显示采用时点和任务版本 |
| 用户即时改变硬约束或研究目标 | 可以停止旧团队，带部分材料交主 Agent | 首版不承诺不停机重排所有成员；语义分类拿不准时不能让旧结果冒充已采用新指令 |
| 最终主 Agent 发现证据不足再叫团队 | 首版不支持同一 Run 内第二次团队阶段 | 主 Agent 可用原有工具补查，或明确留待下一轮；这是主要灵活性损失 |
| 先调用账户工具计算，再决定团队研究方向 | 无工具准备步骤不能完成 | 主 Agent 先处理并在下一轮研究；不应误说本路线已经覆盖任意业务前置步骤 |
| 团队中途向主 Agent 请求额外私有信息 | 首版没有同步往返业务协商 | coordinator 记录缺口，主 Agent 后续处理；成员不能为提高灵活性自行读取账户 |
| 调整成员数、研究工具、队内策略 | 可通过团队 profile 与结果契约扩展 | 新工具/角色仍须授权和用量验证；“最多 2 成员”是初始执行配置，不是永久产品语义 |
| 用户主 Agent 与团队同时研究、实时互相质询 | 当前顺序设计不具备 | 需要运行中委派、消息注入、暂停/恢复及权限机制，属于实质架构扩展 |
| 未来更换团队模型、增加专题研究 | 团队实现可在相同任务/结果 Interface 下替换 | 不能承诺零改动；模型、报告字段、引用和事件协议需要兼容测试 |

代码佐证：plugins/tools/assign_task.py 将任务排入既有成员 session，并以 MAX_TASKS_PER_SESSION 限制重复使用；collect_reports 采用可逐批收集的报告机制。这支持队内有界迭代，但没有自动建立用户主 Agent 与该团队的双向实时协作。

### 13.3 维护成本具体转移到哪里

| 维护面 | 相对双主工作流方案的变化 | 必须落实的条件 |
|---|---|---|
| 主会话与业务职责 | 减少两种快照互转及业务所有权交接 | 原生上下文继续唯一写入者；研究结果只作为本轮数据 |
| 任务准备 | 新增且容易与主 Agent 配置漂移 | 工作流侧复用同一 replay 校验与配置解析；不得复制 system/工具构造代码到 server；抽取只读准备逻辑须做请求等价回归 |
| Run 生命周期 | 从单 worker 扩大为多阶段，成本中高 | 区分 stage_finished 与 run_finished；进程退出不得提前关闭 SSE、回填最终回答或释放整个 Run 锁 |
| 控制与恢复 | 仍然复杂，无法用固定主 Agent 消除 | 取消/审批绑定阶段及执行代次；跨阶段 steer 和未提交输入持久化；停止、重试和迟到结果故障注入 |
| 任务/报告/引用协议 | 新增长期维护契约 | 有限字段、版本与来源校验；保持证据和分歧，不能只传无法核验的摘要字符串 |
| 两个现有 workflow | 两者仍需维护，并未合并为一套 | 复用 agent_team 实现及公共工具，不复制出一套 Web 专用 team 内核；Web 差异留在 profile 与 Adapter |
| 性能与排障 | 多一次任务准备和串行等待，调用链更长 | 按阶段记录错误、时间、token 和材料版本；总成本同时包含主 Agent 与团队 |

server/orchestrator.py 的 _spawn 当前持有单个 RunHandle，并在 worker 退出后统一做 artifacts、usage、conversation 和控制记录收尾；_pump_frames 在 run_finished 时回填最终 assistant，退出时关闭流。因而不能循环调用现有 _spawn 三次实现新方案：那会触发三次 Run 收尾和错误的终态语义。

此外，现有 _spawn 读取会话失败会记录日志后无上下文启动，快照入库也采用 best-effort。这是代码现状，不能把“沿用 single”说成已经具备强一致续接保证。M0 必须暴露此类失败；团队入口不能在缺失历史时悄悄生成任务。纯 single 的既有失败语义是否加固应单独明确，避免借团队接入隐式改动基线。

建议实现结构：现有 orchestrator 继续负责外部 Run、排队和终态；将阶段执行、进程控制和研究材料收集集中到一个 RunExecution Module，注入已有持久化、进程、事件及审批依赖。工作流侧 Context Adapter 负责只读准备视图，TeamResearch Adapter 负责 team profile 与结果转换。这里是局部职责划分，不建立通用 DAG 引擎；也不复制一套完整 orchestrator。single 在团队未启用时继续原路径，公共进程/事件代码按实际需要提取，避免两套收尾逻辑永久分叉。

### 13.4 维护验收与后续扩展门槛

除 §11 的正确性用例外，M0/M1 需给出以下维护证据：

1. 调整团队成员上限或工具 profile 时，不修改原生 replay、业务工具和主 Agent prompt；语义契约未变化时，Web 无须理解新内部调度细节。
2. 模拟替换团队执行器为确定性结果/故障 Adapter，可通过同一 Interface 验证收尾、恢复和材料注入；真实 team 的契约接线另作集成验证，不能只靠替身宣布通过。
3. 对阶段结束、Run 结束、断连、迟到帧、失败输入补偿进行独立测试；不靠最终回答文本是否相似验证生命周期。
4. 升级主 Agent 配置后，准备视图与正式执行使用一致的校验依据，能发现漂移；没有复制第二份 select_replay 或 prompt/tool 构造实现。
5. 关闭团队能力不影响已有 single；已完成团队结果仍可读取；没有通过屏蔽异常掩盖协议不兼容。

“固定主会话所有者”是值得保留的架构原则；“每轮一次、先团队后主 Agent”是首版策略，不能冻结成长期能力上限。若真实任务频繁需要先做业务计算或由主 Agent 多次要求团队补查，应重新评估主 Agent 运行中委派研究的方案：保留 ResearchBrief/ResearchResult 和隔离团队，改动发起时点及恢复方式。这可能涉及工具集合版本、合法历史兼容、主循环暂停/恢复，成本须单独验证，不能声称届时只加一层循环或一个工具即可升级。

**本轮判断：适合作为“批次深度研究 + 多轮追问”的首版，维护成本中等偏高但可集中；不适合直接承诺“主 Agent 与团队实时反复协作”。先验证实际工作是否接受该交互边界，再决定是否扩大实现投入。** 此结论来自代码与设计评估，尚无性能或研究收益实验结果。
